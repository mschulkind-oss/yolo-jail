## The public repo

**#37 — image staleness (Georgi Popov, external). MERGED 2026-08-13.** `AutoLoadImage` decided
"already loaded" with `loadedPaths[currentPath]` — membership in the **unordered** last-ten-loads
LRU. Nix builds are content-addressed, so reverting a config change reproduces a store path you
built before; if it is still in the history while a *newer* path is the runtime's `:latest`, the
reload is skipped and `:latest` stays stale **indefinitely, with no error**. `CurrentLoadedPath`
already existed with a doc comment distinguishing it from the LRU and **zero non-test call sites** —
written for this and never wired up. CI came back all green including both `integration` runs.

**Why it outranked its +88/−4:** it lands on the repo's *mandatory* verification method. `AGENTS.md`
already warns that a failed nix build looks like a working jail on stale code; this was a second,
quieter route to the same false green, reached by ordinary edit-revert-re-edit iteration.

**#34 — weekly `flake.lock` bump. MERGED 2026-08-13.** Three questions worth not re-asking: it *was*
a real change (nixpkgs `643809054d…` → `f13ff45afd…`); weekly (Mondays 06:00 UTC) is a reasonable
floor for a lock the whole toolchain rides; and `update-flake-lock@v28` already self-suppresses when
the lock has not moved, so there is no empty-bump PR to eliminate. **The next bump carries a closure
diff (D3), so this was the last opaque three-liner.**

**What a lockfile's three lines actually are**, since the question recurs: `rev` is the nixpkgs git
SHA and is the whole input; `narHash` verifies the fetched tree; `lastModified` is the tip commit's
timestamp — **descriptive metadata, not a filter.** Nothing queries by it. What decides *what*
resolves is `nixpkgs.url = "github:nixos/nixpkgs/nixos-unstable"` in `flake.nix` — track that branch
head.

**#33 — `ca.key` mounted into every jail (Dong Liu, external). FIXED and pushed.** The loophole
manifest gained an optional `state_files` key naming the state-dir subset that crosses; the broker
declares `["ca.crt", "server.crt", "server.key"]`, each a `:ro` file mount, and the state
**directory** no longer crosses. Omit the key and the whole dir mounts as before, so no external
manifest changed meaning. Verified in a nested jail: `ca.key`/`ca.srl`/`leaf.cnf`/`refresh.lock`
absent, terminator still serves TLS, `curl` verifies against the mounted CA
(`ssl_verify_result=0`). Pinned by `TestBundledBrokerNeverMountsItsPrivateKey`, which fakes a full
state dir against the manifest that *actually ships*.

**Two corrections worth carrying.** (1) The scoping line said "only `server.crt`/`server.key` are
needed in-jail" — **`ca.crt` is needed too**, because `NODE_EXTRA_CA_CERTS` points at it and the
entrypoint merges it into `$HOME/.yolo-ca-bundle.crt`, which `SSL_CERT_FILE`, `CURL_CA_BUNDLE`,
`GIT_SSL_CAINFO` and `REQUESTS_CA_BUNDLE` all reference. The line that matters is **public vs
private**, not ca vs server. (2) The severity was **overstated** as a privilege-boundary failure. It
is not auth escalation: `ca.key` supplies a trusted cert but not the ability to redirect a victim's
traffic, and against the attacker's own jail it adds nothing a UID-0 process can already do. Full
analysis: [`../design/loophole-transport.md`](../design/loophole-transport.md) §5.0.

## Code

**V2 — `apply --host` converges after ONE apply, not three.** Root cause was *misattribution*, not a
write bug: `rmwProvenance`'s `host` pass read the file *before this render* as the user's layer, so
apply 1's own fill-if-absent write made apply 2 relabel `defaults` → `host`. Three provenance files
flapped. The fix is gated three ways and carries an **inverse test** — a default the user genuinely
edits must still go to `host` — which is what stops it becoming "always say defaults".

**V3 — one archive bucket per kind** (`skills`/`files`/`briefing`, plus `retired` for the
kind-agnostic dropped-pack pass). Legacy `archive/skills` copies stay exactly where their report
said; what changed is the sweep, which now enumerates buckets instead of naming one.

**D3 — `flake.lock` bumps are reviewable.** The weekly workflow builds `.#imageClosureRoot` (a new
flake output: the nixpkgs half of the image's contents, our Go build excluded, so both sides of the
diff are a *download* from cache.nixos.org rather than a build) against the old and new lock, and
appends `nix store diff-closures` to the PR body. Rehearsed on the real 08-05 → 08-12 pair. Path
count is reported alongside versions because a staging-next merge that rebuilds the world without
moving a version is otherwise invisible. Runs *after* the PR exists and `continue-on-error`, so it
can only add to a bump, never block one. **Unverified until the first Monday run: the `gh pr edit`
hop.**

**E4 — comments survive a `rmw` TOML render.** The design doc ranked this option third *for
`stateful`*; for `rmw` it is nearly free, and the mode is the reason — three of the four costs
priced there are costs of **captured state**, which an `rmw` surface has none of (its source and
destination are the same file, read and rewritten in one operation). Per-mode ruling: `rmw`
preserve (its contract already promised it); `computed` **correctly does not** (yolo is sole author,
so any comment would be one *yolo wrote* — a different feature); `stateful` remains open as OQ-E4.
The `json` half is **provably vacuous** — strict JSON has no comment syntax, so a commented `json`
surface never decodes and the RMW path refuses it byte-untouched, now pinned by a test.

**D2 and two more doc/code contradictions.** `USER_GUIDE.md` and the broker README both claimed *"no
background timer / no proactive refresh"* while `oauthbrokercmd.go:88` starts `RunBackgroundRefresher`
by default — and that loop **is** architectural, because Claude Code has no proactive refresh of its
own for Pro/Max tokens, so an idle jail or a suspended host would otherwise wake up logged out.
Separately, the USER_GUIDE security note claimed the broker *"mirrors the new tokens"* into the host's
`~/.claude/.credentials.json`. **It cannot** — `rg 'host-creds'` finds nothing in non-test code
(deleted in `cb6e850`) and the mirror writes only the shared file. A false claim about touching real
host credentials is the expensive kind.

**B4 — `agent-credentials.md` §3 corrected.** It documented Bedrock keys arriving via the `env` block
of host `settings.json`; that block is `{}` and always was — the real path is `env_sources`. Kept
pointed forward rather than deleted: the `env` block is the right *target* design, because it is the
one channel rendering at **both** notches, which is what makes a Bedrock auth pack host-complete.

## S4 — AUDITED: the gate holds. Do not re-audit this.

Both readings of the code were right about **what it does**; the conclusion drawn from them — that
the selection gate has a hole — was **wrong**. All three probes ran, probe 1 twice, the second time
in a real nested jail.

- **Probe 1 — `into` is honored with no matching agent selected. TRUE.** `.codex/skills` created,
  populated and bind-mounted with only `claude` selected.
- **Probe 2 — every pack's skills reach every destination. TRUE.** Two packs, two destinations, one
  distinct skill each; both destinations staged both skills.
- **Probe 3 — the notches disagree.** The jail delivers the full cross product; `apply --host`
  delivers only the declared pairing.

**Why it is not a hole.** `into` is a **path**, and core deliberately has no concept of an agent to
check it against (`internal/packdecl`'s opening premise). Every destination traces to a `skills`
contribution on a pack in `packs`, and `packs` is **user-scope only** — so a repo-committed config
still cannot add a destination. The mise-trust shape was an enforcement point a lower layer could
bypass; nothing bypasses anything here. Selecting a pack is consent to its declared destinations,
and they are inspectable beforehand via `yolo pack footprint`.

**What the probes did find** is a reporting gap, not a security one: a pack's manifest understates
where its content goes, because the merge is global. That is intended and load-bearing — it is what
makes a zero-ceremony pack deliver anything — and whether the jail should narrow to match the host
is **OQ-S4**, still open in [`outstanding-work.md`](outstanding-work.md).

Pinned by `internal/cli/run/packskillsdelivery_test.go`, so answering OQ-S4 either way moves a test
deliberately rather than rediscovering the behavior.

### Three arguments of mine that review withdrew

Kept because the corrections are more useful than the conclusions:

1. **`SO_PEERCRED` as the reason to keep the Unix socket.** It cannot distinguish the jail from a
   same-user host process — rootless podman maps the container's UID 0 to the invoking user's uid,
   so both arrive with the *same* uid. The protocol doc said so all along (*"the jail (and anything
   else running as the same user on the host)"*), which is only true **because** peer credentials
   cannot separate them. I cited as decisive a mechanism that answers a question with one possible
   answer.
2. **"The same-user gap is the widest weakness in the loophole model."** It is not a weakness — it
   is the **specification**, chosen to match the host, where anything running as you can already act
   as you. A mechanism that "closed" it would make a tighter claim than the product makes.
3. **"mTLS carries identity a bearer token does not."** False at **one relay per jail**: the relay's
   token *is* its jail's token, so a match identifies the caller structurally. Only a *shared* relay
   would reopen it.

## The process lesson

**"Stage by explicit path" is NOT sufficient with concurrent agents.** It failed six times on
2026-08-12: `git add <path>` stages the **whole file** into a **shared** index, so whoever commits
next sweeps everyone else's staged work into their own commit. Content survived every time — only
attribution scrambled, and no agent reached for `--amend` (correctly; this repo forbids it).

**The fix, found by one of the agents: `git commit -- <paths>` with no staging at all.** That form
commits exactly the named paths from the working tree and ignores the index entirely. It belongs in
every concurrent-agent brief.
