# One launch owns cancellation of its parallel extension builds

**Status:** 2026-10-08. Built on the local branch `lane/pi-cancel` (two commits, not on main). The repair and one independent review's fixes are in: a cancel that dispatched no backend is not retained, a retained workspace is never a failed build, and admission waits out late container removal. Targeted unit, race and mutation checks and the four fork/patched-extension integration tests are green on Linux. The parent's combined gates and non-Linux runtime verification remain.

## 1. What startup actually schedules

A fresh container launch runs the host-side install capture first, then the fork-build slot, before image load and before the new jail's command starts (`internal/cli/run/run.go`, `internal/cli/run/buildslot.go`). The slot is one `buildPool`: checks and builds run concurrently up to their independent limits, and every running build is a `yolo internal fork-build-jail` child (`internal/cli/buildpool.go`, `internal/cli/forkbuildchild.go`). Patched Pi extensions therefore compile in sealed build jails during the host launch, in the same pool as patched forks. A child build is a complete nested launch and owns its own signal arms and keeper-managed jail.

This ordering distinguishes the reported startup from two later paths. The host's TTY proxy wraps the container command after the startup build slot; it does not own this build-phase interrupt (`internal/ttyproxy/ttyproxy.go`, the container arm in `internal/cli/run/run.go`). After the jail boots, Pi's declared `update --extensions` refresh runs from its generated launcher before Pi execs (`packs/pi/pack.json`, `internal/entrypoint/prelaunchrefresh.go`); its no-terminal wrapper already forwards signals to the refresh process group (`internal/notty/notty.go`). Those are real signal paths, but neither schedules the sealed parallel builds repaired here. The entrypoint's program-readiness act is also separate from these host-side capture builds.

## 2. Root cause and evidence

The launch's `ActInterrupt` is the single owner for the pool's whole wait (`internal/cli/run/interruptscope.go`, `internal/cli/buildslot.go`). Before this repair, the fork-build child inherited the launch's process group. A terminal Ctrl-C could therefore arrive independently at the launch and its build children, while cancellation from the act forwarded SIGINT only to `cmd.Process`, not to the compiler descendants. The child uses non-file stdout/stderr writers, so `os/exec` copies through pipes; a compiler subprocess retaining those descriptors can keep `cmd.Wait` from returning after its parent exits. A clean child exit status was also returned unchanged after context cancellation, allowing a child that handled SIGINT and exited zero to look like a successful build.

The permanent Linux test `TestTheLaunchBuildPoolStopsCompilerDescendantsOnOneInterrupt` runs the real pool and real child runner behind a controlling pty. Five harmless compiler fixtures compete for four build slots; four write partial output and block with a descendant holding the output pipes. One terminal Ctrl-C must return in under two seconds, report interrupt status 130 even when the child exits zero, stop/reap the active descendants, start no fifth worker, leave no success marker, drain output, and permit a successful subsequent run. A companion test proves an interrupt-ignoring descendant is killed after the grace. The original fail-first timeout and the final forwarding-call mutation failure are preserved outside this public doc; the QA record below states the commands and results.

## 3. Required repair contract

The following specifies the required repair, not current main behavior. Each `fork-build-jail` child starts as leader of its own process group. The launch's act scope forwards SIGINT to the whole group, waits up to five seconds, then SIGKILLs the group. The child has explicit stdout/stderr pipes, and its output and jail-stream copies drain concurrently under a five-second bound; incomplete output is a failed build, not a truncated success. A context-cancelled child always reports 130 regardless of its own exit status, so a child that handles SIGINT and exits zero cannot publish partial work as a successful build. Ordinary compiler failures and fully-drained successful builds retain their existing status behavior.

A forced child stop cannot establish that its detached jail keeper or runtime teardown is complete. In that case the build keeps its staging tree and host-side jail state instead of deleting them on return. Before a same-key retry can clean those paths or call `Store.Stage`, it must take the workspace launch lock without waiting, establish that the keeper is gone, and get a known-absent answer from the original capture backend. That backend is not guessed from environment variables or PATH: the build's ordinary `run.Run` pipeline records the final validated runtime it actually resolved, after confinement and automatic fallback, before dispatching to the native/container backend. The record lives outside the jail-mounted stage; a keeper start record, when present, must agree. If the run never resolves/records a backend, ownership is unknown and reuse refuses, with one exception: when a stopped build child's whole process group is confirmed gone and it never recorded a runtime, it never reached `run.Run`'s dispatch, so nothing can own its workspace and the build cleans it (`TestACancelledForkBuildThatDispatchedNothingIsNotRetained`; amended 2026-10-08 after review, because the unconditional rule fenced a key for good on a Ctrl-C during checkout). A finished build waits a bounded 30 seconds for its original backend to report the container absent before declaring its output unowned, since `--rm` removal can trail the keeper (`TestAFinishedForkBuildWaitsOutLateContainerRemoval`). Every refusal of this kind is a retained workspace, not a failed build: a patched advance records no outcome and starts no back-off for it, and the next launch builds the commit (`TestARetainedPatchedBuildIsNoFailedBuild`). Cleanup drops the runtime and run-returned records only once the staging tree and jail state are actually gone. Busy/unknown locks, a live keeper, or a live/unknown original runtime also refuse. A backend change is allowed only after the original backend is known absent. `macos-user` has no container listing or native capture completion witness, so an abnormal stop remains unknown; its refusal names the build ID and retained paths and requires a host operator or maintainer to verify that specific native capture has ended before clearing them. `TestForkBuildRetryWaitsForDetachedKeeperEvenWhenContainerIsAbsent`, `TestForkBuildRetryRequiresWorkspaceLaunchOwnership`, `TestForkBuildRetryUsesRetainedBackendWhenRuntimeIsUnspecified`, `TestForkBuildRetryDoesNotProbeTheNewBackendForOldOwnership`, `TestForkBuildRuntimeRecordMatchesChildResolution`, `TestForkBuildRetryWithoutResolvedBackendEvidenceFailsClosed`, `TestResolvedRuntimeHookSeesAutomaticFallback`, `TestMacosGuestNotchLaunchesTheMacosUserBackend`, `TestCancelledForkBuildKeepsWorkspaceUntilItsDetachedKeeperStops`, and the macos-user tests exercise these production cleanup boundaries.

The scope stays narrow: no serialized builds, automatic retry loop, extra CLI layer, weaker readiness check, Pi SDK hook, or TTY-proxy behavior change. Store admission still owns its completion marker, written last; an interrupted partial capture remains unavailable and is rebuilt after its previous jail is known gone, as `internal/capture/store.go` and `TestTornAdmitReadsAsAbsentAndIsRedone` establish.

## 4. Plan and remaining verification

The implementation checklist and local QA are in [`pi-startup-cancellation-plan.md`](pi-startup-cancellation-plan.md) and [`../plans/pi-startup-cancellation-qa.md`](../plans/pi-startup-cancellation-qa.md). The separate background-update thread is in [`roadmap.md`](../plans/roadmap.md), whose owned detail is [the background update mode for what yolo builds](pi-extension-store-builds.md#XB-D42); that broader work is separate from this cancellation repair, and no roadmap status is repeated or changed here.

Linux pty tests prove Linux terminal signal delivery and Unix process-group cleanup only. They do not prove macOS/XNU terminal signal ordering, rootless runtime teardown, Apple Container behavior, or macos-user behavior. Two lifetimes remain distinct: a compiler process that deliberately calls `setsid`/`setpgid` escapes the build child's group and cannot be killed by group cleanup; bounded inherited-output drainage detects only the cases that retain a pipe, fails the build, and cannot reap an escaped process. Separately, the capture jail's detached keeper/runtime teardown can outlive the build-child group even when ordinary compiler descendants were killed. That is why the staging and host-side jail state stays fenced until container liveness is known gone; macos-user has no such witness and requires specific host-operator verification after an abnormal stop. Current build tools are expected to inherit the build-child group. The parent must run the combined `just check-ci`, build the Go binary, exercise the fresh binary in a throwaway nested workspace, and run the applicable launch integration suite. No pack-program bytes changed, so no pack-binary pin update is expected.
