# Native Claude coordination: verify the bridge, then the ruled view

**Status:** 2026-10-20. The owner authorized the synthetic-first contract, harness and runbook slice only. Synthetic tests built in `54038ec3f` pass on Linux/amd64 with btrfs scratch storage; existing launch wiring checked against `f8478d3b7`. No native Claude login or refresh run here. Release publication is unconfirmed and not a prerequisite for this bounded work.

> **In short.** The existing native shared-file bridge may already coordinate Claude's direct refreshes through Claude's own machine-scoped file lock. Measure that first; separately, verify the existing broker-written credential view before proposing any native rollout.

**Why it matters.** A host broker starts natively but a running broker alone does not prove Claude's requests reach it; conversely, the absence of a native terminator does **not** prove direct refreshes race.

**Start at [what exists](#what-exists-and-what-is-ruled)** — this document does not supersede the owning view design.

**Needs your ruling:** None here. [The existing replacement ruling](claude-login-without-interception.md#11-decision-ledger) and [one-machine-login ruling](../reference/claude-oauth-interposition.md#OQ-CI1) already settle direction; hardware results may raise a *new* decision later.

**Reads with:** [the bounded implementation plan](macos-user-claude-refresh-plan.md) (synthetic slice only), [Claude login without interception](claude-login-without-interception.md) (owning design), [native home tiers](../reference/macos-user-home-tiers.md) (workspace boundary).

## What exists and what is ruled

**Terminator declined; broker not rejected.** The precise [native ruling](../reference/macos-user-nix-and-features.md#the-oauth-terminator-stays-declined) says not to start or defer the TLS terminator: a sandbox account cannot bind its fixed privileged port 443, and a native backend with a shared Mac resolver has no container `--add-host` to route just this jail's `platform.claude.com` to it. [The guest filter](../../internal/loopholes/guestrun.go) keys on `Intercepts`, not the broker's name. Host-global DNS/hosts edits would cross the native boundary and are not authorized. The older assertion that the whole broker is off was explicitly retracted in [the native reference](../reference/macos-user-nix-and-features.md#the-oauth-terminator-stays-declined).

[The selected Claude pack](../../packs/claude/pack.toml) contributes a default-enabled [broker host daemon](../../packs/claude-auth/loopholes/claude-oauth-broker/loophole.toml), a machine `.claude-shared-credentials` directory, a workspace `.claude` and the shared-credential hook. Native starts the host service and [registers an opted-in view after it starts](../../internal/cli/run/run.go#L792-L805). The [per-launch ownership ruling](host-daemon-ownership.md#HD-D29) already performs a locked at-launch catch-up for a near-expiry canonical login, without a background timer while no jail runs. Its shared broker flock prevents two broker processes from redeeming the same canonical token, but default native Claude does not use the declined terminator. A published broker endpoint is not a vendor-supported refresh URL.

**The direct-refresh bridge is already built.** [CL-D22](claude-login-without-interception.md#CL-D22) places Claude's file and its `.oauth_refresh.lock` and `.storage-write.lock` together with `CLAUDE_SECURESTORAGE_CONFIG_DIR`; the [native launch supplies that variable](../../internal/cli/run/run.go#L1052-L1056) when the view is off. The [credential reference](../reference/agent-credentials.md#the-claude-oauth-broker) says the two native sessions reach one real directory through one kernel, so vendor lock contention is **inferred**, not hardware-proven. Do **not** design around the assumption that this lock fails. Measurements must determine whether native Claude uses that directory or Keychain for ordinary login, refresh and logout and whether its file lock actually serializes two clients. The cross-VM Apple Container lock question is separate.

**The replacement is already ruled.** [OQ-CL1](claude-login-without-interception.md#11-decision-ledger) approves a broker-written access-token-only view replacing interception everywhere after the [existing measures](claude-login-without-interception.md#7-what-must-be-measured-before-building) and a day on a real rootless host, rather than keeping a permanent second path. [CL-D11](claude-login-without-interception.md#CL-D11) keeps it off by default everywhere until measured. Native [view registration](../../internal/cli/run/claudecredentialview.go) is already wired; the view and shared-store pointer are mutually exclusive. The broker owns the canonical refresh token under a host lock and writes each registered workspace an access token and real expiry **without a refresh token** ([view contract](claude-login-without-interception.md#51-one-writer-one-view-per-workspace)); this would remove direct refreshes *if* native Claude reliably reads that view. [OQ-CI1](../reference/claude-oauth-interposition.md#OQ-CI1) chose one machine login and [OQ-CL2](claude-login-without-interception.md#11-decision-ledger) chose jail `/login` enrollment, workspace `/logout` and host machine logout. Do not reopen either because a native experiment has not yet run.

## The native measurement contract

**Phase S — synthetic contract only, authorized now.** Two fake participants use a fresh temporary directory named by `CLAUDE_SECURESTORAGE_CONFIG_DIR`, with the fake credential file, `.oauth_refresh.lock` and `.storage-write.lock` co-located. Check kernel directory-lock contention, rereading after a cooperating writer releases its storage lock, and the existing shared-file writer's atomic replacement. A killed fake storage-lock participant leaves a directory, not a kernel-held lock: check the existing writer's stale-directory recovery and bounded unlocked-write fallback, without claiming vendor recovery semantics. Preserve the refresh-lock directory across a storage write. All bytes are fixed fake literals; no real CLI, keychain, settings or login is consulted. A fixture success establishes only the participants' specified protocol and yolo's writer behavior on the tested filesystem. It cannot establish that Claude honors that protocol. See [the synthetic runbook](../plans/runbooks/macos-user-claude-synthetic-measures.md).

**Phase A — establish the current bridge's behavior, without assuming a failure.** On a later owner-authorized disposable native workspace pair, record the CLI version and which store native Claude selects: the sandbox account's shared credential directory, its own Keychain or both. Observe whether two overlapping sessions' vendor lock acquisitions truly serialize, whether the second rereads the replaced file before it attempts a refresh, whether both show a valid login after a token rotation, and whether ordinary `/login` and `/logout` use the same selected store. This is a Mac hardware/vendor-behavior check, not a new architecture gate: a successful lock measurement establishes coordination on the *present* native path even while the replacement rollout remains pending. A failed measurement requires a redacted reproduction and owner discussion before any new mechanism is selected.

**Phase B — verify the already-built view.** Follow [the existing measurement runbook](../plans/runbooks/claude-credential-view-measures.md) for a native Mac with a disposable login and the opt-in switch, checking the [view design's native caveat](claude-login-without-interception.md#11-decision-ledger): no-refresh-token file adopted at startup, external update while idle, revoked/old-token 401 recovery, restart, two distinct workspaces concurrently, login adoption, per-workspace logout and host logout. Confirm the native client does not prefer an unrelated Keychain credential while the view is selected. Observe sleep/wake at-launch catch-up and daemon shutdown while a refresh is in flight. The rootless-host day and other-backend requirements of [OQ-CL1](claude-login-without-interception.md#11-decision-ledger) remain independent; a native success alone cannot authorize global deletion.

The Mac agent may inspect fixture layouts, `claude --version` and sandbox/ACL behavior without login. **This design lane does not run a client session, API call or refresh, read actual tokens, request root, or change a credential.** Only an owner-authorized person or explicitly authorized Mac test session can perform the real-login trials later. Capture version, elapsed times, status classes and redacted token fingerprints only; no full credential, request body or upstream response is persisted. Synthetic fixtures can assert shared lock path, one mock upstream redemption per input, safe view registration and failure notices without any real token. Such fixtures cannot certify Keychain/file precedence, real vendor lock behavior or 401 recovery.

## Boundary and fallback

[Native home tiers](../reference/macos-user-home-tiers.md) link each workspace's `.claude` to its own overlay but keep `.claude-shared-credentials` in the sandbox account's machine tier. That account may reach the machine tier: a native shared login already crosses workspace boundaries. A view is a workspace file, but replacing the shared path does not by itself establish that another workspace's sandbox process cannot read it. A future claim of *isolation* depends on the workspace/profile lane's boundary and [the open same-UID threat-boundary question](./macos-user-concurrent-workspaces.md#OQ-MCW2); this lane does not choose a shared-home redesign. [The host-keychain ruling](keychain-from-a-jail.md#8-decision-ledger) keeps the real keychain on the host; its [native client-route question](keychain-from-a-jail.md#OQ-KC5) remains separate. Neither an unlocked sandbox keychain nor copied host credential is selected here.

A possible [launch-owned doorway](host-notch-services.md#HS-D15) requires a **supported** Claude client address override and authenticated, pinned, disclosed loopback TLS. [The existing seam survey](claude-login-without-interception.md#31-the-endpoint-cannot-be-moved) found no supported Claude refresh-URL override. If the view fails on native hardware, state the supported external capability needed and return to owner discussion; do not add a doorway nothing dials, intercept a hostname, inject a CA, loosen TLS, force a global proxy, patch Claude/Pi or deliver a standing refresh token to a second writer. Errors should name the human login or host `yolo claude-auth status` path rather than silently claiming coordination. The existing view's safety and failure semantics remain owned by [the view design](claude-login-without-interception.md#51-one-writer-one-view-per-workspace).
