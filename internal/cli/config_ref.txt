[bold]YOLO Jail Configuration Reference[/bold]

[bold cyan]CONFIG FILE: yolo-jail.jsonc[/bold cyan]

  Location: Project root (per-workspace)
  Format:   JSON with comments (JSONC)
  User defaults: ~/.config/yolo-jail/config.jsonc
  Local overrides: yolo-jail.local.jsonc (sibling, auto-merged when present)
  .json spellings: yolo-jail.json and yolo-jail.local.json are read in place
    of a missing .jsonc file of the same name.  Never create the .jsonc file
    beside one: yolo reads it instead, and ignores the .json file.

  [bold]THE WORKSPACE IS THE DIRECTORY YOU RUN `yolo` IN[/bold], and it is
  bind-mounted [bold]read-write and LIVE[/bold] at [bold]/workspace[/bold].
  `cd ~/code/sysadmin && yolo` makes ~/code/sysadmin *be* /workspace — the same
  files, not a copy, with no sync step in either direction.  It does NOT appear
  under /ctx/, and it must NOT be listed in `mounts`: that key is for paths
  OUTSIDE the workspace, and it is read-only unless an entry says otherwise.
  It is literally the cwd — there is no `--workspace` flag and no walk up the
  tree looking for yolo-jail.jsonc.  Launch from a subdirectory and THAT
  subdirectory is the whole workspace, with its own config and its own jail.

  Workspace config merges over user defaults; a sibling
  `yolo-jail.local.jsonc` merges over the workspace config automatically —
  no include_if_found entry needed. Keep it out of git (global gitignore)
  for per-machine tweaks that don't belong in the tracked config.
  Lists are merged and deduplicated. Scalars override.

  [bold yellow]Rule:[/bold yellow] After [bold]EVERY[/bold] edit to `yolo-jail.jsonc`,
  `yolo-jail.local.jsonc`, or `~/.config/yolo-jail/config.jsonc`, run
  `yolo check` before restarting or asking a human to restart the jail.
  Use `yolo check --no-build` inside a running jail for a faster preflight.

  A refusal or warning about a key starts with where the key is written, as
  `<file>:<line>:<column>: config.<key>: …`, the column being where its value
  starts (a list entry at the entry's own line): the file whose value takes
  effect.  Any other file writing the same key is named after the message,
  "(also written at …)".

[bold cyan]USER SCOPE INSIDE A JAIL[/bold cyan]

  What a jail sees as `~/.config/yolo-jail/config.jsonc` is [bold]GENERATED[/bold] at
  launch — not your real file. It is your effective config filtered down to the
  keys the commands in a jail can actually judge, with a header saying so.

  Two consequences worth knowing:

  • [bold]Keys are missing on purpose.[/bold] Anything whose referent does not exist in
    a container (`gpu`, `devices`, `kvm`, `mounts`, `cache_relocations`) or whose
    meaning would change (`host_files` — "the host home" is the jail's own home in
    there) is filtered out. Evaluating them in a jail reported problems you do not
    have. Your host config is untouched.
  • [bold]It is frozen at launch.[/bold] Editing your user config on the host applies to
    the NEXT jail, not the running one. `yolo config drift` covers the workspace
    config and says so; `yolo config dump` prints the effective config a jail is
    actually running under.

  A jail that can nest also gets `inherited-launch.jsonc` beside it: the keys an
  inner `yolo` composes a nested jail from (`packages`, `packs`, mise tools,
  resources). On a backend that cannot nest, that file is simply not written.

  [bold]--user-layer <file>[/bold] (a global CLI flag, not a config key) layers a JSONC
  file in at user-level precedence for one invocation. It is inert unless passed,
  and a workspace config still wins over it. Inside a jail it is how you grant
  yourself more than you inherited — e.g. add a `packs` entry naming a pack that
  ships a loophole, then `yolo pack install` and launch a nested jail. There is
  deliberately no conventionally-named auto-merged file: a file that takes effect
  because it exists is invisible at the call site.

  Developing a loophole inside a jail, end to end:

    mkdir -p ~/.local/share/mypack/loopholes/mine   # NOT ~/mypack — the home
                                                    # ROOT is read-only
    ...write pack.json and loopholes/mine/manifest.jsonc...
    cat > ~/.config/yolo-jail/my-layer.jsonc <<'EOF'
    { "packs": [ { "source": "file:///home/agent/.local/share/mypack" } ] }
    EOF
    yolo --user-layer ~/.config/yolo-jail/my-layer.jsonc pack install
    yolo --user-layer ~/.config/yolo-jail/my-layer.jsonc loopholes list
    yolo --user-layer ~/.config/yolo-jail/my-layer.jsonc -- bash

  The layer lands beside the read-only inherited config because ~/.config is the
  jail's own writable dir — that is why the inherited file is delivered as a
  single file rather than by mounting the directory.

[bold cyan]FIELDS[/bold cyan]

  [bold]confinement[/bold] (string): How confined the environment is — the dial, separate
    from the MECHANISM (runtime) that enforces it.
    Values: "jail" (default) | "guest" | "host".
      • [bold]jail[/bold] — a container (podman / Apple Container): namespaces, a disposable
        home, a baked image, NONE of your credentials. The default and what
        `yolo -- <cmd>` gives you.
      • [bold]guest[/bold] — a real home on the real filesystem, no image, an LSM boundary
        (Seatbelt on macOS, bwrap+Landlock on Linux), its own separate identity.
      • [bold]host[/bold] — you, your machine, your dotfiles, your credentials. EXPLICIT
        opt-in only: never inferred, never a fallback. `yolo host apply`
        renders your agent config into your real home.
    The three are presets over composable primitives (separate user / Seatbelt /
    bwrap / namespace); you pick a notch, not a hand-assembled policy.
    NOTE: guest and host are being built out (env-manager plan); jail is fully
    supported and is the default, so an absent key is exactly today's behavior.

  [bold]runtime[/bold] (string): Isolation MECHANISM inside the jail notch (a hint, not policy).
    Values: "podman", "container", or "macos-user".
    Override: YOLO_RUNTIME env var takes priority.
    Auto-detect: macOS prefers "container" then "podman"; Linux uses "podman".
    On Apple Silicon the container is native arm64 (no emulation).
    "macos-user" (macOS only, EXPLICIT opt-in — never auto-detected) runs the
    agent as a dedicated macOS user under Seatbelt: NO VM, no Linux image,
    "packages:" materialized as native darwin nix for THIS Mac's arch (Apple
    Silicon or Intel — the system is derived, not assumed). Fastest startup,
    but a WEAKER isolation boundary than a container/VM. (Under the confinement
    dial this is the `guest` notch by another name; `runtime` stays for
    compatibility and as the in-jail mechanism hint.)

  [bold]agents[/bold]: [bold yellow]REMOVED[/bold yellow] — which agents a jail gets is no longer a
    config key of its own.  An agent arrives as a pack, so name the pack that
    installs it in [bold]packs[/bold] instead.  A config still carrying `agents` is a
    `yolo check` error.

  [bold]packages[/bold] (array): Extra nix packages baked into the image.
    Supports three formats:
    • String: a nixpkgs attribute path (latest from flake's pin).  An entry
      installs what `nix build nixpkgs#<entry>` builds, so a dot reaches into
      whatever the name before it holds: an output or a collection member.
      Examples: "postgresql", "gtk4.dev" (gtk4's dev output),
                "rocmPackages.clr" (a member of the rocmPackages collection),
                "rocmPackages.clr.icd" (that member's icd output)
      A name that is not letters, digits, '_' and '-' is quoted as Nix quotes
      it: "nerd-fonts.\"m+\"".  A bare collection ("rocmPackages") is refused,
      naming members you could write instead.
    • Object with nixpkgs: pinned to a specific nixpkgs commit
      Example: {"name": "freetype", "nixpkgs": "<commit-hash>"}
    • Object with version override: build from upstream source
      Uses the existing nix build recipe but swaps version+source.
      Example: {"name": "freetype", "version": "2.14.1",
                "url": "mirror://savannah/freetype/freetype-2.14.1.tar.xz",
                "hash": "sha256-MkJ+jEcawJWFMhKjeu+BbGC0IFLU2eSCMLqzvfKTbMw="}
      Get the hash: nix-prefetch-url <url>  (then convert with nix hash)
      Or set hash to "" and nix will tell you the correct one on build failure.
    • Any object form may add [bold]platforms[/bold]: the entry applies only on
      those platforms, and is EXPECTED-absent elsewhere rather than an error.
      Values are Go GOOS spellings — "linux" or "darwin" — not nix system
      doubles ("x86_64-linux"); an unknown value is a config error, because an
      entry that matched nothing would drop the package everywhere in silence.
      Example: {"name": "strace", "platforms": ["linux"]}
      A bare string, and an object WITHOUT platforms, apply everywhere.
      On the macos-user backend a declared package with no native build is a
      FATAL launch error naming every such package at once — marking it
      linux-only is how you say that absence is intended.  It still installs
      normally in a container.
    Find nixpkgs commits per version: https://lazamar.co.uk/nix-versions/
    Search package names: https://search.nixos.org/packages
    Image rebuilds only when this list changes.
    Nix caches builds — identical configs across jails share cached results.

    Shared libraries: each package's shared libraries are symlinked into
    /lib and /usr/lib, so a package added for its .so (zbar, libdmtx, ...)
    is dlopen-able by bare soname (e.g. ctypes.CDLL("libzbar.so.0")). This
    works via LD_LIBRARY_PATH=/lib:/usr/lib, which the jail sets in every
    process — so a consumer that scrubs LD_LIBRARY_PATH won't find the lib
    (the loader does not use /etc/ld.so.cache in this image). The correct
    shared-lib output is picked automatically (e.g. zbar ships its .so in a
    separate "-lib" output), so a bare "zbar" just works — no need to spell
    ".lib". A ".dev" request (e.g. "lilv.dev") contributes the package's
    runtime libraries too — and those of its propagated closure — so
    binaries you build against it also load: compile with pkg-config, run
    without extra LD_LIBRARY_PATH fiddling.

  [bold]include_if_found[/bold] (array of strings): Layer in sibling override files.
    Each entry is a relative path resolved against the including file's
    directory. Missing files are silently skipped — keep entries that may
    or may not exist on a given machine (an untracked *.local.jsonc, secrets,
    machine-specific tweaks). Present files are loaded and merged on top
    (later wins; lists concatenate-and-dedup; nulls disable). Includes can
    declare their own `include_if_found`; cycles are detected and broken.

    Common use: each level (user config, workspace config) references an
    untracked sibling that adds custom MCP servers, agents_md_extra notes,
    or env_sources entries without committing them.  yolo git-ignores only
    .yolo/, so add such a file to your .gitignore yourself.

    Note: the workspace-level `yolo-jail.local.jsonc` no longer needs an
    include entry — it is auto-merged whenever it exists (listing it
    anyway is harmless; it won't merge twice). include_if_found remains
    for other file names and for the user-level config.

    Example (~/.config/yolo-jail/config.jsonc):
      "include_if_found": ["overrides.jsonc"]

  [bold]agents_md_extra[/bold] (string): Markdown appended to every agent's briefing.
    Whatever you put here is concatenated onto the jail-managed section of
    AGENTS-copilot.md, AGENTS-codex.md, and CLAUDE.md before the host-level
    user content is prepended.  Use it to surface per-jail notes that every
    agent should see — "this jail has cerebras-mcp wired up, prefer it for X",
    project-specific quirks, links to the right runbook, etc.

    It reaches your real home too: `yolo host apply` writes the USER-scope
    value (~/.config/yolo-jail/config.jsonc) into every briefing file your
    packs name, after the section saying the agent is on your real machine
    and before your packs' prose.  A workspace value never leaves the jail.

    Pairs naturally with include_if_found: put it in a local overrides file
    you keep out of git, so the note rides along with custom MCP servers.

    Example:
      "agents_md_extra": "## Cerebras MCP\\n\\nUse cerebras-mcp for X."

  [bold]briefing_provenance[/bold] (boolean, default false): Label each pack's prose in
    a composed briefing with a `<!-- from pack: NAME -->` line.  Off by default:
    your packs are your rules for every repository, and a per-pack label made
    agents read them as someone else's.  Claude Code strips HTML comments from
    CLAUDE.md before the model reads it, so for Claude the label is only ever
    visible to a human opening the file.  Turn it on to debug which pack a rule
    came from.  Read from the effective config for the jail's own briefing and
    from the user config by `yolo host apply`; set it in the user config to
    change both.

    Example (~/.config/yolo-jail/config.jsonc):
      "briefing_provenance": true

  [bold]loopholes[/bold] (object): Host-side services the jail can reach.
    ("host_services" is what this block is called in prose and in the code that
    validates it; the KEY is "loopholes" — config.go's known-key list has no
    "host_services", so writing that spelling is an unknown-key error.)
    Each key is a service name (must match ^[a-zA-Z][a-zA-Z0-9_-]{0,63}$).
    NO NAME IS RESERVED any more.  "cgroup-delegate" and "journal" stopped being
    reserved on 2026-08-18 and "claude-oauth-broker" on 2026-08-19, when the last
    of yolo's own loopholes became a pack's manifest — writing
    "loopholes": {"cgroup-delegate": {"enabled": true}} is how you switch the
    cgroup delegate on, and it is OFF until you do.  What refuses a duplicate now
    is exclusivity ACROSS PACKS (two packs claiming one loophole name refuses the
    launch), not a list of names yolo holds back.

    "claude-oauth-broker" is still the one name yolo reaches by literal — "yolo
    broker status", "yolo check"'s broker section, the host-singleton spawn and
    the in-jail terminator's endpoint variable all name it — so declaring an
    INLINE service under that name is accepted and is almost certainly not what
    you want: yolo will ensure its own broker singleton alongside your daemon.
    Select "packs": ["claude"] to get the real one, and use "enabled" below to
    switch it off.

    A key here does one of two things, and which one depends on whether a loophole
    of that name already EXISTS on this machine (shipped by a selected pack).  A
    new name DECLARES an inline host service; an existing name OVERRIDES that
    loophole.  The two accept different keys, because you cannot replace a
    manifest's daemon from config.

    "enabled" (boolean, optional) is accepted by BOTH, and it is THE SWITCH:

      "loopholes": { "audio": { "enabled": true } }

      It is the USER's answer, and it outranks whatever the loophole's manifest
      declared, in both directions.  DO NOT CONFUSE IT WITH "default_enabled",
      which is a key on a loophole's manifest.jsonc and is not valid here: that
      one is the PACK AUTHOR's default — what happens when nobody has spoken —
      and an ABSENT "default_enabled" means the loophole is OFF (presence never
      activates; docs/reference/loophole-system.md R1/R2).  So a loophole whose
      author shipped it off, "audio" among them, runs only because this key says
      so.  Honored from the user config and from a workspace yolo-jail.jsonc
      alike; the workspace is the agent-editable scope, so a switch written there
      is disclosed by name at every launch and by "yolo check".
      On an inline service the default is ON — writing the argv out by hand is
      already the deliberate act — so there the key is only ever used to switch
      one off without deleting it.

      FOR ONE PROJECT ONLY, run [cyan]yolo loopholes enable <name>[/cyan] (or
      [cyan]disable[/cyan]) on the host, in the project or with --workspace <path>.
      It writes the switch into that project's PER-WORKSPACE FILE,
      ~/.config/yolo-jail/workspaces/<folder>-<hash>.jsonc, never into this
      config, and prints which file.  That file merges LAST, over this config and
      the project's own yolo-jail.jsonc and yolo-jail.local.jsonc, from the
      project's next fresh launch; no jail can read it.  It holds
      "workspace" (the project's path, which must match) and
      "loopholes": {"<name>": {"enabled": true|false}} and nothing else.
      [cyan]yolo loopholes enable <name> --global[/cyan] prints the block to
      paste into this config (config.jsonc) instead, and writes nothing: yolo
      does not edit your config.

      A loophole whose manifest declares "brokered" (the github pack's
      github-broker) is switched ONLY that way, one project at a time: its
      "enabled" here, or under "loopholes" in a project's yolo-jail.jsonc or
      yolo-jail.local.jsonc (or their .json spellings), is an error naming the
      command, and its manifest may not set "default_enabled": true.

    DECLARING an inline service also takes:
      "command" (array of strings, required): the command to launch on the host
        when the jail starts.  "{endpoint}" in any arg is substituted with the
        actual host-side path the service should publish at.  "{socket}" is
        accepted as an alias for it.
      "env" (object, optional): extra env vars for the host daemon (NOT the jail).
      "description" (string, optional), "doctor_cmd" (array of strings, optional),
      "preamble" (boolean, optional, default false — an inline daemon is a
        third-party program that never asked for a framing preamble).
      "jail_endpoint" (string, optional): override the jail-side path.
        Must start with /run/yolo-services/.
        Default: /run/yolo-services/<name>.endpoint
        ("jail_socket" is accepted as an alias.)

    OVERRIDING an existing loophole takes only "enabled", "env", "jail_env" and
    "settings" ("jail_env" being extra env vars set INSIDE the jail, merged over
    whatever the manifest declared).  "command" and "doctor_cmd" are REFUSED there
    by name: they are fixed by the loophole's manifest, and a config that appeared
    to change them would change nothing.

    "settings" (object, optional) is THE LOOPHOLE'S OWN CONFIG KEYS.  Unlike every
    other key here, what may go inside it is not fixed by yolo: the loophole's
    [cyan]manifest.jsonc[/cyan] DECLARES its settable keys, each with a type, an
    optional default and a scope, and yolo validates what you write against that
    declaration.

      "loopholes": {
        "host-processes": {
          "settings": { "visible": ["sway", "waykeeper"] }
        }
      }

      An undeclared key is an ERROR naming the keys that do exist, and a value of
      the wrong type is an error too — the block is typed, never opaque.  Declared
      types are "string", "bool", "int" and "string_list".  See what a loophole
      declares with [cyan]yolo loopholes list[/cyan].

      SCOPE IS PER KEY, and it is the manifest that decides.  A key declared
      "workspace" may be set from a workspace yolo-jail.jsonc as well as the user
      config; a key declared "user" — the DEFAULT when the manifest says nothing —
      may only be set from ~/.config/yolo-jail/config.jsonc, and writing it in a
      workspace file is refused naming both files.  The default is the strict one
      because a setting can reach a host daemon, and silence must not grant.

      RESOLVED ONCE, AT LAUNCH.  yolo merges your values over the declared
      defaults, writes the result to a file it owns in the loophole's state dir,
      and hands the daemon that PATH.  So editing a setting takes effect on the
      next jail START, not on the next request — which is deliberate: a restart is
      where the config-change approval prompt lives, and a value that could change
      under a running daemon could be changed by the agent inside it.

    Each service gets:
      • Its published path bind-mounted into the jail under /run/yolo-services/
      • An env var so agents can locate the service without hard-coding paths:
        YOLO_SERVICE_<NAME>_ENDPOINT for a manifest loophole, or
        YOLO_SERVICE_<NAME>_SOCKET for a service declared here.  The names differ
        because the VALUES differ, and a client that dials a regular file as if it
        were a socket reports something obscure.  An _ENDPOINT value is always a
        PATH, never an address: the address lives inside the file, so a restarted
        daemon needs no jail relaunch.
      • A managed lifecycle: started before container start, SIGTERM + 5s grace +
        SIGKILL after the container exits.
      • stdout/stderr captured to ~/.local/share/yolo-jail/logs/host-service-<name>.log

    A loophole with a [cyan]manifest.jsonc[/cyan] publishes an ENDPOINT FILE — one
    line naming a 127.0.0.1 listener, the exact certificate a client must pin, and
    a per-jail bearer token.  That file IS A CREDENTIAL: it is written 0600 into
    this jail's own directory and is never shared between jails.  There is
    deliberately no token env var.  [cyan]loopback-tls[/cyan] is the only manifest
    transport and the default; [cyan]unix-socket[/cyan] and
    [cyan]tls-intercept[/cyan] were REMOVED from the manifest vocabulary, not
    deprecated.

    A service declared HERE, in yolo-jail.jsonc, still gets a plain Unix socket and
    a YOLO_SERVICE_<NAME>_SOCKET variable, because its daemon is a program yolo did
    not write: nothing yolo ships lets an external daemon publish an endpoint file,
    so flipping this path would kill those daemons rather than migrate them.

    Use this to split the jail boundary cleanly: a host-side process can hold
    secrets, credentials, and access-control logic that the agent inside the
    jail can call but never sees.

    Example:
      "loopholes": {
        "auth-broker": {
          "command": ["~/code/auth-broker/serve.py", "--socket", "{socket}"],
          "env": {"KEYS_FILE": "~/secrets/keys.json"}
        }
      }

    Apple Container is unsupported.  The reason USED to be the transport (no
    Unix-socket bind-mount through virtiofs); loopback-tls removes that obstacle,
    but how the endpoint file crosses into an AC guest is an unmade decision, so
    host services stay explicitly DEFERRED there rather than quietly enabled.

  [bold]brokered[/bold] (object, [bold]WORKSPACE SCOPE[/bold]): More repositories for this
    workspace's brokered loophole, such as the github pack's github-broker.
    A brokered loophole runs your host login's commands for the jail, but only
    against the workspace's repositories: its git remotes, and any it lists
    here, which every fresh launch reads and asks you to approve.  It runs only
    in a workspace you turned it on for with [cyan]yolo loopholes enable <name>[/cyan]
    (see "loopholes" above); answering N at that approval names
    [cyan]yolo loopholes disable <name>[/cyan].  List a repository the project has no
    remote for in yolo-jail.jsonc, or in yolo-jail.local.jsonc for what the
    project should not commit (yolo does not git-ignore that file):
      "brokered": {
        "github": { "repos": ["org/lib", "org/docs"] }
      }
    • The source key is the one the loophole's manifest declares as
      `brokered.source`; the github pack's is "github".  A source no selected
      pack brokers is a host `yolo check` warning; a launch says nothing.
    • Each repos entry is OWNER/REPO, with no host.  A listed repository is in
      scope exactly as a remote is: its reads run, and its writes need the same
      approval.  No entry admits a command across your whole account, such as a
      search with no repository.
    • Lists merge across the workspace's files, compared without case, and
      "repos": null in the local file clears the list.  A `brokered` key from a
      file outside the workspace, reached through an include or a link, is
      refused, and so is one written twice in one file.
    It takes effect at the next fresh launch: the config-change prompt shows each
    repository as a row of the repository-scope block, naming the file it came
    from, and asks you to approve it; then the launch names the scope, as in
    "github-broker: scope for this workspace: you/app (remote "origin"), org/lib (yolo-jail.jsonc)".
    An agent may add an entry: a jail refuses a repository outside its scope with
    a message telling it how, and to ask you to restart and approve.
    NOT IN THE USER CONFIG.  A `repos` list there, with no workspace to key it,
    would widen every workspace, so it is a `yolo check` error.  The old form,
    "workspaces" keyed by a workspace's path, is retired: move each entry into
    its project's yolo-jail.local.jsonc; host `yolo check` prints each edit.

  [bold]host_processes[/bold] (object): REMOVED — a config carrying it is REFUSED.
    Its keys moved to the host-processes loophole's own "settings" block, where they
    are declared by that loophole's manifest rather than by yolo's config schema:

      "packs": ["host-processes"],
      "loopholes": { "host-processes": {
        "enabled": true,
        "settings": {
          "visible": ["sway"],          // process comm names yolo-ps may show
          "fields":  ["pid", "comm"]    // ps -o columns
        }
      }}

    NOTE THE SPELLING: the loophole is "host-processes" (hyphen); the removed
    top-level key is "host_processes" (underscore).  All three lines are needed —
    the loophole ships in a PACK now, so migrating the keys alone leaves yolo-ps
    just as broken.  Two behaviours changed with the move: the allowlist is
    resolved once at launch (so an edit needs a jail restart), and a workspace file
    supplying it is disclosed and gated by the config-change approval flow.

  [bold]journal[/bold] (string): REMOVED — a config carrying it is REFUSED.
    The journal bridge is an ordinary pack-shipped loophole now, so it is selected
    and switched on like anything else, and its mode is its own declared setting.
    yolo's config schema no longer names a loophole at all.

      "packs": ["journal"],
      "loopholes": { "journal": {
        "enabled": true,                // was "journal": "user" (or the bare true)
        "settings": { "full": true }    // was "journal": "full" — USER CONFIG ONLY
      }}

    What it does is unchanged: [bold]yolo-journalctl[/bold] inside the jail forwards
    its args to [cyan]journalctl[/cyan] running on the host and streams
    stdout/stderr back, so an agent can inspect systemd logs without the host
    journal being mounted rw into the jail.
      • off      — don't select the pack, or "enabled": false
      • narrow   — enabled; the daemon forces [cyan]--user[/cyan] on every
                   invocation (this is the default, and what "user" meant)
      • full     — enabled + "settings": {"full": true}; args pass through
                   unchanged, which needs host journal read access
    THE "full" SETTING IS USER-SCOPE.  A workspace yolo-jail.jsonc may switch the
    bridge on ("enabled" is honored from either scope) but may NOT widen what it
    reads: reading the whole host journal used to be settable from a file the agent
    inside the jail can rewrite, and the declared scope is what ended that.
    Endpoint file: /run/yolo-services/journal.endpoint
    Env var: YOLO_SERVICE_JOURNAL_ENDPOINT
    The value is a PATH to the endpoint file, not an address: the bridge is on
    the loopback-TLS transport, so the address lives inside the file and a
    restarted daemon is picked up without relaunching the jail.  The file also
    carries this jail's bearer token, which is why it is 0600.

  [bold]env_sources[/bold] (array): Environment variables set inside the jail.
    Ordered list; each entry is either:
      • a string — path to a KEY=VALUE dotenv file (# comments allowed,
        quoted values OK, `export` prefix tolerated)
      • an object — inline {"KEY": "VALUE"} map; a null value
        ("KEY": null) UNSETS the variable — the spelling
        `yolo host -- <cmd>` uses to drop e.g. AWS_PROFILE from the
        invoking shell (a later entry assigning the key cancels it)
    Later entries override earlier ones.  User-config list loads first,
    then workspace-config list.  File paths support ~ expansion and
    absolute paths.  A RELATIVE path resolves beside the file that
    declared it — for the user config that is
    ~/.config/yolo-jail/, for each include the include's own directory,
    and for the workspace config the workspace root (so
    workspace-relative spelling behaves exactly as it reads).  `yolo
    host` additionally refuses any relative entry that reaches it
    unanchored, which in practice never happens for configs yolo loaded.
    Missing files warn
    and skip rather than failing the run — keep secrets in an unsynced
    file outside your dotfiles tree.
    A value no provider claims is written to ~/.config/yolo-user-env.sh
    (sourced by .bashrc and the entrypoint), so every process sees it; it
    can be overridden by mise .env or by editing that file inside the jail.
    A value a provider CLAIMS (names in its api_key_env_name) is written
    only to ~/.config/yolo-agent-env/<agent>.sh for each agent whose
    profile selects that provider, which that agent's launcher sources:
    no other process, a bare shell included, sees it.  With no agent
    selecting the provider it reaches nothing, and the launch says so.
    At the host, `yolo host --with-credentials <provider[,…]|all> -- <cmd>`
    hands one command the named providers' claimed values, keys only, for
    that run (`all`: every provider claiming a value here); no config key
    can grant it, and a jail launch refuses the flag as host-only.
    Dropping a key (or the whole list) REVOKES it: the next launch rewrites
    that file, truncating it to empty when nothing resolves, so a removed
    credential stops being exported.  Values already live in a RUNNING jail
    persist until it restarts.
    The same file carries the per-entry provider channel (see `profile`):
    the three tables and the ungated pack env land in a marked section as
    unconditional exports, rewritten by every ENTRY — a fresh launch and an
    attach alike — so `-p` reaches a running jail.  Those lines are not
    overridable defaults; the whole section is recomposed each time.  What a
    profile composes for ONE agent (its provider's settings and token, and
    the pack env its selection gates) goes to that agent's own file instead,
    rewritten by every entry the same way, and beats a value you export.
    Example: [
      "~/.config/yolo-jail/defaults.env",
      {"DEBUG": "1"},
      ".secrets/claude.env"
    ]

  [bold]mounts[/bold] (array of strings and objects): Extra host paths, read-only unless you ask.
    [bold]For paths OUTSIDE the workspace only.[/bold]  The workspace itself is
    already /workspace, read-write and live (see the top of this reference) —
    listing it here gets you a second view of a tree you can already write,
    under a name nobody expects.
    Every entry lands under the [bold]context dir[/bold], /ctx on podman and Apple
    Container, which every launch names to the jail as $YOLO_CONTEXT_DIR (it
    exists, possibly empty, whether or not you declared a mount).
    [bold]String entries are READ-ONLY, always[/bold] — every one gets :ro appended:
      Simple path → mounted at /ctx/<basename>
      "host:container" → custom container path
      Example: ["/path/to/repo", "~/lib:/ctx/lib"]
    [bold]Object entries[/bold] carry a mode, and are the only way to write a
    read-write mount:
      {"host": "~/scratch/datasets", "at": "/ctx/data", "mode": "rw"}
      {"host": "~/notes", "mode": "ro"}
    `mode` is REQUIRED ("ro" or "rw") — there is no default, so a writable
    mount is never one you did not write.  `at` is optional (default
    /ctx/<basename>); a read-write mount must land UNDER /ctx/, where it can
    shadow nothing of the home or a composed surface.
    [bold yellow]Do NOT write a docker-style ":ro" or ":rw" suffix.[/bold yellow]  ":rw" is a
    `yolo check` error naming the object form.  ":ro" is worse: the split
    takes the last colon followed by "/", so "~/x:/ctx/x:ro" parses as ONE
    host path literally named "~/x:/ctx/x:ro".  It does not exist, so the
    mount is SKIPPED with a warning — and `yolo check` only warns too, so a
    config that mounts nothing looks accepted.
    [bold yellow]A read-write mount is user-scope only[/bold yellow] — write it in
    ~/.config/yolo-jail/config.jsonc (or a --user-layer).  In yolo-jail.jsonc,
    yolo-jail.local.jsonc or anything they include it is a `yolo check` error
    and the launch refuses: a workspace config is agent-editable, so it cannot
    grant a read-write host mount.  Read-only entries may sit at either scope.
    A read-write source is also REFUSED when it is, or contains, your home,
    ~/.config/yolo-jail or ~/.local/share/yolo-jail, sits inside either yolo
    directory, or overlaps the workspace in either direction (a second
    writable path to it would bypass `workspace_readonly`).  Directories like
    ~/.ssh are not on any list: a mount you wrote in your own config is your
    own authority, and the launch names it every time.
    [bold]Every launch prints one line per read-write mount[/bold] — the host path, the
    jail path, and that anything on this machine which later reads that
    directory reads what the jail wrote there, a planted symlink included.
    YOLO_NO_BANNER does not hide it.  On a ROOTFUL podman the line adds that
    files the jail's root creates there are owned by root on the host (on a
    rootless one they are yours; a file written by a non-root user inside the
    jail lands as a subuid you remove with `podman unshare`).  yolo never
    creates, chowns or relabels a mount source, and there is no locking: two
    jails, or a jail and you, writing one directory get last-writer-wins,
    like two programs on the host.
    Two mounts at one jail path — a pack `mount` at /ctx/<into> included —
    are a `yolo check` error.  An entry whose source does not exist is
    skipped, so it collides with nothing: one entry per machine at the same
    path is fine.  /ctx/packs, /ctx/captures, /ctx/host-user and
    /ctx/host-nvim-config are yolo's own: an entry at, inside or containing
    one (an `at` of /ctx itself) is a `yolo check` error too — including a
    bare path whose basename is one of those names, so pin it with `at`.
    <basename> is the basename AFTER symlink resolution.  A link whose name
    differs from its target's mounts under the TARGET's name: "~/code/sysadmin"
    lands at /ctx/sysadmin-config if that is where the link points.  Use the
    explicit "host:/ctx/name" form (or `at`) when you want to pin the name.
    [bold]Host paths are resolved on the HOST, at launch.[/bold]  An IN-JAIL
    `yolo check` resolves "~" against the JAIL's home, so it warns "host path
    does not exist and will be skipped" for every entry an agent adds from
    inside a jail.  [bold]That warning is expected in there and is not a
    failure[/bold] — only a host `yolo check` can judge these paths.  For the
    same reason `mounts` is dropped from the in-jail user-config snapshot and
    is not inherited by a nested jail.
    Runtime support: podman, and Apple Container ("container").  A read-only
    entry needs Apple Container 1.1.0 or later: below that it accepted :ro
    and ignored it, so rather than hand out a writable context mount yolo
    SKIPS every read-only entry and says so — and it skips for the same
    reason when it cannot read `container --version` at all, because the
    safe error is the one that costs a mount rather than the one that costs
    the guarantee.  A read-write entry is bound on every Apple Container
    version: it needs nothing :ro provides.
    "macos-user" has no container, so each entry is a root-owned LINK in
    $YOLO_CONTEXT_DIR (not /ctx) to the host folder itself, and the sandbox
    profile decides what the agent may do there.  The folder must be one
    the sandbox account can reach, outside every user's home: a read-only
    one under /Users/Shared or outside /Users (/opt, /usr/local, …), a
    read-write one under /Users/Shared/yolo.  Before the sandbox starts the
    launch asks, as that account, whether it can read (and for read-write,
    write) each folder.  Anything else — a folder in a home, on another
    volume, overlapping the workspace or a place the sandbox writes (/tmp),
    or an `at` outside /ctx — REFUSES the launch, naming each entry and why.
    Tools that resolve paths print the host path there, and a subfolder the
    sandbox account may not read stays unreadable.  An entry whose source
    does not exist is skipped with a warning, as on every backend.

  [bold]cache_relocations[/bold] (object): Put a jail cache subdir on other storage.
    Keys are cache SUBDIR NAMES, not paths — a single path segment, no "/",
    not "." or "..".  Values are absolute host directories ("~" expanded).
    Each entry is bind-mounted [bold]read-write[/bold] at /home/agent/.cache/<subdir>,
    nested inside the usual cache mount, so nothing downstream has to know:
    HF_HOME and every other tool's cache path stay exactly as they are.
    Worth it for large, cold, write-once/read-sequential caches — huggingface
    (model repos), ms-playwright (browser bundles) — that you want on a big
    slow disk.  NOT worth it for uv, go-build or pip: those are hit on every
    build and are latency-sensitive, so a slow disk makes every build worse.
    [bold yellow]Scope: this key is read from ~/.config/yolo-jail/config.jsonc ONLY[/bold yellow]
    (plus that file's include_if_found files, which are host-side too).  In
    yolo-jail.jsonc it is a `yolo check` error, not an override — the
    workspace is bind-mounted read-write into the jail, so a workspace config
    is agent-editable and must never be able to hand out read-write host
    mounts.  The mount is built from the user config alone; the merged config
    is read only to VALIDATE the key (which is how a workspace-scoped one gets
    reported), never to decide what gets mounted.
    The target's [bold]parent must already exist[/bold]; only the last path component is
    created for you.  A missing parent means a typo (/data/relcoated/...), and
    creating it silently would leave the bytes on the very disk you were
    trying to get off.
    Runtime support: podman only.  "container" (Apple Container) warns and
    skips it.  "macos-user" has no container and no bind mounts either, and
    warns too.  [bold yellow]A plain host symlink is NOT a workaround there[/bold yellow] —
    Seatbelt evaluates the symlink's TARGET rather than the link (measured
    2026-09-13 on macOS 26.5, absolute and relative links alike: both came
    back "Operation not permitted"), and that backend's profile denies writes
    outside the workspace, the sandbox home, /tmp and /var/folders, and
    denies reads under /Volumes.  A link onto other storage therefore
    resolves to a path the sandbox cannot use, and the cache stays on the
    boot volume — the one outcome this key exists to prevent.
    Moving an EXISTING cache: stop all jails first, copy the bytes, then set
    the key — a running jail keeps its old, now-empty mount until restart.
    Full procedure: userguide/guides/storage.md, "Storage & Persistence".
    Example (~/.config/yolo-jail/config.jsonc):
      "cache_relocations": {
        "huggingface": "/data/relocated/yolo-jail/cache/huggingface"
      }

  [bold]writable_home_dirs[/bold] (array of strings): Extra $HOME paths made writable.
    Each entry is a path relative to /home/agent (no leading /, no "..").  The
    jail's home is mounted read-only except for the dirs yolo manages; an agent
    extension that hardcodes a home path yolo doesn't know about (e.g. pi-lens
    writing ~/.pi-lens) hits that read-only base and its mkdir fails.  List the
    path here and it becomes an ordinary writable dir, backed by
    <workspace>/.yolo/home/writable-home/<path> — so it persists per workspace
    and survives restarts, exactly like the built-in overlays.
    You do NOT need this for anything already writable: ~/.config, ~/.local,
    ~/.cache, ~/go, ~/.ssh and every selected agent's own dir (~/.claude, …)
    are read-write already — listing one is a `yolo check` error, since the key
    would only shadow yolo's own mount.
    Unlike cache_relocations this is safe at ANY scope (workspace or user): the
    destination is always under /home/agent and the backing dir is inside the
    workspace, so it hands out no host access a jail didn't already have.
    Runtime support: podman needs (and does) this — its home base is the only
    one mounted read-only.  Apple Container ("container") mounts all of
    /home/agent writable in one bind, and macos-user's Seatbelt profile allows
    writes to the whole sandbox home, so on both of those every home path is
    already writable and the key is a harmless no-op.
    Example: [".pi-lens", ".config-that-isnt-mine/state"]

  [bold]host_files[/bold] (array): Bring any file into the jail, composed not copied.
    Each entry is either a [bold]string[/bold] (sugar) or an [bold]object[/bold] (rich).  Every entry
    becomes a composed "surface" rendered by the same engine that generates the
    agent settings files, so a plain copy is just codec "raw" — one engine, not
    two.  Use this for a dotfile yolo doesn't know about (~/.npmrc, pi's
    models.json), or to bring a brand-new managed file into being.

    [bold]String form[/bold] — "~/.npmrc" means: copy that host file to the same path in
    the jail, codec auto-detected, mode readonly.  A trailing "/" makes it a
    recursive directory copy.  Always source-bearing, hence user scope only.

    [bold]Object form[/bold] keys:
      path       ~-relative jail DESTINATION.  OPTIONAL when `source` is a "~/…"
                 path — it then defaults to the same home-relative place, so a
                 mirrored file names its path once.  Required for a source-less
                 entry, and for a source outside $HOME (/etc/foo.conf has no
                 unambiguous home-relative counterpart to guess).
      source     host path to seed from.  Its presence is what makes an entry
                 user-scope only.  Mutually exclusive with content.
      content    inline literal seed (a string).  Crosses nothing, so it is
                 legal at any scope.  Use "" to declare a deliberately empty file.
      codec      json | toml | lines | raw.  Overrides auto-detect.  There is no
                 yaml codec — a .yaml file is handled as raw bytes.
                 [bold yellow]Comments:[/bold yellow] a STRUCTURED codec (json/toml) parses the file
                 into keys and re-emits it, which DISCARDS every comment — so
                 naming "codec": "json" on a commented .jsonc file silently
                 drops the comments.  "raw" keeps the bytes exactly as they
                 are, comments included, at the cost of key-level merging and
                 the defaults/managed layers.  Pick per file: raw to preserve a
                 hand-written config, json/toml to compose one.
      defaults   user-overridable base layer (structured codecs).
      managed    keys yolo re-asserts every render, so they revert on edit.
      mode       see below.

    [bold]Codec auto-detect[/bold]: .json -> json, .toml -> toml, everything else -> raw
    (including no extension, .sh, .yaml, .yml, and .jsonc — routing .jsonc
    through the json codec would sort keys and DROP COMMENTS).

    [bold]Modes[/bold] — what happens across boots, and to an in-jail edit:
      readonly  re-rendered every boot at 0444; a host-side edit propagates on
                the next launch.  [bold]Default for a source-bearing entry.[/bold]
      once      seeded when absent, then never touched.  In-jail edits simply
                persist (no sidecar); later host edits do NOT propagate.
                [bold]Default for a source-less entry.[/bold]  To re-seed, DELETE
                the file — the next boot recreates it, because `once` keys off the
                destination's absence.  (`yolo config reset` does NOT re-seed it:
                reset discards CAPTURED edits by deleting the §5 sidecars, and a
                `once` surface has none.)
      copy      overwritten every boot; in-jail edits are discarded.  Implied
                for a directory entry.
      capture   re-rendered every boot AND in-jail edits captured into a sidecar
                that outranks the host layer — and every layer below it, but NOT
                a `computed` or `managed` key, which are re-asserted above the
                capture on every render.  [bold yellow]Never a default — always
                explicit[/bold yellow], because a captured edit wins over the host file
                FOREVER (the sidecar never ages out), so implicit capture would
                silently fork a host-mirrored file the first time a tool
                rewrote its own config (`npm config set`, any CLI's first run).
                Captured at jail TERMINATE as well as at boot, so `yolo config
                diff` describes the session that just ended, not the one before
                it.  The two folds are the same operation over the same baseline,
                so the earlier one cannot record a key the boot render would not.
    Note 0444 is DAC, not kernel enforcement: an agent running as root (Claude
    YOLO does) bypasses the mode bits.  It is a strong signal and a speed bump,
    not a sandbox — use `mounts` for a kernel-enforced read-only file.
    Inspect what any of this produced with [bold]yolo config ls[/bold]. Its first column is
    the canonical surface identity (`agent/surface`): pass that identity to
    [bold]yolo config render[/bold], [bold]diff[/bold], [bold]reset[/bold], [bold]capture[/bold], or [bold]promote[/bold] to select one
    surface; pass a bare agent to select all its surfaces. `diff` and `reset`
    apply to CAPTURE surfaces only — they are defined over the sidecars, which
    no other mode writes.

    [bold yellow]Scope: an entry that names a `source` is read from
    ~/.config/yolo-jail/config.jsonc ONLY[/bold yellow] (plus that file's include_if_found
    files).  In yolo-jail.jsonc such an entry is a `yolo check` error: a
    workspace config travels with the repo and is agent-editable, so it must
    never decide which host files cross into the jail.  A SOURCE-LESS entry
    (inline content, or only defaults/managed) copies nothing from the host, so
    it is allowed at any scope — a repo may legitimately ship one.
    Within your own user config nothing is blocked: listing ~/.ssh/… there is
    your call.  The boundary is that the REPO cannot make it for you.

    A destination may not clobber a file yolo owns (~/.claude.json, ~/.bashrc,
    ~/.gitconfig, the yolo-* single-file mounts) or any yolo-composed agent
    surface (~/.claude/settings.json, ~/.config/mise/config.toml, …).
    Runtime support: podman gets everything.  "macos-user" has no bind mounts,
    so host bytes arrive by COPY into a root-owned tree the sandbox reads
    instead (since 2026-09-13).  A `source` naming a single FILE is delivered
    there normally.  A `source` naming a DIRECTORY is not — a copy does not
    scale to an arbitrary tree — so it is skipped and NAMED in a warning; split
    it into the files you need, or use the Apple Container runtime
    (runtime: "container"), which binds it read-only from version 1.1.0 (older
    versions, or one yolo cannot read, skip it with a warning naming the
    reason).  Source-LESS entries are unaffected
    on every backend: they copy nothing from the host to begin with.
    Example (~/.config/yolo-jail/config.jsonc):
      "host_files": [
        "~/.npmrc",                    // raw, readonly
        "~/.pi/agent/models.json",     // json, readonly
        "~/.pi/agent/themes/",         // directory -> recursive copy
        { "source": "~/.config/starship.toml",  // path + codec both inferred
          "managed": { "add_newline": true } },
        { "path": "~/.config/ripgrep/config",
          "content": "--max-columns=200\n--smart-case\n" },
        { "path": "~/.config/mytool/settings.json",
          "mode": "capture",
          "defaults": { "telemetry": false, "theme": "dark" },
          "managed":  { "telemetry": false } }
      ]

  [bold]host_wrappers[/bold] (boolean): Generate launch wrappers for host agents.
    [bold]Default: ON when host_management is "own", otherwise off.[/bold]  You usually
    do not write this key at all — `own` means yolo composes an agent's config file
    whole, and a config file cannot carry a credential (api_key_env_name holds a
    variable's NAME), so without a wrapper on your PATH a bare `claude` would get the
    config and none of the environment it assumes.  Declaring `own` and nothing else
    used to leave exactly that half-configured host, and `yolo doctor` said nothing.
    An explicit [bold]false[/bold] still wins: if you want yolo to own your config files
    and refuse to have anything put on your PATH, say so and it is honored.
    [bold]"assert" does NOT enable them[/bold] — it is host_management's own unset default,
    so deriving from it would put a PATH claim on every machine that declared nothing.
    When on, `yolo host apply` writes one small wrapper per
    program your selected packs install into
    [bold]~/.local/share/yolo-jail/bin/wrap[/bold], each a three-line `exec` into
    `yolo host -- <program>`.  Put that directory FIRST on your PATH and a bare
    `claude` (or `pi`, `codex`, …) composes its environment — Bedrock flags, the
    credentials from `env_sources`, any unsets — the same way `yolo -- claude`
    does inside a jail.

    [bold]It must be PREPENDED[/bold], ahead of ~/.local/bin: a wrapper only works if
    it is found before the real binary, and claude's own installer writes
    ~/.local/bin/claude.  yolo PRINTS the line and never writes it: your shell rc is
    yours, so add it there yourself, below any line that puts ~/.local/bin on PATH.
      export PATH="$HOME/.local/share/yolo-jail/bin/wrap:$PATH"
    `yolo check` says whether it took effect.

    Wrappers are generated for [bold]every[/bold] program a selected pack installs, whether
    or not that program needs any environment today.  That is deliberate: the
    directory is an addressable launch surface, so `<wrap dir>/claude` is a path
    a script or an IDE's "agent binary" setting can point at and rely on
    existing — which is also the answer whenever PATH is not consulted at all.
    A pack that installs no program (a loophole-only pack) gets no wrapper.

    Enabling this makes yolo a runtime dependency of every wrapped launch: a
    broken yolo or an unparseable config takes the wrapped program down with it.
    The real binary is still behind the wrap dir on PATH, and invoking it by
    absolute path still works.

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.jsonc).  The key
    puts generated executables at the FRONT of your PATH, and a workspace config
    travels with the repo and is agent-editable, so it must never make that
    claim for you.  A workspace value is a `yolo check` error, and is never read.
    `yolo check` also tells you, every run, when the wrap dir exists but is not
    actually on your PATH.
    Example (~/.config/yolo-jail/config.jsonc):
      "host_wrappers": true

  [bold]host_apply_on_launch[/bold] (boolean): Re-check and synchronize the host render at a wrapped launch.
    Default true when [bold]host_wrappers[/bold] is true; otherwise false.  `yolo host apply`
    writes into your real home once, so without re-checking, what is in your agents'
    config files and what your packs NOW say drift apart in silence.  With this enabled,
    a launch through a generated wrapper (see [bold]host_wrappers[/bold] above) checks first:
    if a re-apply would change nothing it execs straight through; if drift is detected
    under active host management (`assert` or `own`), it automatically synchronizes
    host configuration before launch (printing `yolo host: synchronized host configuration (<targets>)`
    to stderr) and execs without pausing for confirmation.

    Interactive confirmation is reserved for first-time adoption that would overwrite
    unmanaged host keys:

      nothing would change      silent; the agent starts as usual.
      a configured pack cannot  renders NOTHING, names each pack with why and the
      be resolved, or its       remedy (for a git pack, the fetch this launch already
      manifest has problems     tried; `yolo pack install` retries it; for a manifest,
                                the problems, which `yolo pack lint` re-checks), and
                                REFUSES the launch: an incomplete pack set is never
                                applied, and no launch runs on one, at any notch.
      an apply would ask        renders NOTHING, prints each question (a skills or
      something                 briefing adoption, a dropped pack's retire, a missing
                                declared dependency) and `yolo host apply --assert`
                                to answer them, and the agent launches.  The launch
                                never asks through a hidden prompt, and another
                                pack's missing tool never stops this agent.
      safe managed changes      auto-applied silently; notice printed, agent launches.
      first apply overwriting
      unmanaged keys, terminal  shows what would change and prompts for confirmation.
      first apply overwriting
      unmanaged keys, off-TTY   REFUSED, naming the commands that fix it.  No flag or
                                variable approves it (below).
      something cannot be       in the launched program's own configuration: REFUSED,
      written (a pack failed    naming it and the fix.  Anywhere else: the rest is
      to render, or a file is   applied, the failure is named with its fix, and the
      a link into a missing     program launches — pi's broken settings.json never
      directory)                stops claude.
      cannot tell               execs.  A malformed pack, an unreadable home or a
                                concurrent apply is not something a launch may
                                stop over.

    A host launch takes no approval: `yolo host` refuses --accept-config-changes,
    and no environment variable grants one.  Dropping MCP servers yolo does not
    declare, on a first apply, is a one-way door kept behind a terminal, so a
    scripted launch that meets it answers it once, where a terminal can:
      yolo host apply --assert
      claude --print ...

    What it compares is the RENDER, not your config — so a file you hand-edited is
    caught even though nothing in `packs` moved.  Concurrent launches serialize on
    a per-home lock, and one that cannot take the lock execs rather than waiting.

    [bold]Coverage:[/bold] only launches that go through a generated wrapper.  An agent
    started by its real binary, by an IDE extension or by a desktop app is not
    observed and runs against whatever the last explicit apply left.  That is the
    same boundary [bold]host_wrappers[/bold] has, and `yolo check` reports both.

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.jsonc).  The key lets a
    launch WRITE INTO YOUR REAL HOME, and a workspace config travels with the repo
    and is agent-editable, so it must never make that claim for you.  A workspace
    value is a `yolo check` error, and is never read.
    Example (~/.config/yolo-jail/config.jsonc):
      "host_apply_on_launch": true

  [bold]host_management[/bold] ("none" | "assert" | "own"): Who owns the config files
    yolo renders into your REAL home.  Default [bold]"assert"[/bold] -- today's behavior, so an
    upgrade changes nothing until you write the key.

    Ownership is DECLARED here, never inferred from where a file happens to live.
    The value selects the surface mode the host notch renders in:

      "none"    yolo writes nothing.  `yolo host apply` REFUSES, naming this key,
                and a wrapped launch has no render to re-check, so
                [bold]host_apply_on_launch[/bold] becomes a no-op rather than a nag.
      "assert"  shared: yolo owns the keys your packs declare and rewrites only
                those; every other key in the file is yours and is left byte for
                byte.  This is what `yolo host apply` has always done, and writing
                the value changes nothing about what it writes.
      "own"     yolo owns the file -- it is derived output, composed whole from
                your packs and reproducible by deleting it and applying again.
                Your edits are CAPTURED, into a store beside the provenance record
                at ~/.local/share/yolo-jail/host-capture/, and re-applied on top of
                every later render -- so the file stays yours to edit even though
                yolo composes it.  Switching a home you have been asserting into
                over to "own" changes ZERO bytes: the first owned render adopts
                what the file already holds.  `yolo config reset <agent>` is the
                way to discard those captured edits, and it works host-side under
                this value alone.

    [bold yellow]The key enables the mechanism.  It does not grant the approval.[/bold yellow]  Same ruling
    as [bold]host_apply_on_launch[/bold] above: it selects HOW the host renders, and every
    individual write still goes through the confirmation it always did.

    Under "assert", keeping ~/.claude/settings.json in a dotfiles repo is coherent
    but mixes two authorships; the apply is idempotent, so the diff is stable after
    the first one.  Under "own" the file is derived and belongs in .gitignore --
    what goes in the dotfiles repo is the pack.

    [bold]--revert[/bold] (`yolo host apply --revert`) is the way back out under "assert": it
    removes the keys yolo asserted, on the authority of the provenance record it
    wrote beside them, and deletes that record -- so a later apply is a FIRST apply
    again.  A key you set yourself is never touched.  It is a dry run until
    --assert, and it REMOVES what yolo wrote rather than restoring what was there
    before.  It keeps a default that is an empty object or list, such as pi's
    `"providers": {}`, since that is the shape the agent's file needs, and names
    each one.  Refused under "own" (the file is derived -- `yolo config reset` it,
    or delete it) and under "none" (yolo wrote nothing).

    An UNSET key is the default, not a fourth value, and it bites in exactly one
    place: `yolo apply --sealed` refuses while it is unset, beside the undeclared
    inputs it already refuses for.  An environment whose host-ownership contract is
    unstated is not sealed.

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.jsonc).  The key decides
    whether yolo may write your real home at all, and a workspace config travels
    with the repo and is agent-editable, so it must never make that claim for you.
    A workspace value is a `yolo check` error, and is never read.  A user config
    that cannot be READ yields "none" -- a declaration nobody could read has granted
    nothing -- while an absent key yields "assert".
    Example (~/.config/yolo-jail/config.jsonc):
      "host_management": "assert"

  [bold]promotion_target[/bold] ("local" | "pack:<name>"): Where `yolo config promote`
    writes when you omit `--to`.  Default [bold]"local"[/bold], the conventional personal
    pack at ~/.config/yolo-jail/local/.

    Set this when you maintain a named personal pack instead of the conventional
    local one:
      "promotion_target": "pack:matt"

    The named pack must be configured and writable when you promote; yolo checks
    that at the promotion itself.  [bold]--to[/bold] always overrides this default for one
    command.  `host` cannot be the default: writing real-home settings remains an
    explicit `--to host` decision every time.

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.jsonc). Captured
    settings are personal, and a workspace is writable by the agent running in its
    jail, so a workspace config cannot redirect their destination. A workspace
    value is a `yolo check` error and is never read.

  [bold]agent_updates[/bold] (boolean, "launch", "next-launch", or object of pack name -> one
    of those): Keep agent CLIs current.  Default TRUE -- absent means on.
    An AGENT dependency is a program yolo installs so a coding agent can run: the
    agent CLIs themselves, and the MCP servers they drive.  Nobody's build
    reproduces against one, so a six-week-old copy is a defect rather than a
    guarantee, and yolo keeps them current.  A PROJECT dependency -- `mise_tools`,
    `packages`, anything the work in /workspace builds against -- is the opposite
    and is never touched by this.

    WHEN AN UPDATE HAPPENS: when you type the agent's name.  The generated
    launcher checks at most once an hour per program, updates if it is due, then
    execs the real binary.  A jail that never starts an agent never touches the
    network for one, and a launch on its own updates nothing.  Failure is scoped
    to that one command: offline with the agent installed runs what is there;
    offline with it absent fails, naming the network.  No jail refuses to boot
    over this.

    TURNING IT OFF freezes the agents at whatever is installed.  `yolo pack
    update` still refreshes them on demand -- it is the only thing that ignores
    this key, because it is an act you performed.

    WHEN AN ADD-ON REFRESH RUNS: "launch" or "next-launch".  Some agents keep
    add-ons beside the program, and their pack declares a refresh for them:
    pi's runs `pi update --extensions`.  By default ("launch", the same as true)
    the refresh runs when you type the agent's name, before the agent starts,
    at most once an hour and for at most a minute.  "next-launch" runs it in the
    background instead: the agent starts at once, the refresh runs while you
    work, and the next launch runs what it installed.  The launch says so in one
    line naming the refresh's log, ~/.local/state/yolo/refresh/<agent>.log, and
    a background refresh that fails, or does not finish, is reported once, at
    a later launch.  Only that refresh moves.  The agent's own update, its MCP
    servers, and add-ons your settings name for the first time still finish
    before the agent starts.  While a background refresh runs, pi may show its
    own "updates available" notice; the next launch has them.  A jail that
    exits while the refresh runs stops it and leaves its lock behind: for ten
    minutes every jail sharing those add-ons skips its refresh, and a launch
    whose settings name a new add-on first waits up to a minute for that lock.
    A launch after that runs the refresh again.  `yolo host` runs no add-on
    refresh, so there "next-launch" means the same as true.

    IT GOVERNS YOLO'S UPDATER, NOT THE AGENT'S OWN.  An agent that ships a
    self-updater runs it on its own terms, and yolo does not suppress one.  Claude
    Code, Copilot and agy all do: each comes from its vendor's own installer and
    updates itself on its own schedule, so `agent_updates: false` does not freeze
    them, and yolo cannot say which version of any of them ran -- its install
    record names only what yolo itself installed.  To freeze Copilot too, set
    COPILOT_AUTO_UPDATE=false in the jail (an `env_sources` entry).  Copilot's own
    `autoUpdate: false` setting is not enough: it stops only copilot's downloads,
    and copilot still runs the newest copy in its package caches, one of which,
    in a jail, is under the ~/.cache every jail on the machine shares.  For
    Claude Code, set DISABLE_AUTOUPDATER=1.

    The map's keys are PACK names, not binary names: one pack may install more
    than one program, and the pack is the thing you selected.  A specific key
    beats "*"; "*" beats absence.  A pack cannot opt itself out -- it declares HOW
    to update itself, never whether to.

    USER SCOPE ONLY.  /workspace is writable by whatever runs in the jail, so a
    workspace value would let an agent freeze its own updates.  A workspace value
    is a `yolo check` error, and is never read.
    Example (~/.config/yolo-jail/config.jsonc):
      "agent_updates": false
      "agent_updates": { "*": true, "claude": false }
      "agent_updates": { "pi": "next-launch" }

  [bold]host_floor[/bold] (boolean, or object of pack name -> boolean): Keep your agents
    installed for `yolo host`.  Default TRUE -- absent means on.
    The HOST AGENT FLOOR is yolo's own copy of every agent CLI your selected packs
    install, kept in ~/.local/share/yolo-jail/host-floor.  `yolo host -- <agent>`
    runs that copy by its full path, so the same agent starts whether you typed
    the command in a terminal or a Waybar widget, cron job or IDE started it with
    a PATH of its own.  It is on no PATH of yours: your shell, and any copy you
    installed yourself (~/.local/bin/claude, Homebrew's), are left alone, and
    `yolo check` names such a copy as not run by `yolo host`.
    WHEN IT INSTALLS: the first `yolo host -- <agent>` installs the agent it
    names, and `yolo host apply --assert` installs every one that is missing,
    printing what it does.  Selecting the pack is the consent; nothing asks.  An
    npm agent runs on the floor's own Node, the official release checked against
    its published checksum; an agent with its own installer comes from the
    machine's `yolo capture` of it (Linux).  Where the floor cannot hold an agent
    -- an installer agent on macOS, codex (its installer puts the program where a
    capture cannot record it), no build for this machine, no container runtime to
    capture with -- `yolo host` runs the one on your PATH, saying so.  The floor
    keeps them current the way a jail does, at most once an hour when you start
    one, and `agent_updates` freezes it the same way.
    A pack set to false here has no floor entry: `yolo host` looks for its agent on
    your PATH, saying so, and the next `yolo host apply --assert` removes the
    floor's copy.
    USER SCOPE ONLY.  It decides which programs yolo installs on your machine, so
    a workspace value is a `yolo check` error, and is never read.
    Example (~/.config/yolo-jail/config.jsonc):
      "host_floor": false
      "host_floor": { "*": true, "claude": false }

  [bold]host_path[/bold] (list of folders): Folders `yolo host` searches after the PATH it was
    started with.  Default: none.
    yolo looks for the programs your packs need (`rg` for the guardrails pack, a
    pack's `requires`, an agent yolo keeps no copy of) and for the command you
    name with `yolo host --` on the PATH it was started with -- it cannot know
    where you keep your tools any other way.  A terminal's PATH usually has them;
    a Waybar button, a cron job or a hotkey launcher often hands yolo only
    /usr/bin:/bin.  Each folder listed here is added AFTER that PATH, in the order
    written, unless it is already on it, so it fills in for a launcher that lacks
    it and never changes what your own PATH finds first.  The same folders reach
    the agent's PATH, before yolo's floor, so the agent's own commands find them
    too.  With no PATH at all, yolo checks these folders alone, and the agent
    gets the usual system folders ahead of them.
    Nothing else is added: yolo guesses no folder of its own, and runs no mise
    command.  To reach mise's tools from every launcher, list its shims folder.
    It does not reach the container runtime yolo boots jails with, `yolo capture`
    included: that is still found on the PATH yolo was started with.
    WHEN SOMETHING IS MISSING, yolo prints one line naming the program, the pack
    that needs it, the whole PATH it searched with this key's part marked, and
    this key as the fix, naming a common folder such as ~/.cargo/bin when one of
    them has the program.  That folder is only a hint: yolo never runs or counts
    a program it found there.  `yolo host apply` and `yolo check-deps` print it
    for any program your packs need, and `yolo host --` for the command it
    starts.  A launch checks the programs your packs need only when
    [bold]host_apply_on_launch[/bold] is on (off unless you set it, or turn on
    [bold]host_wrappers[/bold]); with it off, a missing one prints nothing at
    launch.  `yolo check` shows the PATH it read, which is the PATH of the shell
    you ran it in, plus these folders.
    Each entry is an absolute folder or starts with ~/.  A relative folder, ~user/,
    and any entry with `$` or `:` in it are refused: yolo expands no variable.
    A refused entry is ignored, and the line above and `yolo check` name it, with
    the fix.  A folder that does not exist is kept, and `yolo check` says so.
    USER SCOPE ONLY.  A folder here decides which program `yolo host` runs, and a
    workspace config travels with the repo, so a workspace value is a `yolo check`
    error, and is never read.
    Example (~/.config/yolo-jail/config.jsonc):
      "host_path": ["~/.cargo/bin", "~/.local/share/mise/shims", "/opt/homebrew/bin"]

  [bold]perf_logging[/bold] (boolean): Record every launch's timings, quietly.  Default FALSE.
    The persistent, SILENT form of `--timing`: every span (probes, image load,
    the child window, the whole shutdown chain) is appended to
    <workspace>/.yolo/host-perf.log as it happens, and NO report is printed at
    exit -- one dim line names the file, and that is all.  Any span over a
    second still names itself on stderr the moment it ends, so a slow launch
    says who is holding it while you wait.

    RECORDING IS NOT REPORTING.  This key, and YOLO_TIMING=1 / YOLO_VERBOSE=1 in
    the environment, are the always-on spellings: they record in silence,
    because a ~25-line table at every jail quit scrolls away whatever was on
    screen.  To SEE a launch's table, ask for it on that launch: `yolo --timing
    -- ...` or the global `yolo --verbose -- ...`, which also turn on the
    in-container breakdown.  Read the file any time for the launches you did
    not ask about.

    WHAT IT COSTS: about 2 KB and 35 lines per launch, capped at ~110 KB per
    workspace (the file keeps the last 50 runs and trims the rest at open), and
    tens of milliseconds of wall clock.  The line count is structural -- one
    start/end pair per span -- so a 30-second shutdown writes the same 2 KB as a
    fast one.  Output costs nothing: nothing is printed unless you ask.

    USER SCOPE ONLY.  It is read at the very top of a launch, before any
    workspace config is loaded, so a workspace value is never consulted -- and
    /workspace is writable by whatever runs in the jail.  A workspace value is a
    `yolo check` error.
    Example (~/.config/yolo-jail/config.jsonc):
      "perf_logging": true

  [bold]update_check[/bold] (boolean): Enable update checks and notices.  Default TRUE.
    Every ordinary host command reads the cached answer.  For a release-based install,
    normally once a day it starts a detached request to GitHub's releases API;
    the first automatic request waits for a terminal so its disclosure is
    printed before the network is touched.  Source installs are checked only
    by an explicit `yolo update --check` / `yolo update`, because that operation
    runs Git against the source checkout.  It may fetch commit objects, but
    moves no ref and changes nothing `git status` shows.

    When an update exists, one line under the startup banner says so -- only on
    a terminal -- and a safe, self-contained interactive launch offers to
    update and relaunch.  Homebrew and from-source installs are self-contained.
    `go install`, pipx and uv install only the host binary while the jail build
    comes from YOLO_REPO_ROOT, so `yolo update` refuses to replace just one half
    and explains the coordinated manual update.  A release archive gets a
    download link.  A YOLO_REPO_ROOT override that differs from a
    self-contained install's own source is the same split and suppresses the
    launch offer.

    `false` turns off the background check, the notice and the offer; explicit
    `yolo update` commands still work.  YOLO_NO_UPDATE_CHECK=1 is the per-shell
    spelling.  Automatic behavior never runs in a jail or in CI.

    USER SCOPE ONLY.  It is read on every host command, before any workspace
    config is loaded, and /workspace is writable by whatever runs in the jail.
    A workspace value is a `yolo check` error.
    Example (~/.config/yolo-jail/config.jsonc):
      "update_check": false

  [bold]workspace_readonly[/bold] (array of strings): Workspace sub-paths to overlay as read-only.
    Each entry is a relative path inside the workspace (no leading /, no ..).
    Mounted on top of the writable /workspace volume so agents cannot modify
    those paths. Use this to protect host-executed code that lives in the
    workspace repo (e.g. the yolo-jail src/ directory itself), and the git and
    agent control-plane files the host executes but `git diff` never shows you
    (.git/hooks, .git/config, .git/info, .claude, .mcp.json).
    Example: ["src", "flake.nix", "Justfile"]
    Example: [".git/hooks", ".git/info", ".claude", ".mcp.json"]
    Note: locking .git/hooks WITHOUT .git/config is defeated by core.hooksPath,
    which repoints hooks elsewhere -- lock the pair or neither.  Locking
    .git/config costs `git push -u` and branching from a remote-tracking ref
    (both write branch.*); `git push origin HEAD` and branching from a local
    ref need no config write.  If you lock .git/hooks, give hooks somewhere
    tracked to live first: `git config core.hooksPath .githooks`.
    BACKENDS: enforced on podman.  Enforced on Apple Container from version
    1.1.0 (check with `container --version`); on an older version, or when
    yolo cannot read the version, a loud warning names the paths, which stay
    writable.  So does the workspace config file, which the key also locks,
    and the warning does not mention it.  On macos-user there are no mounts
    at all, so entries are rendered as `(deny file-write* (subpath ...))` lines
    in the Seatbelt profile instead -- same policy, different mechanism.

  [bold]per_side_paths[/bold] (array of strings): Workspace sub-paths kept per side.
    Each entry is a relative path inside the workspace (no leading /, no ..).
    Each gets a per-workspace backing dir (under
    <workspace>/.yolo/home/venv-shadows/) shadow-mounted over it, so the
    host and the jail each see their own copy — for derived state that must
    not cross the host/jail boundary (interpreter symlinks, native builds).
    ".venv", "node_modules", and the venv path configured in the workspace's
    mise.toml are always shadowed automatically; list extra paths here (e.g. a
    workspace .cargo, or a monorepo's packages/*/node_modules -- the defaults
    are root-level only).
    Example: [".cargo", "packages/web/node_modules"]
    Note: node_modules became a default on 2026-08-23.  A node_modules shared
    between a macOS host and a Linux jail is already broken for any package
    with a native build, so the two sides were never able to share it safely.
    Expect one extra install per side on the first launch after upgrading.
    BACKENDS: enforced on podman and Apple Container.  NOT enforced on
    macos-user -- per-side shadowing needs a mount namespace and that backend
    has none, so host and sandbox share these paths; a warning is printed.

  [bold cyan]NETWORKING: WHICH WAY IS WHICH[/bold cyan]
    Read this before writing any port key.  There are two directions, one key
    each, and [bold yellow]THE TWO KEYS PUT THE PORTS IN OPPOSITE ORDERS[/bold yellow].

      WHO CONNECTS   WHO LISTENS   Key                          Entry order
      ------------   -----------   --------------------------   -----------
      the host       the jail      network.ports                "HOST:JAIL"
      the jail       the host      (nothing — dial by name)     n/a
      the jail       the host      network.forward_host_ports   "JAIL:HOST"
        ...same direction as the row above, but arriving on the JAIL's
           own localhost:<port> instead of on a hostname

    Read a row as "who dials whom", never as "which side owns the port".  Both
    keys are written in the jail's config and both name two ports; the only
    thing that tells them apart is the direction of the connection.

    Why the orders differ, so you can remember which is which:
    • `network.ports` is handed to podman's `-p` verbatim, and podman spells
      that flag HOST-side first.  Not yolo's convention to change.
    • `forward_host_ports` is yolo's own, and it is JAIL-side first, because the
      port you write is the one you are going to dial from in here.
    A transposed entry usually does not error — it publishes or forwards the
    wrong port, and presents as a broken service.  Check the order first.

    [bold]There are TWO loopbacks, and that is the whole confusion.[/bold]  In
    bridge mode the jail has its own network namespace, so `localhost` /
    `127.0.0.1` inside the jail is the JAIL's loopback — always, no exceptions.
    The host's loopback is a different interface, reached by NAME:
    `host.containers.internal`.  `forward_host_ports` is the one thing that
    blurs them, and only for the ports you list: it copies a host port onto the
    jail's own loopback so `localhost:<port>` in here answers.

  [bold]network.mode[/bold] (string): Network isolation mode.
    "bridge" (default): the jail gets its OWN network namespace — its own
      loopback, per the paragraph above.  Not cut off from the host: see
      "Reaching the host with no config at all" below.  Both port keys are
      honored ONLY in this mode.
    "host": the jail shares the host's network stack.  The two loopbacks become
      one, so `localhost` works in both directions and NEITHER port key is
      needed — both are ignored, with a warning from `yolo check`.
    `yolo --network <mode>` overrides this key for one launch.

  [bold]network.ports[/bold] (array of strings): [bold]HOST → JAIL.[/bold] Publish a
    server running INSIDE the jail so the host (and its browser) can reach it.
    Format: "HOST:JAIL" — host side first, podman's -p order.
      Also accepted: "IP:HOST:JAIL", and a "/tcp" or "/udp" suffix.
    Example: ["8000:8000", "3000:3000"]
      → a dev server on the jail's 0.0.0.0:3000 is at localhost:3000 ON THE HOST.
    A server bound to 127.0.0.1 inside the jail is NOT publishable — bind
    0.0.0.0 in here, which is safe: the published port is the only way in.
    Bridge mode only.

  [bold]network.forward_host_ports[/bold] (array): [bold]JAIL → HOST[/bold], arriving on
    the jail's own localhost.  Makes a host service answer at `localhost:<port>`
    INSIDE the jail, even one bound to the host's 127.0.0.1 (like `ssh -L`).
    Integer: the same port on both sides (e.g. 5432) — the common case.
    String "JAIL:HOST": different ports on each side (e.g. "5432:3306" listens
      on 5432 in the jail and connects to 3306 on the host).  JAIL SIDE FIRST —
      the reverse of network.ports.
    Example: [5432, 6379, "8080:9090"]
      → "8080:9090" makes the host's :9090 answer at localhost:8080 in the jail.
    [bold]Usually you do not need this.[/bold]  `host.containers.internal:<port>`
    already reaches the same service with no config and no socat.  Reach for
    this key only when something must literally see `localhost:<port>` — a
    hardcoded client, a tool with no host setting.
    Implemented with socat, so it needs socat on the host.  Bridge mode only;
    ignored (with a `yolo check` warning) when network.mode is "host".

  [bold cyan]Reaching the host with no config at all[/bold cyan]
    `host.containers.internal` is written into the jail's /etc/hosts by podman
    (169.254.1.2 today) and needs no key in this file.  It reaches the host
    itself AND host services bound only to the host's 127.0.0.1, because on a
    rootless podman yolo asks the network stack to forward the host's loopback
    in (--network=pasta:--map-host-loopback / slirp4netns
    allow_host_loopback).  This is how yolo's own host daemons are reached, so
    it is load-bearing, not best-effort.
    It was NOT true before 2026-08-17 — an agent "knowing" that the host's
    localhost is unreachable from a jail is remembering the old behaviour.
    What yolo decided rides into the jail as YOLO_HOST_LOOPBACK:
      requested   — the forwarding option went out; a service that does not
                    answer is a FAULT, not a limitation
      shared      — the jail shares the host's network stack, so the two
                    loopbacks are already one and `localhost` IS the host
      unsupported — yolo identified the stack and could not get it to forward
                    (a known limitation; upgrade passt)
      unknown     — no conclusion reached (rootful podman, unrecognised
                    backend, explicit network.mode, YOLO_NO_HOST_LOOPBACK)
    Only "unsupported"/"unknown" mean the forwarding may genuinely be absent.

  [bold]security.blocked_tools[/bold] (array): Tools to block inside the jail.
    Simple: ["curl", "wget"]
    Detailed: [{"name": "grep", "message": "Use rg", "suggestion": "rg <pattern>"}]
    A tool name is a BARE NAME — a single PATH segment, no "/", "..",
    ":" or absolute path — because it names the FILE yolo generates in
    the block dir; a path-shaped name is refused.
    Default: EMPTY — core blocks nothing.  Until 2026-09-04 it blocked
    grep and find by default, a default that silently assumed the image
    bakes rg and fd; that is true of the container backends and false of
    macos-user, which bakes nothing, so the block removed a tool and
    pointed at a binary that did not exist.  The list now lives in the
    [bold]guardrails[/bold] pack — add "guardrails" to `packs` to get it:
      • grep conditionally blocked — only recursive invocations
        (``-r``, ``-R``, ``--recursive``, or bundles like ``-rn``).
        Pipe filters and single-file greps pass through.
      • find unconditionally blocked.
    Your own entries here are unaffected, and an entry naming the same
    tool as a pack's REPLACES it whole.
    Conditional on the ALTERNATIVE existing: add ``replacement`` (a bare
    binary name) and the tool is blocked only when that binary is on the
    jail's PATH.  The two defaults set it (rg for grep, fd for find), so
    on a backend that bakes no image — macos-user, where tools come from
    ``packages`` or not at all — a jail without rg keeps working grep
    instead of losing it and being pointed at nothing.  An entry with no
    ``replacement`` always blocks, which is every custom entry.
    Exemptions: ``allow_flags`` (same pattern syntax) exempts an invocation
    even when block_flags match, or when the entry blocks unconditionally.
    It is scanned FIRST, so one allowed flag exempts the whole command.  This
    is what expresses "block unless limited" — block_flags matches on a flag
    being PRESENT and has no negated form.  Nothing yolo ships sets it.
    Conditional on FLAGS: add ``block_flags`` (array of shell case-glob patterns)
    to block only when argv contains a matching flag.  Absence means
    "always block" (find's default behavior).  Long options in
    block_flags match exactly; short patterns (starting with ``-``)
    match after any non-matching ``--*`` arg is skipped, so patterns
    like ``-*[rR]*`` catch ``-rn`` / ``-Rn`` without false-positive-ing
    ``--regex``.
    Example:
      "security": {
        "blocked_tools": [
          {
            "name": "grep",
            "message": "grep -r blocked; use rg",
            "suggestion": "rg <pattern>",
            "block_flags": ["-r", "-R", "--recursive", "-*[rR]*"]
          }
        ]
      }
    Bypass: Set YOLO_BYPASS_SHIMS=1 in scripts that need blocked tools.

  [bold]mise_tools[/bold] (object): Extra tools installed via mise in the jail.
    Keys are mise tool names, values are version strings.
    Default: {} — yolo ships no mise tool of its own. Every default runtime is a
    baked nix package instead (self-contained, present at boot, no first-use
    download).  (The `yolo init` template used to claim a `neovim` default here;
    there is none — see internal/config/config.go's defaultMiseToolsVals.)
    These are injected into the jail's global mise config (not workspace mise.toml).
    Deep-merged: user config adds tools, workspace config overrides versions.

    [bold]Which of the three places does your tool belong?[/bold] They are not
    interchangeable, and picking by habit is the common mistake:
      • The PROJECT needs it to build (a language runtime, a linter CI also runs)
        -> [bold]/workspace/mise.toml[/bold]. Committed, so CI and non-jail users get it
        too, and `mise install` applies it with NO restart. Putting a project
        requirement in mise_tools hides it where nobody outside a jail can see it.
      • YOU want it in every jail, but not on your host (an editor, a personal
        utility) -> [bold]mise_tools in ~/.config/yolo-jail/config.jsonc[/bold]. This is the
        one thing no workspace file can express, and the reason this key exists.
      • It is available in nixpkgs at the version you want -> prefer [bold]packages[/bold].
        Costs an image rebuild, but the binary is self-contained and present at
        boot. Reach for mise_tools when nix does not track what you need — a
        nightly channel, or a PyPI/npm-only tool (e.g. "pipx:some-tool").
    Once a mise_tools entry stabilizes, consider promoting it to `packages`.
    Example (user config): {"neovim": "nightly", "pipx:some-tool": "latest"}

  [bold]packs[/bold] (array): Everything a jail has beyond a bare shell — a coding agent
    and its config, shared skills, briefing prose.  [bold yellow]USER SCOPE ONLY[/bold yellow]: read from
    ~/.config/yolo-jail/config.jsonc directly, never from a workspace config.  A
    `packs` key in yolo-jail.jsonc is a `yolo check` error, because a workspace
    config travels with the repo and is agent-editable, so it must not decide what
    content (skills and briefing prose an agent then FOLLOWS) enters the jail.  A
    repo that wants to configure its own agents can just commit the files.
    [bold]The packs yolo ships are selected by BARE NAME, and none is on by default:[/bold]
      "packs": ["claude"]     also: copilot, codex, opencode, pi, agy
    With no packs configured a jail has no coding agent, and says so at launch.  That
    is the honest default: activating agents nobody asked for would put six tools and
    their config files in every jail.
    A pack from ELSEWHERE is named by a PATH — [bold]~/dotfiles/packs/mine[/bold] or
    [bold]/opt/packs/mine[/bold] — or, for a remote one, a git address
    [bold]git+ssh://git@host/org/repo//sub?ref=main[/bold].  The "~/" is expanded against your
    home at load, so ONE config can name one pack tree on machines whose homes differ
    (/home/you vs /Users/you) — the reason it exists.  A path needs no scheme: a pack
    NAME can never contain "/", so an entry with a separator is always a path.
    [bold]file:///abs/path[/bold] still works and means the same thing.  Two refusals, both
    naming the fix: [bold]file://~/…[/bold] (not a valid URL — the "~" parses as the host;
    drop the scheme) and relative paths ./x and ../x (no anchor this key can honor).
    [bold]A pack's NAME comes from your config line, never from its pack.json.[/bold]  An entry
    may set "name" itself; otherwise it is the last segment of the source
    ([bold]~/dotfiles/packs/mine[/bold] gives [bold]mine[/bold]; a git address uses its subpath).  That
    name is the staging directory, the handle `yolo pack ls` prints and `yolo pack
    explain` takes, and the /ctx dir a reads-host grant with no "into" lands in — all
    fixed before anything is fetched, which is why the pack's own manifest cannot supply
    it.  Set "name" when the directory is unhelpful, and note that two entries may not
    share one:  { "source": "/tmp/build/002", "name": "house" }
    [bold]Order is precedence, in a jail and at the host alike:[/bold] where two packs set one
    key, the later wins.  Later means the order this list names them in (a shipped pack included, so list
    your own pack AFTER a shipped one it overrides), then the packs another pack pulled in
    through its `needs`, then ~/.config/yolo-jail/local, which is always last.
    A pack named by a PATH may be a tree of symlinks, the shape a dotfile manager (rcm,
    stow, chezmoi) deploys: its links are followed wherever they point and the targets
    delivered as files, in a jail and at the host alike.  A git pack's symlink pointing
    out of the pack is refused, because a repository you do not control must not be able
    to deliver a file from your machine.
    Host access =a reads-host file, a `mount` of a host dir, an installer program, or
    a host-prepending briefing.  EVERY pack's declared claims are honored, whatever its
    origin — embedded, local (file://) or fetched (git).  There is no approval prompt:
    selecting the pack in your config is the consent, `yolo pack footprint <ref>` is
    where to review what a pack claims before you select it, and each launch's banner
    lists what every loaded pack reads from the host.  A launch on the host fetches a
    git pack it has never fetched and re-fetches a BRANCH ref at most hourly, printing
    "Fetched pack …" / "Updated pack …" when content arrives or moves; a TAG or a full
    commit SHA is never re-fetched by a launch, so a pin is how to freeze a pack that
    carries host code (only an explicit `yolo pack install`/`update` follows a
    re-pointed tag).
    [bold]A pack written for a newer yolo:[/bold] a contribution holding a kind, a `via` or a
    field this yolo does not know is left out of every launch, which prints one line naming
    the pack, the contribution and the field; a field outside every contribution is ignored
    and named the same way.  A `blocked-tool`, `intercept` or `autonomy` contribution only
    restricts, so it is kept without the field instead.  `yolo check` warns about each one,
    `yolo host apply --assert` writes nothing while one is left out, and `yolo pack lint`
    refuses the field, so a misspelling is still caught.  `yolo features` lists what this
    yolo reads, such as patch-series, patched-extensions, kind:<kind> and via:<via>.
    A pack.json declares effects as a "contributes" list, one entry per effect with a
    "kind" from the closed set:
      program       a tool on PATH: {bin, via:"npm"|"installer"|"source", package|url, flags}
                    yolo INSTALLS it, via a lazy launcher in ~/.yolo/bin/launch (last on
                    PATH, so it never shadows a baked binary).  Sole-owned by `bin`, so a
                    pack may declare SEVERAL programs (different bins) and each gets its
                    own launcher.
                    Also takes `protocols`: the wire protocols this program can be
                    POINTED AT, in preference order — the same names a provider files an
                    endpoint under (`["anthropic"]`, `["anthropic", "openai"]`), not the
                    `wire_api` dialect values.  It is the agent's half of the pairing a
                    provider and an adapter already declare, and it is what lets a launch
                    tell a provider this agent can use from one it cannot.  Omit it to
                    leave the agent UNCONSTRAINED: every provider then resolves directly,
                    which is what every pack did before the key existed.
                    Also takes `platform_switches`: [{platform, surface:"agent/name",
                    pointer:"/json/pointer"}] — settings in this program's OWN config
                    (a readsHost surface of this pack) that put the agent on a provider
                    platform by themselves, such as claude's
                    `/env/CLAUDE_CODE_USE_BEDROCK` in claude/settings for "aws-bedrock".
                    yolo removes one only where its own `yolo host apply` wrote it and
                    the file still holds that value; when the user's copy turns it on
                    (true, 1, yes, on) and the agent's selected provider is not of that
                    platform, the launch prints one line naming the key and both fixes,
                    and says so when the key is one `yolo host apply` wrote.
                    Also takes `platform_regions`: [{platform, region_env_name:[NAME...]}]
                    — the region variables this program reads on that platform, where it
                    reads fewer than the platform's providers list.  The region check then
                    counts only those for this agent: opencode's pack lists AWS_REGION
                    for "aws-bedrock", because opencode ignores AWS_DEFAULT_REGION, so a
                    launch delivering opencode only AWS_DEFAULT_REGION is refused.
                    via:"source" is a FORK: {bin, via:"source", fork_of:"<base pack>",
                    source:"git+https://…?ref=…", build:"<one command line>",
                    produces:[home-relative paths, one of them .local/bin/<bin>,
                    .npm-global/bin/<bin> or go/bin/<bin>]}.  The base pack keeps the
                    name, its launch flags, posture, profiles, briefing and skills; the
                    fork supplies only the bytes, and may add `platforms` and
                    `node_floor` but no other program field.  `source` is a git address
                    (file:// is refused: a directory has no revision).
                    A PATCHED fork adds `patches:"<pack dir>"`, a `git format-patch --base`
                    series yolo replays onto the UPSTREAM that `source` then names, so
                    what runs follows that upstream while the series applies and builds;
                    a newer upstream that conflicts keeps the last good build running.
                    `follow` picks a branch ref's commit: "release" (default, the newest
                    semantic-version tag), "release:<prefix>", or "head"; a tag or full
                    commit holds it.  `follow` is refused without `patches`.  `yolo pack
                    status` shows the series, the good build and what is pending; `yolo
                    pack rebase <pack>/<bin>` sets up the fix for a series that stopped
                    fitting; `yolo pack series check [<pack dir>]` says whether a local
                    pack's series still applies, and `yolo pack rebase <pack>/<bin> --pack
                    <pack dir>` rebases it, both in a jail too.  `yolo pack lint` reads the
                    series, and `--online` checks its upstream.  Needs git 2.40 on the
                    host.  Export a series from a fork:
                    git format-patch --base=$(git merge-base <upstream>/main HEAD) \
                        -o patches <upstream>/main..HEAD
      blocked-tool  {bin, message, suggestion, replacement, flags} — refuse a tool
                    inside the jail and print an alternative.  `flags` limits the block
                    to matching argv (absent = always); `replacement` names the binary
                    the suggestion points at, and the block is generated ONLY when that
                    binary is on the jail's PATH — so a jail without the alternative
                    keeps the original tool instead of losing both.  Core blocks
                    nothing by default; the `guardrails` pack ships grep/find.
      intercept     {bin, forward} — route a command NAME in the jail to a forwarder
                    the pack declares: ~/.yolo/bin/block/<bin> becomes
                    `exec <forward…> "$@"`, first on PATH, so a bare `<bin>` runs the
                    forwarder while the installed program stays at its own path
                    (reachable by that path, or with YOLO_BYPASS_SHIMS=1).  It layers
                    permissions over an existing CLI: the `github` pack routes `gh` to
                    a host broker.  forward[0] is a bare program name on the jail's PATH
                    and never <bin> itself.  A blocked-tool for the same name wins.
      requires      {bin} — a binary that must ALREADY exist.  Asserts presence and
                    installs nothing: no launcher, nothing on PATH, so it cannot shadow
                    anything.  In a jail an absent bin is reported by name at boot (a
                    warning, not a boot failure).  Many packs may require one binary —
                    unlike program it owns no path, so it never collides.
                    Both program and requires take optional
                      install_hints {"brew"|"brew-cask"|"apt"|"dnf"|"pacman"|"nix": pkg}
                    naming the package that provides `bin` on a host package manager,
                    which `yolo check-deps` / `yolo host apply` print as the remedy for
                    a missing binary (and write into a Brewfile and kin).  `brew-cask`
                    is a Homebrew CASK rather than a formula and wins over `brew`.  For
                    a program, the pack's OWN installer (its via/url/package) is
                    preferred over a hint — a tool shipping its own installer ships its
                    own updater, while a distro package pins whatever that repo has.
                    So hints matter most on `requires`, where yolo installs nothing.
      skills        {from (pack dir), into (~ dir)} — merged (built-in < pack < yours).
                    `from` IS honored, at both notches and by wrapped-plugin discovery; it
                    defaults to skills/.  A `from` naming a dir the pack lacks delivers
                    nothing and says so; an absent CONVENTIONAL skills/ is silent.
                    Takes `agent` and `agents` on the same terms as `briefing` below: the
                    owning pack declares which agent reads a destination, and a content
                    pack addresses its tree to a name instead of a path — or names
                    neither, and it reaches every skills destination.  skills/ is ONE
                    unit: it broadcasts unless a contribution names it, so adding a
                    narrower tree beside it keeps it broadcasting.
      briefing      {from, into, after:"host:<path>" to prepend your own file first,
                    agent, agents}.  A pack's prose is every *.md directly inside its
                    briefing/ dir (filename order), plus any file a `from` names.  A root
                    AGENTS.md, CLAUDE.md or GEMINI.md is NEVER read: it is the pack
                    repository's own instructions.  A `from` with one of those basenames,
                    or such a file inside briefing/, is refused.  `from` names exactly ONE
                    file; one that is missing or blank delivers nothing (a launch warns),
                    and no other file is read in its place.  Omitted, `from` means every
                    briefing/ file no other contribution names.
                    `agent` is the IDENTITY a destination declares for itself — the
                    launcher command whose agent reads that `into`, declared by the pack
                    that OWNS the name.  A destination SOURCES NOTHING: `from` on one is
                    refused.  `agents` is the AUDIENCE a content contribution names:
                    deliver this prose only where a matching `agent` was declared.  A
                    contribution gives `into` OR `agents`, never both — naming who it is
                    for is what makes the destination inferable, and a content pack has
                    no business naming a path it cannot keep current.  Giving NEITHER
                    means BROADCAST, with or without a manifest: {"kind": "briefing"}.
                    Each file has ONE governing contribution, so declarations only add:
                    {"from": "files/pi.md", "agents": ["pi"]} beside briefing/ delivers
                    both.  Two content contributions naming one source are refused.
                    One name has exactly ONE owning pack, across `program`, `launch`,
                    `briefing` and `skills`; two claimants is a launch error naming both.
                    The vocabulary is the packs you SELECTED and nothing wider: naming an
                    agent your `packs` do not provide is fatal at launch and at `yolo host
                    apply`, with one message for a typo and for a real agent you did not
                    select — they are the same mistake, with the same two remedies.  `yolo
                    pack lint` reports the targeting and refuses nothing: it reads one pack
                    root with no config, so it cannot know what you selected.
      files         {from, into} — an opaque tree the pack owns, bind-mounted :ro at
                    `into` in the jail.  Unlike skills/briefing, `from` is REQUIRED (a
                    file or a dir), and `into` or `agents` too: files never broadcasts.  Sole-owned: two packs claiming one `into` is a
                    launch error naming both.  At the HOST notch it is WRITTEN into
                    your real home rather than bound: only paths yolo's ownership
                    record claims, the previous copy archived first, and a render
                    that cannot prove ownership refuses and touches nothing.
                    A PATCHED EXTENSION replaces `from` with `source` (the upstream) and
                    `patches` (a series, as for a patched fork), with optional `follow`
                    (as for a patched fork), `build` and `produces` (paths relative to the
                    built tree): yolo builds the tree on the host and mounts a read-only
                    copy at `into` (the pi pack's extensions use it).  Put it at
                    `into: ".pi/agent/yolo-patched/<name>"`, outside ~/.pi/agent/extensions/
                    where pi would also find it by itself.  pi loads it only through a
                    `config-list` entry in `pi/settings` `/packages` that is ~/ plus `into`
                    (~/.pi/agent/yolo-patched/<name>), or a path under it, with no slash at
                    the end; without one the tree is built and mounted, pi never loads it,
                    and `yolo pack lint` and each launch say so.  Drop the extension's old
                    `git:` entry in the same edit, or pi loads it twice.  Its key in
                    `yolo pack rebase` and `yolo capture` is <pack>/<name>, <name> being
                    the last part of `into`.
      config        {config:[surface...]} — a composed config surface (see below)
      config-overlay {surface:"agent/name", config:{managed:{...}}, profile} — keys on a surface
                    another pack owns.  `managed` is the ONLY body field: a contributor
                    contributes keys, so path/codec/mode/defaults are refused by name.
                    Folds in BELOW the owner's managed layer, so the owner wins a
                    conflict; `yolo config diff <agent>` says which pack set which key.
                    If no selected pack owns the target the overlay has NO EFFECT and
                    is reported by name — it never creates the file.  `profile` GATES
                    the whole contribution on that profile being the one active for the
                    TARGET SURFACE's agent: inactive means a clean skip (selection is
                    the optionality), and a gated overlay naming a surface nobody owns
                    is reported only while its profile is selected.
      config-list   {surface:"agent/name", path:"/json/pointer", add:[entry...]} —
                    ENTRIES appended to one array of a surface a pack owns, without
                    copying or replacing the list (a config-overlay array REPLACES).
                    `path` is an RFC 6901 JSON Pointer ("/packages"; "~1" is a "/"
                    inside a key, "~0" a "~"), never the root and never an empty step.
                    `add` is required, may be [] (a no-op), and may hold no null.
                    Entries fold AFTER every config-overlay: existing entries keep their
                    order, then each contributed entry not already present, compared as
                    whole JSON values, so the same entry from two packs is written once.
                    A missing array starts empty; a non-array there, or a non-object
                    parent, refuses that surface's render.  Captured edits, computed and
                    managed values still replace the final array.  No owning pack
                    selected: no effect, reported by name.  Every object surface
                    captures a list path per entry (stateful, rmw, computed), so an
                    in-jail edit never freezes the list; a keyless (lines/raw) target
                    is REFUSED at launch, naming the surface and its mode.
      state         {at (~ dir), scope:"workspace"|"machine", because} — persists
      reads-host    {host (~-relative file), into (/ctx dest)} — one file, :ro [gated]
      mount         {host (~-relative DIR or file), into (/ctx dest)} — :ro    [gated]
      env           {vars:{KEY:"value"}, platform|profile} — STATIC strings only; no
                    interpolation, no host reads, so it is honored for any origin.
                    A GATE limits the whole contribution to the agents whose selection
                    satisfies it — the pack's own agent, or for a pack that installs no
                    CLI every agent: `platform` to those whose selected provider
                    declares that platform, whatever the profile is named (aws-auth's
                    credential pointer, for "aws-bedrock"), and `profile` to those that
                    selected that profile by name.  One gate at most.  A provider fact
                    belongs on `platform`: a second profile over the same provider gets
                    it, which a name gate misses.  `region_profile_setting` (beside
                    `served_by` and a `platform` gate) names the setting of the serving
                    loophole that holds the profile its credential is minted for
                    (aws-auth's `profile`): an agent it reaches takes its region from
                    that profile's section of the platform's `region_file`.
      hook          {hook:"shared_credentials"|"shared_directory"|"unshare_directory"|
                    "per_jail_history", from (~-relative path the hook acts on), at (a
                    machine-scope state dir THIS pack declares; the two shared_* hooks
                    only)} — the shared pair replaces `from` with a symlink into `at`, a
                    FILE for shared_credentials and a whole DIRECTORY for
                    shared_directory, so one login (or one package store) serves every
                    workspace on the machine. unshare_directory undoes a
                    shared_directory the pack no longer declares: the link at `from` to
                    `at` becomes an empty directory; anything else there is left alone.
      autonomy      {autonomous:{...}, guarded:{...}} — the agent's two permission
                    postures; the confinement notch selects one (autonomous at
                    jail/guest, guarded at host), so a jail-bypass key never reaches
                    your real home via `yolo host apply`.  Each posture takes
                    {config:[surface...]} patching the managed layer of a surface THIS
                    pack owns, plus {launch:[{bin, flags}]}.  Either posture may be
                    empty, in both directions: a permissive-by-default tool only needs
                    `guarded`, and a pack whose autonomy is a LAUNCH FLAG ALONE only
                    needs `autonomous` — a flag has no persistence, so not selecting it
                    IS the guarded posture (copilot's `--yolo` is the shipped instance).
                    A posture is the ONLY place a launch flag can be declared, so every
                    flag yolo injects is one some notch can withhold; an injection is
                    printed at the launch that makes it, with both command lines.
      profile       {name, provider} — a NAMED SELECTION OVER A PROVIDER, and that is the
                    whole body.  `name` is the selector the `profile` key or `-p <name>`
                    sets; `provider` is the `providers` entry it selects and is
                    REQUIRED — a profile without one is refused by the manifest schema.
                    Whatever ELSE a launch under that profile should deliver (env
                    vars, config keys) is declared by the gated contributions of the
                    kinds that own those channels: `env` and `config-overlay` both take
                    a `profile` field naming the profile that activates them, and `env`
                    a `platform` naming the provider service instead, which a fact of
                    the provider (not of the profile's name) should use.  A
                    profile name is sole-owned WITHIN the pack only: two packs may both
                    declare `bedrock` and stay unrelated.  A profile no launch selects
                    does nothing.
      provider      {name, platform, endpoints:{protocol:{base_url, wire_api}},
                    api_key_env_name, region, region_env_name:[NAME...],
                    region_file:{path, path_env_name, profile_env_name,
                    default_profile, profile_section, key},
                    models:{alias: id}, model_options, capabilities,
                    options:{option: default|null}} —
                    the SERVICE facts of a named provider: what service it is
                    (`platform`, open vocabulary, "aws-bedrock" for Bedrock; an agent's
                    derive and a `platform` env gate recognize the service by it), the
                    endpoints that speak each wire protocol, the region a regional
                    provider is reached through, the model ids an alias names, and the
                    OPTION names a profile may set (`options`; see [bold]providers[/bold]
                    below).  `region_env_name` makes a region a LAUNCH REQUIREMENT for
                    every provider of this one's `platform` (which it needs beside it):
                    the variables an agent there reads its region from, so a launch
                    whose agent is on such a provider with no `region`, none of them
                    delivered to it and none in its `region_file` is refused, naming
                    every way to set one.
                    `region_file` (which needs `region_env_name` beside it) says where
                    that platform's agents keep a region the environment does not carry:
                    the `key` of one profile's section of a file under your home
                    (`path`, relocated by `path_env_name`), the profile being the one the
                    serving loophole's `region_profile_setting` names, else the one
                    `profile_env_name` delivers, else `default_profile`.  A profile's
                    section is `profile_section` with {profile} replaced; the default
                    profile's is that one when the file has it, else its bare name
                    (`profile default`, then `default`).  yolo reads it on the machine
                    it launches on and delivers the region in the first variable the
                    agent reads, at every notch, saying so; packs/bedrock declares
                    ~/.aws/config's
                    `region`, AWS_CONFIG_FILE and AWS_PROFILE.  Composed UNDER your
                    `providers` entries per field, so overriding one model alias, one
                    region or one URL keeps everything else the pack shipped.  The
                    credential is NEVER
                    here: api_key_env_name is the NAME of a variable you hydrate
                    (env_sources), and a base_url carrying userinfo is refused.  The
                    entry carries facts only — WHICH environment variable each fact
                    lands in is stated by the agent pack's own derive.lua (its
                    yolo.env producer), never by provider vocabulary, so a pack cannot
                    ship a credential that way either.  A
                    provider name is sole-owned — two packs shipping one is a launch
                    error.
      models        {provider, add:[{id, vendor, alias, name, description,
                    context_window, max_tokens, reasoning, input, cost}]} or
                    {provider, only:[id...]} — SHAPES the model list of the provider
                    it names, any provider's, another pack's included: `add` appends
                    entries (a duplicate id keeps the first writer's), `only` keeps the
                    ids it names and drops the rest.  One verb per contribution.
                    Every `add` applies, in pack order, before every `only`, and two
                    `only`s intersect; then your own `providers.<name>.models` composes
                    over the result, so your config has the last word.  `vendor` (the
                    model's maker) is required on each entry; `alias` makes the entry
                    reachable under a second name, such as `default`.  Under an
                    `only`, each agent's model menu for the provider is exactly the
                    list where the agent allows it, and while the profile's
                    `enforce_models` is on (the default) claude, opencode and pi also
                    refuse any other model.  `yolo check` names a duplicate, an
                    `only` id nothing added, and a provider nothing declares.
      adapter       {adapts:{from, to}, address} — a PROTOCOL CONVERSION: the wire it
                    reads, the wire it speaks, and where the converted wire is served.
                    An agent that speaks `to` can be pointed at a provider that offers
                    `from`, with no yolo-internal value in anyone's config: the address
                    composes into that provider's table entry under `to`, exactly as if
                    the provider had declared it.  IT SAYS NOTHING ABOUT WHO RUNS IT —
                    the address may be a daemon the same pack ships (a `service`
                    contribution beside this one, joined by `needs`), a remote gateway
                    you already pay for, or a proxy running on your own machine.  The
                    PAIR is sole-owned, so two selected packs converting one wire into
                    another is an error naming both; one pack may declare several pairs.
      loophole      {from} — a loophole MODULE dir the pack ships, holding a
                    manifest.jsonc (the same on-disk shape a bundled loophole has, so a
                    loophole can be developed standalone and dropped into a pack).
                    `from` is REQUIRED and there is no `into`: the host half runs on the
                    host and the jail half mounts at a path core owns.  A `from` naming
                    a dir the pack lacks is refused BY NAME, not skipped.  The loophole's
                    NAME is that dir's basename and must match the manifest's own `name`;
                    it is sole-owned, so two packs shipping one name is an error.
                    THE SHARPEST KIND, and the only one whose claim is host code
                    EXECUTION rather than a host read.  Every crossing the module
                    declares is a SEPARATE claim, disclosed rather than approved (there
                    is no prompt; selecting the pack is the consent, and `yolo pack
                    footprint` lists the claims): the daemon argv + doctor_cmd (one
                    claim, raw and unelided, printed just before it runs), one per TLS
                    intercept (a CA every client
                    in the jail trusts — claimed even with no daemon), one per host bind
                    mount, one per SOCKET bind as its own read-write host-IPC class (`:ro`
                    is no boundary for an AF_UNIX socket — measured), and one per host
                    device.  `state_files` needs no claim (it stays inside yolo's own
                    state tree).  Refused at the host notch: a loophole is a host daemon
                    whose only client is a container, so with no jail there is no client.
      service       {name, jail_daemon:{cmd, restart}, host_daemon:{cmd}, endpoint,
                    platforms, serves, settings} — a DAEMON the pack contributes to a
                    namespace: a yolo-jaild subcommand run in the jail (under the same
                    supervised list the loopholes use) and/or a host-side `yolo internal
                    daemon`, plus its endpoint file at /run/yolo-services/<endpoint>.
                    THE ANTI-LOOPHOLE: it holds NO grant and crosses NO boundary — it
                    binds the jail's own loopback, reads no host state, mounts nothing,
                    and so is never a claim.  The name
                    is sole-owned (the daemon log and the endpoint file are both
                    name-keyed).  The jail daemon runs under the existing supervisor.
                    The host_daemon half (argv `yolo internal daemon <name>`) runs at
                    `yolo host --` and on macos-user, as a child of the one launch whose
                    agent is paired through the service, and stops when that agent exits;
                    only a pack yolo ships may declare one that runs, and a fetched or
                    local pack's is refused by name (host-notch-services.md OQ-HS4).
    AT THE HOST NOTCH (`yolo host apply`) THE KINDS BELOW DO NOT APPLY, and this is
    where the reason lives.  The report names them in one line and stops, because a
    reason is for the person changing a rule and not the person meeting it; what
    follows is that reason, per kind, once.  "Does not apply" means the kind has no meaning off-container
    — it is never a refusal of your apply, which stops nothing and writes your other
    surfaces normally.
      blocked-tool  a blocker is a shim at the head of a JAIL's PATH.  Off-container yolo
                    owns no PATH entry to put one in, and editing your shell rc to take
                    one over is a far larger claim than a pack's contribution makes.
      intercept     an intercept is a forwarding shim at the head of a JAIL's PATH, for
                    blocked-tool's reason: off-container yolo owns no PATH entry to put
                    one in.
      state         state names a jail-writable home subtree — off-container the home
                    simply is writable, so there is nothing to declare.
      reads-host    reads-host carries a host file INTO a jail.  With no jail the file is
                    already where the reader is.
      mount         a mount needs a mount namespace, which is unavailable without a
                    container.
      env           env vars apply to a process yolo starts, and `yolo host apply` only
                    configures your tools — it never runs them.  Setting them for your
                    whole session would mean editing your shell rc.  `yolo host --
                    <program>` delivers them at launch instead, to that process only.
      hook          the shipped hooks are jail provisioning steps — a credential or
                    package-store symlink into the machine tier, and per-jail history.
                    Off-container each is either meaningless or a mutation of real user
                    state that no pack should perform unprompted (the directory one would
                    replace a real directory in your own home with a symlink), so this
                    command runs none of them.
      adapter       an adapter's address is composed into the providers table a LAUNCH
                    carries, so it reaches an agent the moment one starts and never
                    through a config file.  This command starts none, so nothing is
                    pointed anywhere.
      loophole      a loophole is a host daemon whose only client is a container: with no
                    jail there is no client, no --add-host, no YOLO_JAIL_DAEMONS, and
                    nothing for its endpoint file to be mounted into.  Launch a jail to
                    run it.
      service       a service is a daemon pair plus an endpoint file under the jail's
                    /run.  With no jail there is nothing to supervise the jail half and
                    nothing to read the endpoint.
    WHAT A HOST APPLY COMPUTES, as a jail does: `yolo host apply`, and the automatic
    apply a wrapped launch runs, run each pack's derives over inputs composed from
    your USER config alone — the providers table (your `providers` over the selected
    packs' provider facts), your `mcp_servers`, your `lsp_servers`, and the selection
    your `profile` key names.  So the provider facts reach `pi/models`,
    `pi/codex-models`, `codex/config`, `opencode/config` and `oh-omp/models` at the
    host too, pi registers the declared openai-codex list, and every agent's MCP and
    LSP files carry your servers.  Never an MCP preset (its command is a wrapper only
    a jail writes), a pack's `mcp` declaration, a workspace's config, or a value naming
    a path only a jail has: each is left out and named.  A table a derive declares in
    full is yolo's there, as in a jail, so an entry you added by hand to one is
    dropped — confirmed first, the first time — unless your config declares it.
    That selection is applied edge-triggered: written when the chosen profile
    changes, your own later /model pick kept, and only what yolo wrote cleared when
    you deselect.  A one-launch `-p` has no meaning here, since this command launches
    nothing.
    NOTE (shipped behavior): two packs declaring a skills `into` at the SAME path fail
    the jail at boot.  (This note also said a jail ignored `briefing.from` and read a
    root AGENTS.md regardless.  Both notches now resolve every pack through one
    predicate, and neither reads a root AGENTS.md at all.)
    Entry forms — a bare name, a source string, or an object:
      source      required unless the entry is a bare embedded-pack name.
                  file:///abs/path (local) or
                  git+ssh://git@host/org/repo//subdir?ref=branch.
      name        short name for the staging dir and `yolo pack ls`.  Defaults to
                  the last path segment; two packs resolving to the same name is an
                  error (they would share a staging dir).
      only        globs to include; matches a DIRECTORY prefix, so "skills/rust-*"
                  takes the whole skill dir.  Default: everything.
      exclude     globs to drop, applied after `only`.
    A pack SHIPS ITS TOOLS: a file carrying the exec bit stages executable, so a skill
    can ship the script it tells an agent to run.  What a pack may NOT do is land a
    destination on the jail's PATH — that is refused in the manifest, because a name on
    PATH comes from a `program` contribution, which owns it and discloses it.
    Precedence: later entries win on same-named skills.  Within one agent, the order
    is built-in skills < pack skills < your own ~/.<agent>/skills, so a pack may
    override a yolo built-in but never a skill you wrote.
    Pack prose is appended to each briefing as plain text, one blank line between
    files and between packs (`briefing_provenance: true` labels each pack's section
    once).  To EACH briefing unless the file's contribution named an audience: prose
    carrying `agents` reaches only the destinations whose owner declared a matching
    `agent`, at both notches.
    Tooling: [bold]yolo pack init|lint|ls|explain|footprint[/bold].  `lint` runs the real
    staging rules (the escaping-symlink refusal) AND validates the pack.json
    manifest (unknown kind, missing field, unknown key — every problem, not the
    first), then prints the pack's footprint.  `footprint <path>` shows what a local
    pack you are authoring claims, and any collision, before you configure it.
    `explain` lists exactly which files stage and which the filters dropped.
    Example: ["claude", "file:///home/me/code/acme/tools/agent-pack"]

  [bold]providers[/bold] (object): Your own provider entries, composed OVER the ones the
    selected packs ship, per field — overriding one model alias, one region or one URL
    keeps every other field the pack shipped.  Each key is a provider NAME, and the name
    is sole-owned across packs and config together: two packs shipping one is a launch
    error.
    ⚠ WHERE A CREDENTIAL GOES IS USER-SCOPE ONLY.  `endpoints` in any form (a URL, a
    protocol, a dialect, or a null removing one), `api_key_env_name` (a value or a null),
    `platform`, and a null provider or null `providers` are REFUSED in a workspace
    `yolo-jail.jsonc` or `yolo-jail.local.jsonc`, each naming the field; write them in
    your user config instead.  The workspace file is agent-editable: an agent that can
    repoint its own model endpoint can send everything it reads to a server you did not
    choose, one that can rename the variable a provider claims can send you a different
    credential (GH_TOKEN, say) to that provider, or unclaim a key so every process
    receives it, and one that can relabel a provider's platform can hand its agents a
    credential pointer meant for another service.
    `models`, `options`, `region` and `capabilities` still merge from either scope, a
    `region` only as a region name (below).
    Per entry:
      base_url       [bold yellow]REMOVED[/bold yellow] — an entry carrying it is REFUSED, naming the
                     explicit spelling.  The bare field said WHERE without saying WHICH
                     WIRE, so the same line meant different protocols to different
                     agents (pi read it as openai, claude as anthropic) — and its
                     headline case was the trap, because llama.cpp, ollama and vLLM all
                     speak OpenAI, so `claude` plus a bare URL pointed it at a server it
                     could not talk to.  Write `endpoints.<protocol>.base_url`.
      endpoints      {protocol:{base_url, wire_api}} — where each wire protocol points.
                     The KEY is the protocol an agent asks for by name, and an agent
                     that speaks none of them reaches the provider only if some selected
                     pack declares an `adapter` from one of these to one of its own —
                     otherwise the launch REFUSES, naming both protocols and the pack
                     that would bridge them.  A URL carrying userinfo is refused: a
                     base_url routes an ADDRESS, never a credential.
      wire_api       the DIALECT an endpoint speaks, when it is not the protocol key's
                     own default; declared inside an `endpoints` entry.
      api_key_env_name  the NAME of the variable you hydrate (env_sources), or a list of
                     names for a provider with several credential routes (packs/bedrock's
                     bedrock lists six) — the credential itself is never in this
                     config.  A named variable reaches only the agents whose profile
                     selects this provider, and the launch pre-flight refuses a provider
                     some agent selected whose variable is empty.  A provider that sets
                     no api_key_env_name but a `platform` claims the names every provider
                     of that platform lists, so a Bedrock provider of your own keeps the
                     six AWS names to its agents as `bedrock` does.
      platform       what service this provider is, one token in an open vocabulary
                     ("aws-bedrock" for Amazon Bedrock).  Yours gets exactly the behavior
                     a shipped provider of the same platform gets: a Bedrock provider of
                     your own, `{"platform": "aws-bedrock", "region": "eu-west-1"}` with a
                     profile over it, switches claude to its Bedrock client, receives the
                     aws-auth credential pointer, claims the AWS credential variables
                     `bedrock` claims (unless it lists its own api_key_env_name) and is
                     required a region.  A value no pack knows changes nothing.
      region         the region a regional provider is reached through, as one DNS label
                     ("us-east-1"): the agents build their service's host name from it,
                     so a value with a dot, a slash or a "#" is refused at every scope.
                     For a provider whose platform a selected pack declares region
                     variables for (`bedrock`, and any provider of yours with
                     "platform": "aws-bedrock"), an agent with no `region` here and none
                     of the region variables it reads (AWS_REGION or AWS_DEFAULT_REGION;
                     opencode reads AWS_REGION alone) delivered to it is given the
                     region its AWS profile has in ~/.aws/config on the machine yolo
                     launches on, in a jail and at `yolo host` alike, and the launch
                     says so.  When that file gives none either, the launch is REFUSED,
                     naming the three ways to set one: this key, a variable in
                     env_sources, or the profile's `region` in that file.
                     YOLO_ALLOW_MISSING_PROVIDERS=1 launches anyway.
      models         {alias: model id} — the aliases a profile's `model` option names.
                     A value may instead be an object, {id, name, description,
                     context_window, max_tokens, reasoning, input, cost}: the wire id
                     plus the facts an agent's menu shows (`description` is the second
                     line claude's picker gives a model).
                     The agent pack's own derive.lua decides which alias each of the
                     agent's keys reads; `default` is the alias used when a profile
                     states no option, and it is an ordinary name, not a keyword.
                     This map composes LAST, over the provider's own list and every
                     pack's `models` contribution (added entries, or an `only`), so
                     your aliases, additions and nulls win.
                     Four names are CONVENTIONAL TIER ALIASES every provider is
                     expected to declare: `default`, `fast` (cheap and quick),
                     `balanced` (the middle tier) and `frontier` (the most capable).
                     A convention, not a requirement: when a pack asks for one this
                     provider does not name, the launch warns and proceeds.
                     claude pins its tiers from them: `balanced` its Sonnet tier, `fast`
                     its Haiku tier, and `frontier` its Opus tier on the ChatGPT
                     subscription's list (`openai-codex`) and on a list a pack's `only`
                     narrowed. `sonnet`, `haiku` and `opus` still work, and win when a
                     provider names both.
                     `yolo check` warns about an id no installed agent's own model
                     catalog knows, and says when it could read no catalog; it never
                     refuses one, and no launch asks.
                     A value may be an object instead of an id string: {id, name, vendor,
                     reasoning, input, cost, context_window, max_tokens}, where `id` is
                     the wire model id and the rest are facts an agent's derive reads.
                     `vendor` is the model's MAKER, one lowercase token such as
                     "anthropic" or "openai": on a provider that serves several makers'
                     models (`bedrock`), each agent is offered only the entries its own
                     client can call (claude's Bedrock client, Anthropic's alone), and an
                     entry with no vendor is offered to every agent.
                     Example: {"bedrock": {"models": {"kimi":
                     {"id": "global.moonshotai.kimi-k3", "vendor": "moonshotai"}}}}
      capabilities   the named jobs this provider performs for itself, e.g.
                     ["web_search"].  A launch that selects it OMITS every
                     `mcp_servers` entry whose "provides" names one of them — the
                     server would be a second implementation of something the
                     provider already does.  Same vocabulary `provides` and
                     `required_capabilities` are spelled in; the packs that ship a
                     provider declare it, and an entry here overrides that.
      options        {option: default} the profile surface this provider DECLARES —
                     the only schema a `profiles` entry answers to.  A default value
                     is what a profile inherits when it does not state the option;
                     `null` declares the option settable but defaultless, so a profile
                     that says nothing about it delivers nothing.  A profile entry
                     naming an option this map does not hold is refused — but only
                     once the provider declares at least one option, since a provider
                     with no `options` imposes no schema at all.
    Null removes an entry.  Which environment variable each fact lands in is the agent
    pack's decision (its yolo.env producer) — this key carries facts, not bindings.
    Example: {"zai": {"endpoints": {"openai": {"base_url": "https://api.z.ai/api/paas/v4",
                                               "wire_api": "openai-chat-completions"}},
              "api_key_env_name": "ZAI_API_KEY",
              "models": {"default": "glm-5.3[1m]", "fast": "glm-5.3-flash[1m]"},
              "options": {"model": "default"}}}

  [bold]adapters[/bold] (object): Where an ADAPTED provider answers — the one field of an
    adapter you may set.  [bold yellow]USER SCOPE ONLY[/bold yellow], for the same reason `providers`
    addresses are: this decides where an agent's inference goes, and a workspace config
    travels with the repo and is agent-editable.
    An adapter is a pack declaration — it says which wire it converts into which, and at
    what address — so a provider that offers only `openai` reaches an anthropic-speaking
    agent with nothing in your config naming a port.  You need this key only when that
    port collides with something: harmless inside a container, where 127.0.0.1 is the
    jail's own private loopback.  At `yolo host --` and on `macos-user` an adapter whose
    own pack's service serves it (the wire bridge's) answers on a port that one launch
    picks for the service it starts, and this override does not apply to it there; it
    still moves an adapter no pack service serves (a gateway or a proxy you run).
    Each key is the CONVERSION, spelled "<from>-><to>" — the same pair the declaring pack
    claims, which is sole-owned.  The only field is `address`, an http/https URL; a key
    naming a conversion nothing declares is inert, and a null drops the override.
    Example: {"openai->anthropic": {"address": "http://127.0.0.1:9214"}}

  [bold]profiles[/bold] (object): Your own NAMED SELECTIONS over providers — profile
    name → {provider, ...option values}.  USER-SCOPE ONLY: the key is read from your
    user config directly, and a workspace config carrying it is REFUSED, because a
    workspace file travels with the repo and is agent-editable, and a profile steers
    WHICH ENDPOINT and WHICH MODEL an agent talks to.  Per entry:
      provider       REQUIRED — what the name selects.  An entry without one is
                     refused: a profile is a selection, so the name declares nothing
                     by itself.
      enforce_models true (the default) or false — a profile FIELD, not an option.
                     Where a pack's `models` contribution narrowed the provider's list
                     with an `only`, on means every agent that can refuse a model
                     outside the list does (claude's allowlist, opencode's whitelist,
                     pi's extension), and on `openai-codex` claude and pi refuse outside
                     the subscription's list with no `only`; off means the list only
                     shapes the agents' menus.
      (any other key)  an OPTION VALUE, and it must be a string.  The option name must
                     be one the resolved provider's `options` declares; what the value
                     MEANS is the agent pack's derive.lua's business (for the shipped
                     packs, `model` names an alias of the provider's `models` table).
                     Omit a key to leave that option at its declared default; a null
                     here is refused, not read as a delete.  A provider that declares
                     NO options imposes no schema at all — an undeclared option name
                     is refused only once the provider declares at least one.
    A name both sides declare is yours to customize: your entry wins per option and
    keeps the pack's provider when it states none.  Declaring a profile does nothing
    until a launch selects it (the `profile` key, or `-p <name>` before the `--`).
    Example: {"zai-fast": {"provider": "zai", "model": "fast"}}

  [bold]profile[/bold] (string, list or object): The profile each agent runs — the
    persistent spelling of `-p`/`--profile`, form for form:
      "profile": "bedrock"                             every agent: -p bedrock
      "profile": {"pi": "codex", "claude": "bedrock"}  per agent: -p pi=codex,claude=bedrock
      "profile": {"*": "bedrock", "pi": "codex"}       "*" is every agent not named:
                                                       -p bedrock -p pi=codex
      "profile": {"pi": ["zai", "openrouter"]}         a list for one agent:
                                                       -p pi=zai,openrouter
      "profile": ["zai", "openrouter"]                 a list for every agent:
                                                       -p zai,openrouter
    An object key is the BINARY a pack installs (`claude`, `pi`, `codex`) and NOT a pack
    or agent name; an unknown key is fatal, naming what is installed.  "*" names no
    CLI, so it cannot collide with one.  The string and list forms and "*" reach every
    CLI the selected packs install that the object does not name, whether or not a command
    follows `--` — the command is never a profile target, so `yolo -- sleep 60` launches
    with the profile active for every CLI the jail installs.  A named agent keeps its
    own entry beside "*", as `-p pi=codex` keeps pi's beside a bare `-p bedrock`.
    A null entry selects NO profile for that agent, so "*" does not reach it; a null
    `profile` selects nothing.  An empty name is refused (null is the spelling of none).
    PRECEDENCE: every `-p` beats this key, form for form — a bare `-p <name>` replaces
    the key's selection for every CLI it reaches, named entries included, and
    `-p <cli>=<name>` replaces that CLI's.
    A value may also be a LIST of profile names, the agent's ACTIVE SET: every listed
    provider is live in one session (its models in the picker, its key delivered to that
    agent alone), and the FIRST entry is where a fresh session starts.  Only an agent whose
    pack declares `provider_sets` holds one (pi, opencode and oh-omp today); a list NAMED at
    any other agent is REFUSED, naming the one-profile spelling: claude, codex and copilot
    run one provider per session.  A list naming no agent — the list form, a list under
    "*", or a bare `-p zai,openrouter` — goes whole to every agent that holds a set and its
    first entry to every other, and the launch names the agents that ignore the rest.
    A list of one is the plain name.  An empty list is refused (null means "none"), as is a
    name listed twice, two entries on one provider, two on one regional platform (two
    Bedrock providers share the agent's one AWS_REGION), and a via profile anywhere but
    first.  Every name must be declared, the entries a bare list's narrowed agents ignore
    included.
    On the command line a comma continues one agent's list: `-p pi=zai,openrouter` (a
    later `-p pi=…` replaces the whole list, as a `-p` pair replaces the key's).  A profile
    name may not contain a comma, and in this key a list is a JSON array, never a comma
    string.
    USER-SCOPE ONLY, like `profiles`: this key is read from the merged config, so a
    workspace spelling would TAKE EFFECT rather than sit inert — it is REFUSED there
    for the same reason `profiles` is (OQ-CS5).
    At `yolo host` it selects for the one command composed: its own entry, else "*" when
    a selected pack installs it.  A profile reaches agent CLIs only, so
    `yolo host -p zai -- curl …` is REFUSED, naming the grant that hands an arbitrary
    command a provider's key, `yolo host --with-credentials zai -- curl …`; an object
    key naming such a command cannot do it either — it is the unknown key above,
    refused at `yolo host` too — and "*" simply does not reach it.
    RENAMED from `use_profiles` (2026-09-29): that key is refused by name, and the
    refusal respells your entries, which the object form takes unchanged.
    Selecting a name nothing declares (pack-shipped or yours) refuses the
    launch rather than selecting nothing — a silently inert selector is
    indistinguishable from a working one.  A selected profile switches ON; deactivating
    it does not write the agent's surface back — whatever a selection wrote stays, and
    the agent's own choice stands.
    AT THE HOST NOTCH `yolo host apply` (and a wrapped launch's automatic apply) writes
    this selection into the agents' real files too — pi's defaultProvider and
    defaultModel, codex's and opencode's model, claude's picker — when the chosen
    profile changes; a later /model pick of yours stands, and deselecting clears only
    what yolo wrote.  A selection the host cannot run is left out and named.  A
    selection whose pairing runs through a pack service (claude on `codex` or
    `cerebras`, through the wire bridge) writes no address anywhere: the service lives
    only for the command that starts it, so the selection takes effect through
    `yolo host -- <agent>` or the host wrappers, which start it, and `yolo host env`
    refuses it.  An agent started any other way runs without it.
    Example: {"*": "bedrock", "pi": "zai-fast", "codex": null}
    Example: {"pi": ["zai", "openrouter"]}

  [bold]required_capabilities[/bold] (array of strings): Named capabilities this
    environment DECLARES it needs, e.g. ["web_search"].  Validated as a string list
    at pre-flight, and passed through to a nested launch (it is one of the keys an
    inner jail inherits).
    ENFORCED: a launch that declares a capability nothing satisfies is REFUSED
    (docs/design/agent-auth-modes.md OQ-CAP2).  A capability is satisfied by a
    declaration — `providers.<name>.capabilities` naming it, an `mcp_servers.<name>`
    entry whose "provides" is it, or a SELECTED agent whose pack declares it for the
    source that agent runs on: its own login when no profile points it elsewhere
    (claude and agy search the web on theirs), or the provider its profile selects
    (a pack's provider counts only there, so `pi` on no profile gets no web search
    from the `openai-codex` provider its pack brings along; your `providers.<name>`
    entry overrides a pack's list, and null removes the provider) — or by the
    baseline every agent meets (code_editing, command_execution), which needs no
    declaration.  A server set to null satisfies nothing: the jail deletes it.  One
    agent's source is enough for the whole launch, and so is any profile of an
    agent's list.  A `providers.<name>.capabilities` YOU write counts whether or not
    a profile selects that provider.
    The refusal runs above the backend dispatch, so it fires on every backend, and
    `yolo check` predicts it.
    YOLO_ALLOW_UNMET_CAPABILITIES=1 launches anyway, loudly.  It is there for a
    capability you really have that nothing declares — an agent whose pack does not
    state what its login does, or a tool it reaches some way yolo does not deliver.
    The key is no longer exported to the jail: nothing in a jail read
    YOLO_REQUIRED_CAPABILITIES, and the check it stood in for now happens on the host
    before the launch.
    Default: [] (declares nothing).
    Example: {"required_capabilities": ["web_search"]}

  [bold]prune[/bold] (object): Disk-usage nudge settings for `yolo check`.  ONE key, and
    the block is host-side only — an in-jail `yolo check` skips the disk section, so a
    threshold written in a jail snapshot does nothing there.
    • [bold]warn_threshold_gb[/bold] (number, [bold]default 15[/bold]): total yolo-jail
      footprint, in GiB, above which `yolo check` warns and points at `yolo prune`.  It
      changes WHEN YOU ARE TOLD, never what `yolo prune` reclaims: every reclaim policy
      is a flag (--image-cache-keep, --cache-age, --nix-gc-max), so nothing else belongs
      under this key and any other sub-key is refused as unknown.
    ⚠ THE BLOCK HAD NO VALIDATOR AT ALL UNTIL 2026-09-16, so `prune: "hello"` and a
    misspelled sub-key were both accepted in silence — and this reference had no section
    for it, which is how it stayed that way: the coverage test that should have caught
    the omission was satisfied by the substring "prune" inside `programs.autoprune`.
    Both halves are fixed; the value is now checked and a typo names itself.
    Example: {"prune": {"warn_threshold_gb": 40}}

  [bold]lsp_servers[/bold] (object): Language servers to hand to the agents that read them.
    No defaults — declare each server you want. Its binary must be on PATH (via
    mise_tools, a pack program, or an absolute path).
    Each key is a server name; value is an object with:
      • command (string, required): Binary name (on PATH) or absolute path.
      • args (array of strings): Args passed to the LSP binary. Default: [].
      • fileExtensions (object): Extension → language ID map (required for Copilot).
    The entrypoint translates these for each agent:
      • Copilot: written to ~/.copilot/lsp-config.json as native LSP servers.
      • Claude Code: the launcher renders ONE generated plugin, yolo-lsp, from the
        whole table into the skills tree Claude loads plugins from.
    yolo installs no language server itself, on any backend.
    At the host notch `yolo host apply` writes the same translation into your real
    home from your USER config, less any server naming a path only a jail has.
    Example: {"rust": {"command": "rust-analyzer", "args": [],
              "fileExtensions": {".rs": "rust"}}}

  [bold]mcp_presets[/bold] (array of strings): Enable built-in MCP server presets by name.
    No presets are enabled by default. Available presets:
      • chrome-devtools: Headless Chromium automation via Chrome DevTools Protocol.
      • sequential-thinking: Chain-of-thought reasoning via MCP.
    Invalid: enabling a preset here and null-removing it in the same config file.
    Jail only: a preset's command is a wrapper a jail's boot writes, so `yolo host
    apply` writes no preset into your real home and names each one it leaves out.
    Example: ["chrome-devtools", "sequential-thinking"]

  [bold]mcp_servers[/bold] (object): Custom MCP servers for Copilot, Claude, and Codex.
    Add custom servers, or set a preset/inherited server to [bold]null[/bold] to disable it.
    Each key is a server name; value is an object with:
      • command (string, required): Binary name (on PATH) or absolute path.
      • args (array of strings): Args passed to the MCP server. Default: [].
      • env (object of string→string): Environment variables passed only to
        this MCP server's process. Use for per-server secrets and config so
        they don't leak into the jail-wide env. Default: {}.
        [bold]${VAR}[/bold] references are expanded against the jail's startup env
        (after [bold]env_sources[/bold] is loaded), so a secret can live in one
        unsynced file and be scoped to a single server. Undefined names
        are left as the literal [bold]${VAR}[/bold] and logged as a warning.
      • provides (string): the named JOB this server implements, e.g.
        "web_search".  Two things read it, and they are different questions.
        DELIVERY: the authentication source your launch resolves to — the
        provider a profile selects, or the agent's own built-in login — omits
        this server when it already does that job, so a search MCP is delivered
        on a gateway that has no native search and dropped on one that does.
        REQUIREMENT: it also satisfies a `required_capabilities` entry naming
        it.  Two servers declaring one name refuse the launch: which one
        implements the job is not something to pick at random.  Optional; a
        server without it makes no claim and is always delivered.
      • requires_env (array of strings): Conditional loading gate. The
        server is only configured when every listed variable is set
        (and non-empty) in the jail's startup env. If any is missing,
        the server is skipped with a notice — not an error. Lets a
        dotfiles-shared user config declare machine-dependent servers
        that activate only where env_sources provides the keys. It is
        asked per agent: a variable a provider claims (its
        api_key_env_name) reaches only the agent whose profile selected
        that provider, so the server is configured for that agent only.
        Example:
          {"tavily": {
            "command": "npx", "args": ["-y", "tavily-mcp"],
            "env": {"TAVILY_API_KEY": "${TAVILY_API_KEY}"},
            "requires_env": ["TAVILY_API_KEY"]
          }}
    The entrypoint translates these for each SELECTED agent:
      • Copilot: written to a per-workspace overlay mounted at ~/.copilot/mcp-config.json.
      • Claude: written to a per-workspace overlay mounted at ~/.claude/settings.json.
      • opencode: written to ~/.config/opencode/opencode.json (mcp key, native schema).
      • codex: written to ~/.codex/config.toml (\\[mcp_servers.<name>] tables).
      • pi: no native MCP support (skipped).
    AT THE HOST NOTCH the same translation is written into your real home by
    `yolo host apply` (and a wrapped launch's automatic apply), from this key in your
    USER config: every selected agent's MCP file gets these servers, as in a jail.
    A server whose command or arguments name a path only a jail has (/workspace,
    /home/agent, /ctx, …) is left out and named, and `requires_env` is asked of the
    environment `yolo host env --agent <agent>` composes for each agent.  To give one
    host agent a server the others should not get, add a `config-overlay` for that
    agent's surface to your local pack (~/.config/yolo-jail/local/pack.json).
    Example:
      {"cerebras-mcp": {
        "command": "npx", "args": ["-y", "cerebras-code-mcp"],
        "env": {"CEREBRAS_API_KEY": "csk-...", "CEREBRAS_MCP_IDE": "claude"}
      }}

  [bold]devices[/bold] (array): Host devices to pass through to the jail.
    Three formats supported:
    • USB by vendor:product ID (preferred — stable across reboots):
      {"usb": "0bda:2838", "description": "RTL-SDR Blog V4"}
      Resolved to /dev/bus/usb/... at startup via lsusb.
    • Raw device path (fragile — changes on replug):
      "/dev/bus/usb/001/004"
    • Cgroup rule (broad access):
      {"cgroup_rule": "c 189:* rwm"}
      Grants access to all devices matching the major number.
    Missing devices produce a warning, not an error — the jail still starts.
    Subject to config change safety (human approval required).

  [bold]gpu[/bold] (object): GPU passthrough configuration (NVIDIA / AMD ROCm).
    NVIDIA (default) uses the NVIDIA Container Toolkit on the host (podman +
    CDI). AMD ROCm defaults to raw device-node passthrough and needs no host
    toolkit — just the amdgpu kernel driver.
    • [bold]enabled[/bold] (bool): Enable GPU passthrough. Default: false.
      If true but the host lacks drivers/CDI (e.g. laptop without a
      GPU), yolo prints a one-line warning and starts without
      GPU passthrough — so the same config can be committed and used
      on both a GPU box and a GPU-less machine.
    • [bold]vendor[/bold] (string): GPU vendor. Default: "nvidia".
      Values: "nvidia" or "amd".  Absent ⇒ "nvidia" (backward compatible).
    • [bold]devices[/bold] (string): Which GPUs to expose. Default: "all".
      Values: "all", "0", "0,1", or "GPU-<uuid>".
      NVIDIA: mapped to CDI device entries (nvidia.com/gpu=...).
      AMD: mapped to /dev/dri/renderD<N> nodes (or amd.com/gpu=... in cdi mode).
    • [bold]mode[/bold] (string): AMD only. Default: "devices".
      Values: "devices" (raw /dev/kfd + /dev/dri render nodes, no host
      toolkit) or "cdi" (amd.com/gpu=... via the AMD Container Toolkit).
      Rejected for vendor="nvidia".
    • [bold]capabilities[/bold] (string): NVIDIA only. Default: "compute,utility".
      Valid: compute, utility, graphics, video, display, compat32.
      "compute,utility" is sufficient for PyTorch/CUDA training.
      Rejected for vendor="amd" (ROCm has no driver-capabilities concept).
    • [bold]hsa_override_gfx_version[/bold] (string): AMD only, optional.
      Sets HSA_OVERRIDE_GFX_VERSION inside the jail to make ROCm treat an
      unsupported/consumer GPU as a known gfx target (e.g. "11.0.0" → gfx1100,
      "10.3.0" → gfx1030). Best-effort, same-architecture-family only.
    • [bold]seccomp_unconfined[/bold] (bool): AMD only, optional. Default: false.
      Opt-in --security-opt seccomp=unconfined (enables memory mapping for
      some HPC/numactl workloads). Removes syscall filtering — leave off
      unless a workload actually needs it.
    • [bold]vaapi[/bold] (bool): AMD only, optional. Default: false.
      VA-API video encode/decode acceleration. Bakes mesa (radeonsi VA
      driver) + libva-utils (vainfo) into the image and sets
      LIBVA_DRIVERS_PATH inside the jail. Requires enabled=true and
      vendor="amd" — device nodes and the render group come from the
      regular AMD passthrough. Adds ~1 GB to the image (mesa pulls LLVM),
      which is why it's opt-in. Verify in-jail with: vainfo

    NVIDIA host prerequisites (on the GPU machine):
      1. NVIDIA driver installed (nvidia-smi works)
      2. nvidia-container-toolkit installed
      3. sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml

    AMD ROCm host prerequisites (on the GPU machine):
      1. amdgpu kernel driver installed (amdgpu-dkms) and /dev/kfd present
      2. Host user in the group owning /dev/kfd + /dev/dri/renderD*
         (usually 'render'; some distros ship them world-writable)
      3. (cdi mode only) sudo amd-ctk cdi generate --output=/etc/cdi/amd.json
      ROCm userspace (HIP, rocm-smi) lives in the image, not on the host —
      use a rocm/* base image for working compute.
    When GPU passthrough is active, yolo lifts the container's locked-memory
    soft limit to the host hard cap ([cyan]--ulimit memlock=<host-hard>[/cyan])
    so the GPU runtime can pin device queue buffers.  Current ROCm (7.2+) runs
    fine at the common 8 MB rootless cap — no host change needed.
    Run [bold]yolo check[/bold] to verify GPU readiness on a given host.
    Subject to config change safety (human approval required).

  [bold]kvm[/bold] (boolean, default false): Expose /dev/kvm inside the jail.
    When true, yolo adds [cyan]--device /dev/kvm[/cyan] to the container run
    command plus [cyan]--group-add keep-groups[/cyan] so the in-jail user
    inherits the host's kvm-group membership (podman).
    Enables nested hardware-accelerated VMs inside the jail (QEMU,
    firecracker, Android emulator, kernel dev workflows).  Runs full-speed
    virtualization via KVM instead of falling back to software emulation.
    Host prerequisites (verified by [bold]yolo check[/bold] when enabled):
      1. CPU virtualization extensions enabled in firmware (VT-x / AMD-V)
      2. kvm kernel module loaded ([cyan]modprobe kvm_intel[/cyan] or [cyan]kvm_amd[/cyan])
      3. Your host user is a member of the kvm group
    Not supported on macOS (Apple hosts use the VZ framework) or on the
    Apple Container runtime (no device passthrough).  Skipped with a warn
    when /dev/kvm is absent on a Linux host.
    [yellow]Security note:[/yellow] /dev/kvm is a kernel hypervisor interface.
    The attack surface is narrow — historical CVEs have mostly been
    guest-to-host escape bugs requiring attacker code in a KVM guest —
    but it is strictly larger than no-kvm.  Leave this off unless you
    actually need nested virtualization.

  [bold]programs[/bold] (object, [bold]USER SCOPE ONLY[/bold]): What a launch does about
    programs nothing declares any more.
    • [bold]autoprune[/bold] (boolean, [bold]default false[/bold]): Remove orphans at boot.
      An ORPHAN is something installed in this jail's per-workspace home that no
      selected pack or MCP preset declares — what a dropped pack left behind.
      Every boot already NAMES them ("boot catalog: ..." lines, with sizes);
      nothing removes them unless you set this.
      With it on, each launch removes what it cataloged, printing every path first.
      [yellow]It is destructive and it runs with nobody present.[/yellow] ~/.local/bin
      is also where YOU may have put things, and yolo cannot tell a tool you installed
      by hand from a dropped pack's leftovers — both are "installed and undeclared".
      Look before you enable it:
        yolo programs ls              # in the jail: the orphans and their sizes
        yolo programs remove          # what removing them would unlink (a dry run)
        yolo programs remove --apply  # do it once, by hand, instead of every boot
      Workspace configs cannot set this. A repo-committed, agent-editable file must
      not be able to authorise deleting your programs; a workspace-scoped `programs`
      is a validation error, not a silent no-op.
      Container backends only (the boot catalog it hangs off does not run under
      macos-user, which stages no pack tree to compare against).

  [bold]resources[/bold] (object): Container resource limits.
    Sets hard cgroup constraints on the jail container via podman flags.
    memory, cpus and pids_limit are enforced by the kernel — the jail cannot exceed them.
    io is not a limit, and is described on its own below.
    • [bold]memory[/bold] (string): Maximum memory. Format: number + suffix (b/k/m/g).
      Examples: "8g" (8 GB), "512m" (512 MB), "2g".
      Maps to --memory flag. OOM-killed if exceeded.
    • [bold]cpus[/bold] (number|string): CPU limit as a decimal. Default: no limit.
      Examples: 4 (four cores), 2.5 (two and a half cores), "0.5" (half a core).
      Maps to --cpus flag (CFS quota).
    • [bold]pids_limit[/bold] (integer): Maximum number of processes. Default: 32768 (Podman's built-in default of 2048 is too low for agent workloads).
      Prevents fork bombs and runaway process creation.
      Maps to --pids-limit flag.
    • [bold]io[/bold] (string|object): Disk I/O priority for every process in the jail, so a
      build yields the disk to your desktop when both want it. Default: "normal".
      "low" is best effort, level 7; "idle" is the idle class; "normal" sets nothing and
      keeps the priority the launching process has. "io": "low" is shorthand for
      "io": {"priority": "low"}, and priority is the only key the object takes.
      Examples: "io": "low" (the one to start with), "io": "idle" (a build can crawl
      while your desktop reads the disk).
      ADVISORY, NOT A LIMIT: any process can raise its own priority again, and the
      priority reaches reads and synchronous writes but not buffered writeback, which
      is most of a build's output. Only the bfq and mq-deadline disk schedulers honor
      it, and mq-deadline honors "idle" only; kyber and none, the usual NVMe default,
      ignore it. The launch prints one line when the disk under the workspace ignores
      the value, and `yolo check` grades that disk and names the host change.
      A `nix build` runs its builders in the host nix daemon, outside the jail, so it
      keeps that daemon's priority.
      Applied on podman on Linux, nested jails included. Not applied on Apple
      Container or podman on macOS, where the workspace reaches the Mac over VirtioFS,
      which carries no priority, nor yet on macos-user; the launch says so on all
      three. Frozen at the fresh launch, like every resources key.

    [bold]In-jail sub-process limits (cgroup v2 delegation)[/bold]:
    A host-side cgroup delegate runs alongside the container and performs all
    privileged cgroup operations on behalf of agents inside the jail.  No
    CAP_SYS_ADMIN or writable cgroup mount is needed inside the container — it
    validates every request and operates on the host cgroup filesystem via a
    Unix socket.
    [bold]OPT-IN since 2026-08-18[/bold] — two lines in your USER config, and
    until you write them yolo-cglimit reports that it is not wired up:
      "packs": ["cgroup-delegate"],
      "loopholes": { "cgroup-delegate": { "enabled": true } }
    Then, inside the jail:
      yolo-cglimit --cpu 75 -- python train.py           # 75% of all CPUs
      yolo-cglimit --cpu 50 --memory 2g -- make -j8      # 50% CPU + 2GB RAM
      yolo-cglimit --pids 100 -- ./script.sh             # Max 100 processes
    It used to start whenever the platform allowed it, with no config key at
    all — which is the "presence activates" default the loophole rules delete.
    Podman is the primary supported runtime.
    Falls back to nice/timeout/ulimit if delegation is unavailable.
    Subject to config change safety (human approval required).

  [bold]ephemeral_storage[/bold] (string, default "volume"): Backing for /tmp,
    /var/tmp, and /var/lib/containers inside the jail.
    The container rootfs is mounted [cyan]--read-only[/cyan], so these scratch
    paths need explicit writable mounts. Two modes:
      • "volume" (default) — podman volumes, disk-backed, one set per
        launch. Deleted in the background after the jail exits, so quitting
        never waits for the delete; a set a crashed launcher left behind is
        removed by the next launch or [cyan]yolo prune --apply[/cyan], and
        [cyan]yolo stores[/cyan] lists them. Doesn't compete with the jail's
        memory budget. Recommended for workloads that touch large temp files
        (builds, model downloads).
      • "tmpfs" — RAM-backed scratch. Faster reads/writes, but counts
        against host free memory and can OOM the jail under pressure.
    /run and /dev/shm always stay on tmpfs in either mode (small + shared
    memory, respectively). Apple Container always uses tmpfs (its volume
    syntax differs and isn't a drop-in replacement).

  [bold]macos_log[/bold] (string, default "off"): Apple unified-log access, through a
    generated [cyan]yolo-log[/cyan] helper.  [bold]macos-user backend only.[/bold]
    The macOS analog of the Linux jail's [cyan]yolo-journalctl[/cyan], and a much
    smaller thing than it: there is no loophole, no host daemon and no bridge here —
    the sandbox account runs the machine's own [cyan]/usr/bin/log[/cyan].  This key
    decides only what the helper installed at [cyan]~/.local/bin/yolo-log[/cyan] does.
      • "off" (default) — the helper is a stub: it prints how to turn logging on
        and exits 1.
      • "user" — the helper wraps [cyan]log[/cyan].  Bare, it shows the last five
        minutes compact; the [cyan]show[/cyan], [cyan]stream[/cyan], [cyan]collect[/cyan],
        [cyan]config[/cyan] and [cyan]help[/cyan] subcommands pass straight through;
        anything else becomes arguments to [cyan]log show[/cyan].
      • "full" — the helper is [cyan]log[/cyan], argv for argv.
    [yellow]It is a convenience, not a boundary.[/yellow] The Seatbelt profile is
    [cyan](allow default)[/cyan] plus targeted write and read denials, and none of them
    cover exec: an agent under "off" can still run [cyan]/usr/bin/log[/cyan] itself.
    So "off" makes the helper refuse — it does not make the log unreadable.  Do not
    read this key as a permission.
    On [cyan]podman[/cyan] and [cyan]container[/cyan] the key is inert (nothing there
    reads it), the same way [bold]kvm[/bold] is inert on macOS — declared so one config
    file can serve both of your machines.

[bold cyan]CONFIG CHANGE SAFETY[/bold cyan]

  When yolo-jail.jsonc changes between jail startups, the CLI shows a
  diff of the normalized config and asks for y/N confirmation. This
  prevents agents from silently adding packages or mounts without the
  human operator noticing. Agents should still run `yolo check` after
  every config edit before asking for that restart.

  - First run: config is accepted and a snapshot saved.
  - Subsequent runs: changes require explicit y/N approval.
  - Non-interactive (piped input, CI): the launch is REFUSED. Approve
    the change for that one launch with `yolo --accept-config-changes`,
    which records it exactly as answering y would. A flag rather than an
    environment variable, so an approval is never inherited by a child
    process or left behind in a shell.

  Snapshot location: ~/.local/share/yolo-jail/approvals/<container>.json
  (HOST-side, never mounted into the jail — a record an agent could
  rewrite is not a record).

[bold cyan]AGENT PACKAGE WORKFLOW[/bold cyan]

  Agents inside the jail can request new packages:

  1. Agent edits /workspace/yolo-jail.jsonc, adds to "packages" array
  2. Agent ALWAYS runs `yolo check` after the edit (`--no-build` is okay inside a running jail)
  3. If the check passes, agent tells the human: "Please restart the jail for new packages"
  4. On next startup, human sees the config diff and approves (y/N)
  5. Image rebuilds with the new package
  6. Agent can use the package after restart

  This keeps the human in the loop for all environment changes.
  Do NOT install packages via apt, nix-env, or other package managers.

[bold cyan]INSIDE THE JAIL[/bold cyan]

  [bold]Workspace[/bold]
    Your project is bind-mounted read-write at /workspace.
    Edits are visible on the host immediately — this is the SAME directory.
    The workspace path changes from the host path to /workspace.

  [bold]Networking[/bold]
    Full internet access, outbound and unrestricted.
    Bridge mode (default) gives the jail its own network namespace, so
    `localhost` in here is the JAIL's loopback.  The host is reached by NAME at
    `host.containers.internal` — no config needed, and it covers host services
    bound to the host's own 127.0.0.1.
    To go the other way and let the HOST reach a server running in here, publish
    it with network.ports ("HOST:JAIL").  To make a host port answer at
    `localhost:<port>` in here specifically, network.forward_host_ports
    ("JAIL:HOST" — the opposite order; see "NETWORKING: WHICH WAY IS WHICH").
    Host mode shares the host's network stack: the two loopbacks become one and
    neither key is needed.

  [bold]Home Directory (/home/agent)[/bold]
    Composed at every launch, not one directory. Most of it is the
    workspace's own overlay (<workspace>/.yolo/home): npm/go globals, shell
    and agent state, sessions. It survives restarts of that workspace's jail
    and is not seen by any other. Shared by every jail on the machine: each
    selected pack's shared dirs, the cache at ~/.cache, and mise tool data
    at /mise. No host credential is mounted unless your config grants it.

  [bold]Per-Workspace State[/bold]
    Some state is isolated per-workspace (in <workspace>/.yolo/):
    SSH keys, bash history, copilot sessions, claude projects.
    These are NOT shared across different project jails.

  [bold]Identity & Auth[/bold]
    Git identity (name + email) is injected from the host automatically.
    GitHub CLI (gh) is not signed in: the host's gh token does not cross
    into the jail. Give gh a credential of its own if the work needs it
    (e.g. GH_TOKEN through env_sources, or `gh auth login` in the jail).
    SSH keys are per-workspace — configure in <workspace>/.yolo/home/ssh/.

  [bold]Tools & Runtimes[/bold]
    Runtimes: Node.js 22, Python 3.13, Go (managed by mise)
    Editors:  nvim (version configurable via mise_tools config)
    CLI:      rg, fd, bat, jq, git, gh, curl, strace, uv, tmux
    Agents:   whichever ones your configured `packs` install — each with
              auto-approve/YOLO mode wired up.  With no packs configured a jail
              has no agent, and says so at launch.
    The 'yolo' command is available inside for nested jailing and help.

  [bold]Mise Tool Management[/bold]
    Mise manages all runtimes and supports thousands of tools from
    multiple registries:
    • aqua — pre-built binaries (kubectl, terraform, gh, etc.)
    • asdf — version-managed runtimes (python, node, ruby, etc.)
    • cargo — Rust crates (ripgrep, fd-find, bat, etc.)
    • go — Go modules (built from source)
    • npm — Node packages (installed globally)
    • pipx — Python CLI tools (isolated envs)
    • ubi — universal binary installer (GitHub releases)
    Run 'mise registry' to browse all available tools. Add tools via:
    • "mise_tools" in yolo-jail.jsonc (injected into jail global config)
    • /workspace/mise.toml (workspace-specific, checked into git)
    All jails share one jail-land mise store, mounted at /mise — a tool
    installed in one jail is available in every jail. The host's own mise
    installation is fully independent; installs never cross the boundary.

  [bold]Blocked Tools[/bold]
    NOTHING is blocked by default. Blocking is opt-in, two ways:
    • the "guardrails" pack — add it to "packs" and grep -r / find are
      replaced by rg / fd (this is where the old default went, 2026-09-04)
    • security.blocked_tools in yolo-jail.jsonc — your own list, and an
      entry naming the same tool as a pack's REPLACES it whole
    A blocker also declares a replacement, and is generated only when that
    replacement is on the agent's PATH — so a block can never leave a jail
    with neither the tool nor its alternative. The old unconditional default
    assumed the image bakes rg and fd, which is false on the macos-user
    backend: it bakes nothing, so the block removed a tool and pointed at a
    binary that did not exist.
    Once generated, a blocker is unconditional at run time — set
    YOLO_BYPASS_SHIMS=1 for installers and scripts that need the real tool.

  [bold]Venvs & Python[/bold]
    Venvs are per side: /workspace/.venv (plus any venv path configured in
    mise.toml and any per_side_paths entries) is shadow-mounted over a
    per-workspace backing dir, so the host and the jail each keep their own
    venv at the same idiomatic path. The jail's venv is created on first
    boot and persists across restarts; host venvs never leak in, and
    jail-built native extensions never leak out. The lockfile
    (uv.lock/requirements) in the shared workspace is the sync channel.

  [bold]Persistence Summary[/bold]
    Shared home:   /home/agent (same across all jails — auth, tools, caches)
    Workspace:     /workspace edits visible on host immediately
    Per-workspace: SSH keys, bash history, copilot sessions
    Ephemeral:     /tmp, container processes

[bold cyan]SPAWNING A NEW PROJECT[/bold cyan]

  When setting up a new project for jail use:

  1. Run 'yolo init' in the project root to create yolo-jail.jsonc
  2. Edit the config — add any nix packages or mise_tools needed
  3. Run 'yolo check' after EVERY config edit to validate the config before restarting
  4. Run 'yolo -- bash' to enter the jail interactively
  5. Start your agent: 'yolo -- claude' (or copilot / opencode / pi / codex,
     whichever your configured `packs` install)

  [bold]For agents preparing to enter a jail:[/bold]
  Before asking the human to restart you inside the jail, ALWAYS run 'yolo check'
  and write a
  handoff document (e.g., scratch/jail-notes.md) with:
  • Current task state and what remains to be done
  • Decisions made and their rationale
  • Key files to examine first
  Your inner-jail self will be a fresh session without your context.
