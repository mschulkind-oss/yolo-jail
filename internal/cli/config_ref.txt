[bold]YOLO Jail Configuration Reference[/bold]

[bold cyan]CONFIG FILE: yolo-jail.toml[/bold cyan]

  Config files are TOML.  Every example in this reference is TOML.  yolo still
  reads the legacy JSONC files for a few releases, until that format is
  deleted.  [bold]LEGACY JSONC FORMAT[/bold], near the end, gives the old spelling of
  every key.  `yolo check` and every launch say when a file is in the old
  format, and `yolo config migrate` converts it.

  Project file:    yolo-jail.toml in the project root (committed)
  Local overrides: yolo-jail.local.toml beside it (this machine; merged
                   automatically when it exists; keep it out of git)
  Your defaults:   ~/.config/yolo-jail/config.toml, plus every
                   ~/.config/yolo-jail/config.d/*.toml fragment
  Legacy names:    yolo-jail.jsonc, yolo-jail.local.jsonc and
                   ~/.config/yolo-jail/config.jsonc (or .json); see LEGACY JSONC FORMAT.

  [bold]THE WORKSPACE IS THE DIRECTORY YOU RUN `yolo` IN[/bold], and it is
  bind-mounted [bold]read-write and LIVE[/bold] at [bold]/workspace[/bold].
  `cd ~/code/sysadmin && yolo` makes ~/code/sysadmin *be* /workspace — the same
  files, not a copy, with no sync step in either direction.  It does NOT appear
  under /ctx/, and it must NOT be listed in `mounts`: that key is for paths
  OUTSIDE the workspace, and it is read-only unless an entry says otherwise.
  It is literally the cwd — there is no `--workspace` flag and no walk up the
  tree looking for yolo-jail.toml.  Launch from a subdirectory and THAT
  subdirectory is the whole workspace, with its own config and its own jail.

  Workspace config merges over user defaults; a sibling
  `yolo-jail.local.toml` merges over the workspace config automatically —
  no include_if_found entry needed. Keep it out of git (global gitignore)
  for per-machine tweaks that don't belong in the tracked config.
  Lists are merged and deduplicated. Scalars override.

  [bold yellow]Rule:[/bold yellow] After [bold]EVERY[/bold] edit to `yolo-jail.toml`,
  `yolo-jail.local.toml`, `~/.config/yolo-jail/config.toml` (or a legacy
  `.jsonc` file), run
  `yolo check` before restarting or asking a human to restart the jail.
  Use `yolo check --no-build` inside a running jail for a faster preflight.

  A refusal or warning about a key starts with where the key is written, as
  `<file>:<line>:<column>: config.<key>: …`, the column being where its value
  starts (a list entry at the entry's own line): the file whose value takes
  effect.  Any other file writing the same key is named after the message,
  "(also written at …)".

[bold cyan]THE TOML FORMAT[/bold cyan]

  Files: `yolo-jail.toml` (project, committed), `yolo-jail.local.toml` (this
  machine, not committed) and `~/.config/yolo-jail/config.toml` (yours).  A
  project needs no file to run.  `yolo init` writes a three-line pointer file.
  One format per scope: a TOML file beside a legacy file of the same scope is a
  `yolo check` error, so convert both together with [bold]yolo config migrate[/bold].

  Most keys sit at the top level of the file under their own name.  A few
  live in tables: [install] (nix packages and mise tools), [machine] (gpu,
  resources, ports, forward), [env], [allow], [requests] and [active_provider].  Each
  key's entry under FIELDS shows its TOML spelling.

  A higher file can drop what a lower file wrote.  TOML has no null, so each
  kind of value has its own way to say "none":
    a list (install.nix, security.blocked_tools, env.sources ...) takes an empty
                           list, e.g. [security] blocked_tools = []
    one server or tool takes "off": mcp_servers.<name> = "off",
                           lsp_servers.<name> = "off", [install] mise.<tool> = "off"
    an agent's provider takes "native": active_provider.<agent> = "native"
  `yolo config migrate` and a jail's inherited config write exactly these.

  [bold]allow[/bold] — (table, [bold]USER SCOPE ONLY[/bold]): what a project's jail may do with your
    logins and your host's loopholes.  `[allow.<pack>]` takes `always = [...]`
    (every project's jail gets it, each project's next prompt showing it once)
    and `on_request = [...]` (a project may ask for it; it is never granted by
    this line).  Capabilities are the ones the selected pack declares: for git
    and github `fetch`, `push`, `new_branches`, `create_pr`; for a loophole its
    grant kinds, such as `[allow.journal] always = ["read"]` or
    `[allow.host-processes] on_request = ["view"]`.  A kind that carries values
    (process names, device patterns) is allowed on request only.  A pack's own
    settings live under `[allow.<pack>]` as well.  `[allow.mounts]
    on_request = ["write"]` lets a project request a writable mount.  Edit with
    [bold]yolo allow <source> [always|on_request] <capability>[/bold], on the host; it offers
    this workspace's approval of the change through `yolo config apply`.

  [bold]requests[/bold] — (table, [bold]WORKSPACE SCOPE[/bold]): what this project asks for within your
    `allow` ceiling: `[requests.git]` `push = ["main"]`, `push_tags`,
    `new_branches = true`; `[requests.github]` `repos = ["acme/other"]`,
    `create_pr`, `create_issue`, `runs = ["nightly.yml"]` (run and re-run
    that workflow on the default branch only, and cancel any run; `"*"` for
    every workflow),
    `approve_runs = ["github-actions[bot]"]` (approve a held workflow run that
    login triggered from this repository itself, never a fork's; `"*"` for
    every actor); for a
    loophole, `[requests.journal] read = true` or
    `[requests.host-processes] view = ["postgres"]`.  A request is a grant
    once approved (`yolo config apply`, or y at the launch prompt).  A
    request your ceiling does not allow is reported and skipped, never an
    error.  A `requests` table in a legacy JSONC user config is refused.  Edit with
    [bold]yolo request <source> <capability> [resource][/bold], which writes the project's
    file, runs `yolo check`, and names the host step (`yolo config apply`).

  [bold]active_provider[/bold] — (table, [bold]USER SCOPE ONLY[/bold]): which provider each agent runs on.
    `claude = "bedrock"`, `claude = "bedrock/opus"` (a variant), `default = ...`
    for every agent the table does not name, and `"native"` to leave an agent
    to its own login (a legacy null under active_provider reads as "native").  The name must be one a selected pack declares.  Edit with
    [bold]yolo active-provider <agent|default> <provider|provider/variant|native>[/bold];
    it takes effect at the next launch.

  [bold]setup[/bold], [bold]setups[/bold] — ([bold]USER SCOPE ONLY[/bold]): `setup = "seatbelt-self"` names
    your default setup (where the agent runs); `[setups.<name>]` defines one of
    your own with `confinement` and `run_as`.  A project file holding either is
    an error.  Copy a setup into a new table with [bold]yolo setup new <name> --from <setup>[/bold];
    set your default with `yolo config set setup <name> --user`.  See `setup`
    and `setups` under FIELDS.

  [bold]mounts[/bold] (list of paths or tables): `"~/data"` lands at /ctx/data, read-only;
    `{ host = "~/x", at = "/ctx/x" }` names the destination; `write = true` asks
    for a writable mount, which needs `[allow.mounts] on_request = ["write"]` in
    your user config and is approved, in red, at the config-change prompt (see
    `mounts` below).

  [bold]env[/bold] — (table): `files = [...]` (env files to load), `set = { NAME = "value" }`
    and `unset = ["NAME"]`.  A variable is removed with `unset`, never by a
    magic value, because any string is a legal value.

  [bold]packs[/bold]: `packs = ["claude", "local/matt", { git = "https://..." }]`, user scope
    only.  Edit with [bold]yolo pack add <name>[/bold] and [bold]yolo pack remove <name>[/bold]
    (host); `yolo pack ls` lists what is available.  See `packs` and
    `pack_sources` under FIELDS.

  Pack manifests have a TOML spelling too: a pack directory's `pack.toml`
  (`yolo pack migrate <path>` rewrites a local pack's `pack.json`).  In it,
  `install = false` (or `install = { default = false, ... }`, or
  `install.<manager> = false`) is no install hint, `options.<name> = false`
  declares a provider option with no default, and a config surface's
  `unset = ["/pointer"]` lists the keys its managed patch deletes.

  Inspecting and editing, in either format:

    yolo config why <key>      the effective value, every file and line that sets
                               it, and what would apply without it
    yolo config set|add|unset <key> [value] [--user|--project|--local]
                               one typed edit, with the splice that keeps comments
    yolo config migrate        convert old files to TOML once, proving equality
    yolo config drift|dump|apply   as described below

[bold cyan]USER SCOPE INSIDE A JAIL[/bold cyan]

  What a jail sees as `~/.config/yolo-jail/config.toml` is [bold]GENERATED[/bold] at
  launch — not your real file. It is your effective config filtered down to the
  keys the commands in a jail can actually judge, with a header saying so.
  The launch writes the legacy `config.jsonc` instead, and says why, in two
  cases: the jail's home already holds a legacy file of that name, or a value
  in your legacy files has no TOML spelling.

  Two consequences worth knowing:

  • [bold]Keys are missing on purpose.[/bold] Anything whose referent does not exist in
    a container (`machine.gpu`, `devices`, `kvm`, `mounts`, `cache_relocations`) or whose
    meaning would change (`host_files` — "the host home" is the jail's own home in
    there) is filtered out. Evaluating them in a jail reported problems you do not
    have. Your host config is untouched.
  • [bold]It is frozen at launch.[/bold] Editing your user config on the host applies to
    the NEXT jail, not the running one. `yolo config drift` covers the workspace
    config and says so; `yolo config dump` prints the effective config a jail is
    actually running under.

  A jail that can nest also gets `inherited-launch.toml` beside it (or
  `inherited-launch.jsonc`, in the same two cases): the keys an inner `yolo`
  composes a nested jail from (`install.nix`, `packs`, mise tools, resources).
  On a backend that cannot nest, that file is simply not written.

  [bold]--user-layer <file>[/bold] (a global CLI flag, not a config key) layers a config
  file in at user-level precedence for one invocation.  A `.toml` file is read
  as TOML; any other name is read as legacy JSONC.  It is inert unless passed,
  and a workspace config still wins over it. Inside a jail it is how you grant
  yourself more than you inherited — e.g. add a `packs` entry naming a pack that
  ships a loophole, then `yolo pack install` and launch a nested jail. There is
  deliberately no conventionally-named auto-merged file: a file that takes effect
  because it exists is invisible at the call site.

  Developing a loophole inside a jail, end to end:

    mkdir -p ~/.local/share/mypacks/mypack/loopholes/mine   # NOT ~/mypacks — the
                                                            # home ROOT is read-only
    ...write pack.toml and loopholes/mine/loophole.toml...
    cat > ~/.config/yolo-jail/my-layer.toml <<'EOF'
    packs = ["mine/mypack"]
    [pack_sources.mine]
    path = "~/.local/share/mypacks"
    EOF
    yolo --user-layer ~/.config/yolo-jail/my-layer.toml pack install
    yolo --user-layer ~/.config/yolo-jail/my-layer.toml loopholes list
    yolo --user-layer ~/.config/yolo-jail/my-layer.toml -- bash

  The layer lands beside the read-only inherited config because ~/.config is the
  jail's own writable dir — that is why the inherited file is delivered as a
  single file rather than by mounting the directory.

[bold cyan]FIELDS[/bold cyan]

  [bold]confinement[/bold]: [bold yellow]REMOVED[/bold yellow] — a config carrying it is REFUSED.  A named
    [bold]setup[/bold] chooses where an agent runs now (`yolo setup list` shows them).
    `yolo config migrate` drops "jail" from your user file (an unset `setup` is
    the same default); every other value is refused naming its setup and the
    unset: "guest" was seatbelt-yolo-account on macOS,
      yolo config set setup seatbelt-yolo-account --user
      yolo config unset confinement --user
    and "host" is `yolo host -- <cmd>`, never a default.  A project file's
    `confinement` chose nothing a project may choose; remove it with
    `yolo config unset confinement --project`.

  [bold]runtime[/bold]: [bold yellow]REMOVED[/bold yellow] — a config carrying it is REFUSED.  A named
    [bold]setup[/bold] chooses the mechanism now (`yolo setup list` shows them).
    `yolo config migrate` converts your user file's value: "podman" becomes
    `setup = "podman-self"` and "container" `setup = "apple-container-self"`.
    "macos-user" is refused naming both Seatbelt setups:
      yolo config set setup seatbelt-yolo-account --user
      yolo config set setup seatbelt-self --user
    A project file's `runtime` chose nothing a project may choose; remove it
    with `yolo config unset runtime --project`.  YOLO_RUNTIME is removed too,
    and a launch refuses it naming YOLO_SETUP.

  [bold]setup[/bold] (string, [bold]USER SCOPE ONLY[/bold]): Your default setup — the one name that
    chooses where an agent runs.  A built-in is named <confinement>-<run_as>:
    podman-self, apple-container-self, seatbelt-self, seatbelt-yolo-account,
    landlock-self, landlock-yolo-account, host-self, host-yolo-account; or name
    one of your own [bold]setups[/bold].  The launch takes `--setup`, then YOLO_SETUP,
    then this key, then this OS's default (Linux podman-self, macOS
    apple-container-self).  A host setup puts no walls around the agent, so
    this key never chooses one: only `yolo host` runs one.
      setup = "seatbelt-yolo-account"
    Write it with `yolo config set setup seatbelt-yolo-account --user`.  A
    project file cannot hold it: where the agent runs is yours to choose, and
    a project's `setup` line is an error naming `--setup`, the `--user` set
    and `yolo config unset setup --project`.

  [bold]setups[/bold] (table, [bold]USER SCOPE ONLY[/bold]): Your own setups, one table per name.  A
    setup has two fields, each with its own default: `confinement` ("podman"
    (default) | "apple-container" | "seatbelt" | "landlock" | "host") and
    `run_as` ("self" (default) | "yolo-account").  Any other field is refused.
      [setups.mac-as-me]
      confinement = "seatbelt"
      # run_as is not written, so it is its default, self
    A name is lowercase letters, digits and inner hyphens, at most 32
    characters, and never a built-in's: a [setups.podman-self] table is
    refused, naming `yolo setup new my-podman --from podman-self`.  A project
    file cannot define one; setups are yours.

  [bold]agents[/bold]: [bold yellow]REMOVED[/bold yellow] — which agents a jail gets is no longer a
    config key of its own.  An agent arrives as a pack, so name the pack that
    installs it in [bold]packs[/bold] instead.  A config still carrying `agents` is a
    `yolo check` error.

  [bold]install.nix[/bold] (array): Extra nix packages baked into the image.
    The legacy JSONC key is `packages`.
    Example (yolo-jail.toml):
      [install]
      nix = ["postgresql", "gtk4.dev", { name = "strace", platforms = ["linux"] }]
    `yolo config add install.nix '"postgresql"' --project` adds one entry.
    Supports three formats:
    • String: a nixpkgs attribute path (latest from flake's pin).  An entry
      installs what `nix build nixpkgs#<entry>` builds, so a dot reaches into
      whatever the name before it holds: an output or a collection member.
      Examples: "postgresql", "gtk4.dev" (gtk4's dev output),
                "rocmPackages.clr" (a member of the rocmPackages collection),
                "rocmPackages.clr.icd" (that member's icd output)
      A name that is not letters, digits, '_' and '-' is quoted as Nix quotes
      it: 'nerd-fonts."m+"'.  A bare collection ("rocmPackages") is refused,
      naming members you could write instead.
    • Table with nixpkgs: pinned to a specific nixpkgs commit
      Example: { name = "freetype", nixpkgs = "<commit-hash>" }
    • Table with version override: build from upstream source
      Uses the existing nix build recipe but swaps version+source.
      Example (yolo-jail.toml):
        [[install.nix]]
        name = "freetype"
        version = "2.14.1"
        url = "mirror://savannah/freetype/freetype-2.14.1.tar.xz"
        hash = "sha256-MkJ+jEcawJWFMhKjeu+BbGC0IFLU2eSCMLqzvfKTbMw="
      Get the hash: nix-prefetch-url <url>  (then convert with nix hash)
      Or set hash to "" and nix will tell you the correct one on build failure.
    • Any table form may add [bold]platforms[/bold]: the entry applies only on
      those platforms, and is EXPECTED-absent elsewhere rather than an error.
      Values are Go GOOS spellings — "linux" or "darwin" — not nix system
      doubles ("x86_64-linux"); an unknown value is a config error, because an
      entry that matched nothing would drop the package everywhere in silence.
      Example: { name = "strace", platforms = ["linux"] }
      A bare string, and a table WITHOUT platforms, apply everywhere.
      On the macos-user backend a declared package with no native build is a
      FATAL launch error naming every such package at once — marking it
      linux-only is how you say that absence is intended.  It still installs
      normally in a container.
    Find nixpkgs commits per version: https://lazamar.co.uk/nix-versions/
    Search package names: https://search.nixos.org/packages
    For Mesa graphics libraries in a GPU-enabled Linux container, select
    `mesa`; its resolved profile may also supply the 32-bit tree. The explicit
    nixpkgs attr `pkgsi686Linux.mesa` can be selected where supplied. Pin with
    the existing table form, for example
    `{ name = "mesa", nixpkgs = "fe13242281a67641c0102cdb1087f0ebe586c7df" }`;
    that revision is this checkout's `.nodes.nixpkgs.locked.rev` in `flake.lock`.
    Image rebuilds only when this list changes.
    Nix caches builds — identical configs across jails share cached results.

    Shared libraries: each package's shared libraries are symlinked into
    the library search paths, so a package added for its .so (zbar, libdmtx, ...)
    is dlopen-able by bare soname (e.g. ctypes.CDLL("libzbar.so.0")): the
    libraries also land in /usr/local/lib/yolo-ld on LD_LIBRARY_PATH
    (or /run/yolo/packages/lib for store-delivered packages), and FHS
    binaries find them through nix-ld, since the loader does not use
    /etc/ld.so.cache in this image. The correct shared-lib output is picked
    automatically (e.g. zbar ships its .so in a separate "-lib" output), so a
    bare "zbar" just works — no need to spell ".lib". A ".dev" request (e.g.
    "lilv.dev") contributes the package's runtime libraries too — and those of
    its propagated closure — so binaries you build against it also load: compile
    with pkg-config, run without extra LD_LIBRARY_PATH fiddling.

  [bold]include_if_found[/bold] (array of strings): Layer in sibling override files.
    Each entry is a relative path resolved against the including file's
    directory. Missing files are silently skipped — keep entries that may
    or may not exist on a given machine (an untracked *.local.toml, secrets,
    machine-specific tweaks). Present files are loaded and merged on top
    (later wins; lists concatenate-and-dedup; a removal spelling such as an
    empty list drops what came before). Includes can declare their own
    `include_if_found`; cycles are detected and broken.  A TOML file may
    include a legacy JSONC file.

    Common use: each level (user config, workspace config) references an
    untracked sibling that adds custom MCP servers, agents_md_extra notes,
    or env.sources entries without committing them.  yolo git-ignores only
    .yolo/, so add such a file to your .gitignore yourself.

    Note: the workspace-level `yolo-jail.local.toml` needs no include
    entry — it is auto-merged whenever it exists (listing it
    anyway is harmless; it won't merge twice). include_if_found remains
    for other file names and for the user-level config.

    Example (~/.config/yolo-jail/config.toml):
      include_if_found = ["overrides.toml"]

  [bold]~/.config/yolo-jail/config.d/*.toml[/bold] (user config fragments): Read
    automatically, with no include_if_found line, whenever the user config is
    config.toml or there is no user config file at all.  A legacy config.jsonc
    (or config.json) reads no config.d/.
    What is loaded: each entry of config.d/ whose name ends in ".toml" and is a
    regular file once links are followed (a linked fragment is read; a
    subdirectory, a .jsonc file or any other name is skipped).  Each fragment
    is user-scope, like config.toml, and may list its own include_if_found,
    relative to config.d/.  A file already read (through an include, say) is
    not read twice.
    Order: config.toml with its includes first, then the fragments in byte
    order of their names (uppercase before lowercase; number them, as in
    10-base.toml and 20-work.toml, to fix the order), each with its own
    includes, then a --user-layer last.
    Merge: each fragment merges on top of everything before it exactly as a
    TOML include does: tables merge key by key, a later scalar wins, lists
    from each file add up (duplicates dropped), and a removal spelling
    (an empty list, "off", "native" where a key has one) drops what earlier
    files wrote.
    Use one file per machine or role (a dotfiles manager can link in
    work.toml on one machine only).

  [bold]agents_md_extra[/bold] (string): Markdown appended to every agent's briefing.
    Whatever you put here is concatenated onto the jail-managed section of
    AGENTS-copilot.md, AGENTS-codex.md, and CLAUDE.md before the host-level
    user content is prepended.  Use it to surface per-jail notes that every
    agent should see — "this jail has cerebras-mcp wired up, prefer it for X",
    project-specific quirks, links to the right runbook, etc.

    It reaches your real home too: `yolo host apply` writes the USER-scope
    value (~/.config/yolo-jail/config.toml) into every briefing file your
    packs name, after the section saying the agent is on your real machine
    and before your packs' prose.  A workspace value never leaves the jail.

    Pairs naturally with include_if_found: put it in a local overrides file
    you keep out of git, so the note rides along with custom MCP servers.

    Example (yolo-jail.toml):
      agents_md_extra = """
      ## Cerebras MCP

      Use cerebras-mcp for X.
      """

  [bold]briefing_provenance[/bold] (boolean, default false): Label each pack's prose in
    a composed briefing with a `<!-- from pack: NAME -->` line.  Off by default:
    your packs are your rules for every repository, and a per-pack label made
    agents read them as someone else's.  Claude Code strips HTML comments from
    CLAUDE.md before the model reads it, so for Claude the label is only ever
    visible to a human opening the file.  Turn it on to debug which pack a rule
    came from.  Read from the effective config for the jail's own briefing and
    from the user config by `yolo host apply`; set it in the user config to
    change both.

    Example (~/.config/yolo-jail/config.toml):
      briefing_provenance = true

  [bold]allow.<pack>[/bold] (table, [bold]USER SCOPE ONLY[/bold]): A loophole's grants, settings and off switch.
    A loophole is a host-side service the jail can reach.  Every loophole ships
    in a pack, and it runs whenever its pack is selected.  The legacy JSONC key
    was `loopholes`; LEGACY JSONC FORMAT lists its old fields.

    GRANTS.  A loophole that declares [[grants]] in its loophole.toml
    ("journal", "audio", "host-processes" among them) grants nothing until a
    grant covers the project.  You give a grant to every project with
    [cyan]yolo allow <pack> <kind>[/cyan] on the host.  You let a project ask for one with
    [cyan]yolo allow <pack> on_request <kind>[/cyan]; the project then asks with
    [cyan]yolo request <pack> <kind>[/cyan].  THE TOML FORMAT above describes the
    `[allow.<pack>]` and `[requests.<pack>]` tables these verbs write.
    Example (~/.config/yolo-jail/config.toml):
      packs = ["journal", "host-processes"]
      [allow.journal]
      always = ["read"]
      [allow.host-processes]
      on_request = ["view"]
    To keep a pack's loophole away from every project, do not select the pack.

    [cyan]yolo loopholes enable[/cyan] and [cyan]disable[/cyan] are RETIRED: a
    loophole runs whenever its pack is selected, and a project gets access by
    a grant, not a switch — [cyan]yolo request <pack> <kind>[/cyan] for one
    project, [cyan]yolo allow <pack> <kind>[/cyan] for every project.  Both
    refuse, naming those two.  An older yolo wrote switches into a project's
    PER-WORKSPACE FILE (~/.config/yolo-jail/workspaces/<folder>-<hash>.jsonc,
    which merges LAST and no jail can read).  yolo still reads such a switch
    as that project's legacy request for the loophole's grant, until the
    migration retires that file.  [cyan]yolo loopholes disable <name>[/cyan], run on
    the host in the project, removes it and exits 0.

    THE OFF SWITCH.  Five loopholes hand over a login, a credential or the
    cgroup delegate with no grant at all: claude-oauth-broker (the claude-auth
    pack), openai-auth-broker (codex-auth), mcp-auth-broker (mcp-auth),
    aws-auth and cgroup-delegate.  You keep one of them off for every launch
    with `off = true` in its pack's table:
    Example (~/.config/yolo-jail/config.toml):
      [allow.aws-auth]
      off = true
    `yolo config set allow.aws-auth.off true --user` writes it.  A project's
    `[requests.<pack>] off = true` keeps it off for that workspace alone.  A
    pack that ships no such loophole refuses the key.

    A brokered loophole (the github pack's github-broker, the git pack's
    git-broker) grants nothing until a read grant does; see BROKERED
    LOOPHOLES below.

    SETTINGS.  The other keys of `[allow.<pack>]` are THE LOOPHOLE'S OWN
    SETTINGS.  yolo does not fix what may go there: the loophole's
    [cyan]loophole.toml[/cyan] DECLARES its settable keys, each with a type and an
    optional default, and yolo validates what you write against that
    declaration.
    Example (~/.config/yolo-jail/config.toml):
      [allow.host-processes]
      fields = ["pid", "comm"]
    `yolo config set allow.host-processes.fields pid comm` writes it.

      An undeclared key is an ERROR naming the keys that do exist, and a value of
      the wrong type is an error too — the block is typed, never opaque.  Declared
      types are "string", "bool", "int" and "string_list".  See what a loophole
      declares with [cyan]yolo loopholes list[/cyan].

      EVERY SETTING IS USER SCOPE.  A setting may only be set from your user
      config, and writing it in a workspace file is refused naming both files.
      A manifest's `scope = "workspace"` is retired and refused at load: a
      setting can reach a host daemon, and a project's say over what a
      loophole may do is a request for one of its grant kinds instead.

      RESOLVED ONCE, AT LAUNCH.  yolo merges your values over the declared
      defaults, writes the result to a file it owns in the loophole's state dir,
      and hands the daemon that PATH.  So editing a setting takes effect on the
      next jail START, not on the next request — which is deliberate: a restart is
      where the config-change approval prompt lives, and a value that could change
      under a running daemon could be changed by the agent inside it.

    Each loophole gets:
      • Its endpoint file bind-mounted into the jail under /run/yolo-services/
      • An env var so agents can locate the service without hard-coding paths:
        YOLO_SERVICE_<NAME>_ENDPOINT.  Its value is always a PATH, never an
        address: the address lives inside the file, so a restarted daemon
        needs no jail relaunch.
      • A managed lifecycle: started before container start, SIGTERM + 5s grace +
        SIGKILL after the container exits.
      • stdout/stderr captured to ~/.local/share/yolo-jail/logs/host-service-<name>.log

    The ENDPOINT FILE is one line naming a 127.0.0.1 listener, the exact
    certificate a client must pin, and a per-jail bearer token.  That file IS
    A CREDENTIAL: it is written 0600 into this jail's own directory and is
    never shared between jails.  There is deliberately no token env var.
    [cyan]loopback-tls[/cyan] is the only manifest transport and the default;
    [cyan]unix-socket[/cyan] and [cyan]tls-intercept[/cyan] were REMOVED from the
    manifest vocabulary, not deprecated.  The manifest key "default_enabled"
    is refused at load: a loophole.toml declares what can be granted under
    [[grants]] instead.

    Use loopholes to split the jail boundary cleanly: a host-side process can
    hold secrets, credentials, and access-control logic that the agent inside
    the jail can call but never sees.  A host service of your own belongs in a
    pack: `yolo pack init` starts one.  (The legacy JSONC `loopholes` key can
    still declare one inline; LEGACY JSONC FORMAT describes it.)

    "claude-oauth-broker" is the one loophole name yolo reaches by literal:
    "yolo broker status", "yolo check"'s broker section, the host-singleton
    spawn and the in-jail terminator's endpoint variable all name it.  Select
    `packs = ["claude"]` to get it; to stop it, set `off = true` under
    [allow.claude-auth].  Two packs that claim one loophole name refuse the
    launch.

    Apple Container is unsupported.  The reason USED to be the transport (no
    Unix-socket bind-mount through virtiofs); loopback-tls removes that obstacle,
    but how the endpoint file crosses into an AC guest is an unmade decision, so
    host services stay explicitly DEFERRED there rather than quietly enabled.

  [bold cyan]BROKERED LOOPHOLES: requests.github.repos, read grants, sets[/bold cyan]
    A brokered loophole, such as the github pack's github-broker or the git
    pack's git-broker, runs your host login's commands for the jail.  It runs
    them only against the workspace's repositories: its git remotes, and any
    repositories its config lists, which every fresh launch reads and asks you
    to approve.  It runs in every workspace while its pack is selected, and
    GRANTS NOTHING until a read grant does: with none, it refuses every call,
    naming the grant.  The usual grant gives read access to every workspace,
    in your user config:
    Example (~/.config/yolo-jail/config.toml):
      packs = ["git", "github"]
      [allow.git]
      always = ["fetch"]
      [allow.github]
      always = ["read"]
    `yolo allow git fetch` and `yolo allow github always read`, run on the
    host, write these lines.  The grant still joins each workspace only at
    that workspace's config-change prompt, or at [cyan]yolo config apply[/cyan] on
    the host, as a line of the repository-scope block marked as your user
    config's.  Every call through the broker needs a read grant on its
    repository, a push as well as a fetch.
    [bold]requests.github.repos[/bold] ([bold]WORKSPACE SCOPE[/bold]): more repositories for this
    workspace.  List a repository the project has no remote for in
    yolo-jail.toml, or in yolo-jail.local.toml for what the project should not
    commit (yolo does not git-ignore that file):
    Example (yolo-jail.toml):
      [requests.github]
      repos = ["org/lib", "org/docs"]
    `yolo request github repos org/lib` writes it.
    • The table name is the source the loophole's manifest declares as
      `brokered.source`; the github pack's is "github".  A source no selected
      pack brokers is a host `yolo check` warning; a launch says nothing.
    • Each repos entry is OWNER/REPO, with no host, or a whole-segment
      wildcard: "*/*" for every repository the login can reach, "OWNER/*" for
      every repository of one owner, "*/REPO" for that name under any owner.
      A partial glob such as "org*" is refused.  An entry is in scope exactly
      as a remote is: its reads run, and its writes need the same approval.
      A wildcard widens which repositories run, and nothing else; no entry
      admits a command across your whole account, such as a search with no
      repository.
    • Lists merge across the workspace's files, compared without case, and
      `repos = []` in the local file clears the list.  A repository list from
      a file outside the workspace, reached through an include or a link, is
      refused, and so is one written twice in one file.
    • NOT IN THE USER CONFIG.  A user `requests` table is an error: with no
      workspace to key it, it would widen every workspace.
    [bold]allow.<source>.sets[/bold] (USER SCOPE ONLY): the named permission sets this source's
      grants hand over.  A standing set runs freely; a windowed set runs only under a
      grant, for its window and up to its ceiling and use cap.
      Example (~/.config/yolo-jail/config.toml):
        [[allow.github.sets]]
        name = "review"
        mode = "windowed"
        window = "1h"
        max_window = "session"
        uses = 50
        admit = ["pr comment", "pr review"]
      • name (required): lowercase letters, digits and hyphens, unique in the list.
      • mode (required): "standing" or "windowed".
      • window, max_window, uses: a windowed set only.  window is a duration such as "15m" or
        "1h"; max_window is a duration or "session" (the jail's life); uses is a whole number
        of 1 or more.  A field a set does not name keeps the source's default.
      • admit: the command rules the set adds, in the broker's own vocabulary; a set named like
        a default with no admit keeps that default's rules.
      Every set is definable, "read-only" included, and each launch names what it found, as in
      "github-broker: sets from user config: read-only (+ pr comment), review 1h".  A workspace
      file may NOT name sets: that file is the agent's to edit, so `sets` there is a `yolo check`
      error.  A config that writes both spellings (a TOML user config including a legacy file)
      reads both lists, the TOML entries first; a name may appear once across the two.
    [bold]What a workspace may request[/bold]: your `[allow.<source>] on_request` list names
      the capabilities a project may ask for, and the project's `[requests.<source>]`
      table asks.  The git pack's capabilities are `new_branches` (create a branch),
      `push` (a branch the broker may create, update, force-push and delete) and
      `push_tags` (a tag, handled the same way); the github pack's are `create_pr`,
      `create_issue`, `runs` and `approve_runs` (THE TOML FORMAT describes each).
      Example (~/.config/yolo-jail/config.toml):
        [allow.git]
        always = ["fetch"]
        on_request = ["new_branches", "push", "push_tags"]
      Example (yolo-jail.toml):
        [requests.git]
        new_branches = true
        push = ["main"]
        push_tags = ["v*"]
      `yolo allow git on_request push` (host) and `yolo request git push main`
      (project) write these lines.  A request covers every remote of this
      workspace.  A branch or tag value is a short name git accepts, or git's
      refspec pattern with one "*", which matches any run of characters, "/"
      included ("patch/*", "v*"); two "*" are an error.  A request your allow
      list does not allow is reported and skipped.
      A request joins only when you approve it: each is a line of the repository-scope block at
      the next fresh launch, or at `yolo config apply`, which replaces a running jail's grants
      as it replaces its repositories, and each launch names the grants in force.
    It takes effect at the next fresh launch: the config-change prompt shows each
    repository as a row of the repository-scope block, naming the file it came
    from, and asks you to approve it; then the launch names the scope, as in
    "github-broker: scope for this workspace: you/app (remote "origin"), org/lib (yolo-jail.toml)".
    An agent may add an entry: a jail refuses a repository outside its scope with
    a message telling it how, and to ask you to restart and approve.

  [bold]on_request[/bold] (string, [bold]USER SCOPE ONLY[/bold]): A command yolo runs for each request a
    jail files for your approval, so one line can be your whole approval front
    end.  Off unless set.  The git broker (a push that needs approval) and the
    GitHub broker (a write or a dispatch that needs approval) both run it.
    Each running jail's broker (such as the github pack's github-broker) runs it
    on the host, as you, with `sh -c`, from your home directory, once per
    request that jail files, and for nothing else: a decision, an expiry or a
    grant's use runs nothing.  To follow every event, read
    `yolo approve --watch --json` instead.  The request-filed event's JSON
    object, the same one `yolo approve --watch --json` prints, is on its stdin,
    and its fields are in the environment: YOLO_EVENT (request-filed),
    YOLO_SOURCE, and YOLO_REQUEST_* in three groups.
      Safe anywhere, yolo's own words and validated parts: _ID, _ACTION
      (push, pr-create, pr-merge, pr-write, issue-create, issue-write,
      workflow-dispatch, repo-write or api), _TARGET (such as `PR o/r#70`),
      _HEADLINE (one short phrase, such as `merge PR o/r#70` or
      `push 2 refs to github.com/o/r`), _SET, _JAIL, _EXPIRES and _REPO
      (for git, the remote's host and path as its approved URL names them).
      Free text, the agent's words made terminal-safe: _TITLE (the
      --title or --subject, a workflow file, an API path), _REFS (one per
      line: a push's refs, a dispatch's ref), _DESCRIPTION (the headline,
      then `title: ...` and one `ref: ...` per ref, a line each) and
      _SUMMARY (one line of at most 2048 bytes, the complete record: the
      request id, the set, the repository and the jail, then the command,
      each value over 60 characters cut to its first 40 with its length and
      a short hash, then its digests).
      Escaped for notification markup: _DESCRIPTION_MARKUP and
      _SUMMARY_MARKUP, the same text with & < > " ' as XML entities.
    _WORKSPACE names the request's workspace.  A notifier that renders
    markup (a desktop notification daemon such as swaync renders <b> and
    <a href>) shows a _MARKUP field, a plain-text one (a terminal, a log)
    shows _DESCRIPTION, and _HEADLINE is safe in either; never run any of
    them.  The _MARKUP fields are for notification markup only; any other
    renderer (Slack, HTML) needs its own escaping of the plain field.
    A plain `yolo` works in the command, whatever your PATH: a private
    directory holding only a link named yolo to the running yolo comes first
    on its PATH, and YOLO_BIN names that same yolo by its full path, for a
    script that wants it absolute.  The command does not inherit the pane
    identity of the terminal that started the broker (HERDR_PANE_ID,
    HERDR_TAB_ID, HERDR_WORKSPACE_ID, TMUX_PANE, ZELLIJ_PANE_ID, WEZTERM_PANE,
    KITTY_WINDOW_ID), which is stale by then; the session's identity
    (HERDR_SOCKET_PATH, HERDR_SESSION, TMUX, ...) is kept.
    IT ONLY NOTIFIES.  yolo reads nothing back from the command, and no hook is
    required: a pending request is also visible in the background broker log and
    can be answered manually with `yolo approve` on the host.  When configured,
    the hook runs the CLI itself, so its buttons get the same checks, refusals and audit.
    This desktop notification has Allow once and Deny buttons, and it sits at
    the top level of the file:
    Example (~/.config/yolo-jail/config.toml):
      on_request = 'a=$(notify-send -u critical -A once="Allow once" -A deny=Deny "yolo: $YOLO_REQUEST_HEADLINE" "$YOLO_REQUEST_DESCRIPTION_MARKUP"); case "$a" in once) yolo approve "$YOLO_REQUEST_ID";; deny) yolo approve "$YOLO_REQUEST_ID" --deny;; esac'
    Allow once is `yolo approve <id>`: the exact command, once.  A GitHub write
    also takes `--for <duration>` on its resource (see `yolo approve --help`).  The same lines can live in a script
    the key names instead.  `"$YOLO_BIN" approve` works wherever plain yolo approve does.
    • A run may take as long as its request waits, one hour, so a notification
      left on screen can still be answered; several requests run several
      commands at once.  Use `notify-send -u critical`: the desktop
      notification spec asks that a critical notification not expire on its
      own.  A `-t` toast timeout is optional, since a notification ignored
      until the request expires is not a failure.
    • As soon as the request stops waiting, whichever way (a click's own
      `yolo approve`, a `yolo approve` elsewhere, expiry, or refused because
      its jail stopped), or the jail stops, yolo sends SIGINT to the
      command's process group, everything it started included, then SIGKILL
      to whatever is left 2 seconds later.  notify-send (libnotify 0.8.0 and
      newer) waiting on -A or -w closes its notification on SIGINT, so the
      example above cleans up after itself.  For a notifier that does not, a
      script can close it from `trap ... INT`.
    • A command that exits non-zero, or cannot start, is a failure: `yolo
      approve` lists it on its request ("hook exited 127: sh: notify-send:
      not found"), and --json carries it as "hook_failure" with the last
      4 KiB of its output as "hook_output", including what a refusing `yolo
      approve` it ran printed.  The agent is told your notifier failed.  The
      output never decides anything.
    • notify-send: -A needs libnotify 0.7.10 or newer.  A notification that
      times out or is dismissed ends the command with no answer, so the
      request waits for `yolo approve`.  On a machine you reach over SSH, it
      pops up on that machine's desktop, which may be unattended.
    • The summary and fields come from the jail's request, so treat them as
      the agent's words: show them, never run them.
    USER SCOPE ONLY.  A workspace config is the agent's to edit, and this
    command runs on the host and can approve, so a workspace value is a
    `yolo check` error and refuses the launch.  It takes effect at the next
    fresh launch.

  [bold]host_processes[/bold] (object): REMOVED — a config carrying it is REFUSED.
    The host-processes loophole ships in the pack of that name, and what it may
    show is a grant a project requests, not a config key:

      yolo pack add host-processes
      yolo allow host-processes on_request view        # on the host, once
      yolo request host-processes view sway            # in the project
      yolo config set allow.host-processes.fields pid comm   # ps -o columns

    NOTE THE SPELLING: the loophole is "host-processes" (hyphen); the removed
    top-level key is "host_processes" (underscore).  The columns are read once at
    launch, so changing them needs a jail restart.

  [bold]journal[/bold] (string): REMOVED — a config carrying it is REFUSED.
    The journal bridge is an ordinary pack-shipped loophole now: it runs whenever
    its pack is selected and reads nothing until a grant covers the project.
    yolo's config schema no longer names a loophole at all.

      yolo pack add journal
      yolo allow journal read          # was "journal": "user" (or the bare true)
      yolo allow journal read_all      # was "journal": "full"

    What it does is unchanged: [bold]yolo-journalctl[/bold] inside the jail forwards
    its args to [cyan]journalctl[/cyan] running on the host and streams
    stdout/stderr back, so an agent can inspect systemd logs without the host
    journal being mounted rw into the jail.
      • off      — don't select the pack, or grant nothing
      • narrow   — the "read" grant; the daemon forces [cyan]--user[/cyan] on every
                   invocation (what "user" meant)
      • full     — the "read_all" grant; args pass through unchanged, which
                   needs host journal read access
    A GRANT IS YOURS TO GIVE.  A workspace file may ask (a request), never grant:
    reading the whole host journal used to be settable from a file the agent
    inside the jail can rewrite, and the grant is what ended that.
    Endpoint file: /run/yolo-services/journal.endpoint
    Env var: YOLO_SERVICE_JOURNAL_ENDPOINT
    The value is a PATH to the endpoint file, not an address: the bridge is on
    the loopback-TLS transport, so the address lives inside the file and a
    restarted daemon is picked up without relaunching the jail.  The file also
    carries this jail's bearer token, which is why it is 0600.

  [bold]env[/bold] (table): Environment variables set inside the jail.
    The legacy JSONC key is `env_sources`.
    Example (~/.config/yolo-jail/config.toml):
      [env]
      sources = ["~/.config/yolo-jail/defaults.env",
                 { set = { DEBUG = "1" }, unset = ["AWS_PROFILE"] },
                 "secrets/claude.env"]
      set = { EDITOR_THEME = "dark" }
      unset = ["HTTP_PROXY"]
    [env] has four keys:
      • sources — an ordered list; each entry is either:
        • a string — path to a KEY=VALUE dotenv file (# comments allowed,
          quoted values OK, `export` prefix tolerated)
        • an inline table — `{ set = { KEY = "VALUE" }, unset = ["KEY"] }`.
          A name in `unset` UNSETS the variable — the spelling
          `yolo host -- <cmd>` uses to drop e.g. AWS_PROFILE from the
          invoking shell (a later entry assigning the key cancels it).
      • files — a list of dotenv paths only.
      • set and unset — one table of values and one list of names, which
        apply after every list.
    `yolo config add env.files '"secrets.env"' --project` adds a file entry.
    An unset name removes a pack's `env` value of the name too, in a jail
    as at the host.  It never removes a value the selected provider
    composes, nor the YOLO_PROVIDERS, YOLO_PROFILES and YOLO_USE_PROFILES
    tables a launch sets.
    Later entries override earlier ones.  A value here beats a
    pack's `env` of the same name and loses to the selected
    provider's.  User-config list loads first,
    then workspace-config list.  File paths support ~ expansion and
    absolute paths.  A RELATIVE path resolves beside the file that
    declared it — for the user config that is
    ~/.config/yolo-jail/, for each include the include's own directory,
    and for the workspace config the workspace root (so
    workspace-relative spelling behaves exactly as it reads).  A file
    entry in the WORKSPACE config (yolo-jail.toml, its local sibling,
    their includes) must resolve inside the workspace, symlinks
    followed: a workspace config travels with the repository, so `~/…`,
    an absolute path elsewhere, a `../` escape or a link pointing out is
    refused, and the refusal gives the same entry to put in your user
    config, where any path is fine.  `yolo
    host` additionally refuses any relative entry that reaches it
    unanchored, which in practice never happens for configs yolo loaded.
    Missing files warn
    and skip rather than failing the run — keep secrets in an unsynced
    file outside your dotfiles tree.
    A value no provider claims is written to ~/.config/yolo-user-env.sh
    (sourced by .bashrc and the entrypoint), so every process sees it; it
    can be overridden by mise .env or by editing that file inside the jail.
    A value a provider CLAIMS (names in its api_key_env_name) is written
    only to ~/.config/yolo-agent-env/<agent>.sh for each agent that
    selected that provider, which that agent's launcher sources:
    no other process, a bare shell included, sees it.  With no agent
    selecting the provider it reaches nothing, and the launch says so.
    At the host, `yolo host --with-credentials <provider[,…]|all> -- <cmd>`
    hands one command the named providers' claimed values, keys only, for
    that run (`all`: every provider claiming a value here).  At a jail
    launch, `yolo --with-credentials <provider[,…]|all> -- <cmd>` starts the
    jail holding them, keys only, for its whole life: every process in it,
    and every session attached to it later, inherits them, and an attach
    asking for a provider the running jail was not launched with is
    refused (`yolo stop`, then launch again with the flag).  A profile an
    attach selects is no grant: it still hands its agent that profile's
    key, as ruled, and the attach says so.  On macos-user the grant is the
    one sandbox session's.  No config key can grant either.
    Dropping a key (or the whole list) REVOKES it: the next launch rewrites
    that file, truncating it to empty when nothing resolves, so a removed
    credential stops being exported.  Values already live in a RUNNING jail
    persist until it restarts.
    The same file carries the per-entry provider channel (see `active_provider`):
    the three tables and the ungated pack env land in a marked section as
    unconditional exports, rewritten by every ENTRY — a fresh launch and an
    attach alike — so `-p` reaches a running jail.  Those lines are not
    overridable defaults; the whole section is recomposed each time.  What a
    profile composes for ONE agent (its provider's settings and token, and
    the pack env its selection gates) goes to that agent's own file instead,
    rewritten by every entry the same way, and beats a value you export.
    The lists are walked per config file, in the order the files
    merge (your config, its includes, a --user-layer, the workspace
    config); within a TOML file, sources and then files.  So a project
    may convert to TOML while your config stays legacy, or the other
    way round, and the variables come out the same.  An empty list
    (sources = [] or files = []) drops every list a lower file wrote.

  [bold]mounts[/bold] (array of strings and tables): Extra host paths, read-only unless you ask.
    [bold]For paths OUTSIDE the workspace only.[/bold]  The workspace itself is
    already /workspace, read-write and live (see the top of this reference) —
    listing it here gets you a second view of a tree you can already write,
    under a name nobody expects.
    Every entry lands under the [bold]context dir[/bold], /ctx on podman and Apple
    Container, which every launch names to the jail as $YOLO_CONTEXT_DIR (it
    exists, possibly empty, whether or not you declared a mount).
    [bold]String entries are READ-ONLY, always[/bold] — every one gets :ro appended:
      Simple path → mounted at /ctx/<basename>
      "host:container" → custom container path
      Example (yolo-jail.toml):
        mounts = ["/path/to/repo", "~/lib:/ctx/lib"]
    [bold]Table entries[/bold] carry a mode, and are the only way to write a
    read-write mount.  The "optional" key is described below.
      Example (~/.config/yolo-jail/config.toml):
        mounts = [
          { host = "~/scratch/datasets", at = "/ctx/data", mode = "rw" },
          { host = "~/notes", mode = "ro" },
          { host = "~/papers", mode = "ro", optional = true },
        ]
    `mode` is REQUIRED ("ro" or "rw") — there is no default, so a writable
    mount is never one you did not write.  `at` is optional (default
    /ctx/<basename>); a read-write mount must land UNDER /ctx/, where it can
    shadow nothing of the home or a composed surface.
    [bold yellow]Do NOT write a docker-style ":ro" or ":rw" suffix.[/bold yellow]  ":rw" is a
    `yolo check` error naming the table form.  ":ro" is worse: the split
    takes the last colon followed by "/", so "~/x:/ctx/x:ro" parses as ONE
    host path literally named "~/x:/ctx/x:ro".  It does not exist, so the
    mount is SKIPPED with a warning — and `yolo check` only warns too, so a
    config that mounts nothing looks accepted.
    [bold yellow]A read-write mount is user-scope only[/bold yellow] — write it in
    ~/.config/yolo-jail/config.toml (or a --user-layer).  A `mode = "rw"`
    entry in yolo-jail.toml, yolo-jail.local.toml or anything they include is
    a `yolo check` error and the launch refuses: a workspace config is
    agent-editable, so it cannot grant a read-write host mount.  Read-only
    entries may sit at either scope.
    [bold]A project may REQUEST one instead[/bold] — a table with `write = true`
    in yolo-jail.toml or yolo-jail.local.toml, such as
      Example (yolo-jail.toml):
        mounts = [{ host = "~/scratch", at = "/ctx/scratch", write = true }]
    — once YOUR user config allows requests with these two lines:
      Example (~/.config/yolo-jail/config.toml):
        [allow.mounts]
        on_request = ["write"]
    `yolo config add allow.mounts.on_request '"write"' --user`, run on the
    host, writes them.
    Without them the request is a `yolo check` error naming them.  With them
    it is approved at the config-change prompt like any change, the writable
    mount printed in red and marked "WRITABLE HOST MOUNT" (color or not), and
    a changed request asks again; --accept-config-changes approves it too,
    after printing the same block.  `allow.mounts` has no `always`: every
    writable mount is approved per project.  `write` and `mode` together are
    an error.  A legacy JSONC project file cannot request one: a read-write
    entry there keeps the refusal above.  Only yolo-jail.toml and yolo-jail.local.toml
    themselves may request one, never a file they include, and `host` must be
    absolute or start with "~".  A request meets every rule below.
    [bold]A workspace config's mounts, read-only or read-write:[/bold] a source whose
    path AS WRITTEN (before any symbolic link is followed) is inside the
    workspace, or inside another mount, is a `yolo check` error and the launch
    refuses — a link there is the agent's to point at ~/.ssh.  Any other link
    is followed, and the config-change prompt shows and records where it
    lands; a source that later resolves elsewhere refuses the launch until
    you approve the new destination.
    A read-write source is also REFUSED when it is, or contains, your home,
    ~/.config/yolo-jail or ~/.local/share/yolo-jail, sits inside either yolo
    directory, or overlaps the workspace in either direction (a second
    writable path to it would bypass `workspace_readonly`).  Directories like
    ~/.ssh are not on any list: a mount you wrote in your own config is your
    own authority, and the launch names it every time.
    [bold]Every launch prints one line per read-write mount[/bold] — the host path, the
    jail path, and that anything on this machine which later reads that
    directory reads what the jail wrote there, a planted symlink included.
    YOLO_NO_BANNER does not hide it.  On a ROOTFUL podman the line adds that
    files the jail's root creates there are owned by root on the host (on a
    rootless one they are yours; a file written by a non-root user inside the
    jail lands as a subuid you remove with `podman unshare`).  yolo never
    creates, chowns or relabels a mount source, and there is no locking: two
    jails, or a jail and you, writing one directory get last-writer-wins,
    like two programs on the host.
    Two mounts at one jail path — a pack `mount` at /ctx/<into> included —
    are a `yolo check` error.  An entry whose source does not exist is
    skipped, so it collides with nothing: one entry per machine at the same
    path is fine.  /ctx/packs, /ctx/captures, /ctx/host-user and
    /ctx/host-nvim-config are yolo's own: an entry at, inside or containing
    one (an `at` of /ctx itself) is a `yolo check` error too — including a
    bare path whose basename is one of those names, so pin it with `at`.
    <basename> is the basename AFTER symlink resolution.  A link whose name
    differs from its target's mounts under the TARGET's name: "~/code/sysadmin"
    lands at /ctx/sysadmin-config if that is where the link points.  Use the
    explicit "host:/ctx/name" form (or `at`) when you want to pin the name.
    [bold]Host paths are resolved on the HOST, at launch.[/bold]  An IN-JAIL
    `yolo check` resolves "~" against the JAIL's home, so it warns "host path
    does not exist and will be skipped" for every entry an agent adds from
    inside a jail.  [bold]That warning is expected in there and is not a
    failure[/bold] — only a host `yolo check` can judge these paths.  For the
    same reason `mounts` is dropped from the in-jail user-config snapshot and
    is not inherited by a nested jail.
    Runtime support: podman, and Apple Container ("container").  A read-only
    entry needs Apple Container 1.1.0 or later: below that it accepted :ro
    and ignored it, so rather than hand out a writable context mount yolo
    SKIPS every read-only entry and says so — and it skips for the same
    reason when it cannot read `container --version` at all, because the
    safe error is the one that costs a mount rather than the one that costs
    the guarantee.  A read-write entry is bound on every Apple Container
    version: it needs nothing :ro provides.
    "macos-user" has no container, so each entry is a root-owned LINK in
    $YOLO_CONTEXT_DIR (not /ctx) to the host folder itself, and the sandbox
    profile decides what the agent may do there.  The folder must be one
    the sandbox account can reach, outside every user's home: a read-only
    one under /Users/Shared or outside /Users (/opt, /usr/local, …), a
    read-write one under /Users/Shared/yolo.  Before the sandbox starts the
    launch asks, as that account, whether it can read (and for read-write,
    write) each folder.  Anything else — a folder in a home, on another
    volume, overlapping the workspace or a place the sandbox writes (/tmp),
    or an `at` outside /ctx — REFUSES the launch, naming each entry and why.
    Tools that resolve paths print the host path there, and a subfolder the
    sandbox account may not read stays unreadable.  An entry whose source
    does not exist is skipped with a warning, as on every backend.
    [bold]optional = true[/bold] (table entries only; default false) marks an entry
    this backend may not be able to deliver.  Where a required entry would
    refuse the launch (macos-user can't reach the folder; the macOS Podman
    Machine doesn't share it) or be skipped with a warning (a read-only entry
    on an Apple Container older than 1.1.0; a source that does not exist), an
    optional one is skipped with one plain line and the launch goes on:
      Example (~/.config/yolo-jail/config.toml):
        mounts = [
          { host = "~/.local/share/yolo-jail/logs", at = "/ctx/host-yolo-logs", mode = "ro", optional = true },
        ]
      skipped optional mount: ~/.local/share/yolo-jail/logs → /ctx/host-yolo-logs (macos-user can't reach a folder inside a home)
    The agent's briefing marks an optional entry "may be absent".  `yolo
    check` lists what this backend will skip as information.  A string entry
    has no optional form: a ":optional" suffix is a `yolo check` error naming
    the table form.  Optional never softens a safety refusal: a read-write
    source in the refused set above, a source the broker mount fence refuses,
    and on macos-user a source containing every home, inside the sandbox
    account's home, or in yolo's own state directory all still refuse, as
    does a jail-path collision.

  [bold]cache_relocations[/bold] (object): Put a jail cache subdir on other storage.
    Keys are cache SUBDIR NAMES, not paths — a single path segment, no "/",
    not "." or "..".  Values are absolute host directories ("~" expanded).
    Each entry is bind-mounted [bold]read-write[/bold] at /home/agent/.cache/<subdir>,
    nested inside the usual cache mount, so nothing downstream has to know:
    HF_HOME and every other tool's cache path stay exactly as they are.
    Worth it for large, cold, write-once/read-sequential caches — huggingface
    (model repos), ms-playwright (browser bundles) — that you want on a big
    slow disk.  NOT worth it for uv, go-build or pip: those are hit on every
    build and are latency-sensitive, so a slow disk makes every build worse.
    [bold yellow]Scope: this key is read from ~/.config/yolo-jail/config.toml ONLY[/bold yellow]
    (plus that file's include_if_found files, which are host-side too).  In
    yolo-jail.toml it is a `yolo check` error, not an override — the
    workspace is bind-mounted read-write into the jail, so a workspace config
    is agent-editable and must never be able to hand out read-write host
    mounts.  The mount is built from the user config alone; the merged config
    is read only to VALIDATE the key (which is how a workspace-scoped one gets
    reported), never to decide what gets mounted.
    The target's [bold]parent must already exist[/bold]; only the last path component is
    created for you.  A missing parent means a typo (/data/relcoated/...), and
    creating it silently would leave the bytes on the very disk you were
    trying to get off.
    Runtime support: podman mounts it.  "container" (Apple Container) warns
    and skips it.  "macos-user" has no bind mounts, so ~/.cache/<subdir> in
    the sandbox account's home becomes a LINK to the target, and the sandbox
    profile opens the target for reading and writing; each launch names the
    link.  The target may be on another volume under /Volumes; it may not be
    inside a home, the workspace or a `mounts` source.  A folder yolo makes
    for it is opened to the sandbox account as it is made; one that already
    holds files needs `yolo yolo-account share <folder>`, and the launch
    refuses until the sandbox can write it.  Only ~/.cache moves there: a
    macOS tool caching under ~/Library/Caches (Go's build cache, and likely
    pip and playwright) is not relocated.  [bold yellow]A symlink you make yourself is
    NOT a workaround[/bold yellow] on that backend: Seatbelt judges the link's TARGET
    (measured 2026-09-13 on macOS 26.5), and only yolo's own relocation
    opens one.
    Moving an EXISTING cache: stop all jails first, copy the bytes, then set
    the key — a running jail keeps its old, now-empty mount until restart.
    Full procedure: userguide/guides/storage.md, "Storage & Persistence".
    Example (~/.config/yolo-jail/config.toml):
      [cache_relocations]
      huggingface = "/data/relocated/yolo-jail/cache/huggingface"

  [bold]writable_home_dirs[/bold] (array of strings): Extra $HOME paths made writable.
    Each entry is a path relative to /home/agent (no leading /, no "..").  The
    jail's home is mounted read-only except for the dirs yolo manages; an agent
    extension that hardcodes a home path yolo doesn't know about (e.g. pi-lens
    writing ~/.pi-lens) hits that read-only base and its mkdir fails.  List the
    path here and it becomes an ordinary writable dir, backed by
    <workspace>/.yolo/setups/<setup>/home/writable-home/<path> — so it persists per workspace
    and survives restarts, exactly like the built-in overlays.
    You do NOT need this for anything already writable: ~/.config, ~/.local,
    ~/.cache, ~/go, ~/.ssh and every selected agent's own dir (~/.claude, …)
    are read-write already — listing one is a `yolo check` error, since the key
    would only shadow yolo's own mount.
    Unlike cache_relocations this is safe at ANY scope (workspace or user): the
    destination is always under /home/agent and the backing dir is inside the
    workspace, so it hands out no host access a jail didn't already have.
    Runtime support: podman needs (and does) this — its home base is the only
    one mounted read-only.  Apple Container ("container") mounts all of
    /home/agent writable in one bind, and macos-user's Seatbelt profile allows
    writes to the whole sandbox home, so on both of those every home path is
    already writable and the key is a harmless no-op.
    Example (yolo-jail.toml):
      writable_home_dirs = [".pi-lens", ".config-that-isnt-mine/state"]

  [bold]host_files[/bold] (array): Bring any file into the jail, composed not copied.
    Each entry is either a [bold]string[/bold] (sugar) or an [bold]object[/bold] (rich).  Every entry
    becomes a composed "surface" rendered by the same engine that generates the
    agent settings files, so a plain copy is just codec "raw" — one engine, not
    two.  Use this for a dotfile yolo doesn't know about (~/.npmrc, pi's
    models.json), or to bring a brand-new managed file into being.

    [bold]String form[/bold] — "~/.npmrc" means: copy that host file to the same path in
    the jail, codec auto-detected, mode readonly.  A trailing "/" makes it a
    recursive directory copy.  Always source-bearing, hence user scope only.

    [bold]Object form[/bold] keys:
      path       ~-relative jail DESTINATION.  OPTIONAL when `source` is a "~/…"
                 path — it then defaults to the same home-relative place, so a
                 mirrored file names its path once.  Required for a source-less
                 entry, and for a source outside $HOME (/etc/foo.conf has no
                 unambiguous home-relative counterpart to guess).
      source     host path to seed from.  Its presence is what makes an entry
                 user-scope only.  Mutually exclusive with content.
      content    inline literal seed (a string).  Crosses nothing, so it is
                 legal at any scope.  Use "" to declare a deliberately empty file.
      codec      json | toml | lines | raw.  Overrides auto-detect.  There is no
                 yaml codec — a .yaml file is handled as raw bytes.
                 [bold yellow]Comments:[/bold yellow] a STRUCTURED codec (json/toml) parses the file
                 into keys and re-emits it, which DISCARDS every comment — so
                 naming codec = "json" on a commented .jsonc file silently
                 drops the comments.  "raw" keeps the bytes exactly as they
                 are, comments included, at the cost of key-level merging and
                 the defaults/managed layers.  Pick per file: raw to preserve a
                 hand-written config, json/toml to compose one.
      defaults   user-overridable base layer (structured codecs).
      managed    keys yolo re-asserts every render, so they revert on edit.
      mode       see below.

    [bold]Codec auto-detect[/bold]: .json -> json, .toml -> toml, everything else -> raw
    (including no extension, .sh, .yaml, .yml, and .jsonc — routing .jsonc
    through the json codec would sort keys and DROP COMMENTS).

    [bold]Modes[/bold] — what happens across boots, and to an in-jail edit:
      readonly  re-rendered every boot at 0444; a host-side edit propagates on
                the next launch.  [bold]Default for a source-bearing entry.[/bold]
      once      seeded when absent, then never touched.  In-jail edits simply
                persist (no sidecar); later host edits do NOT propagate.
                [bold]Default for a source-less entry.[/bold]  To re-seed, DELETE
                the file — the next boot recreates it, because `once` keys off the
                destination's absence.  (`yolo config reset` does NOT re-seed it:
                reset discards CAPTURED edits by deleting the §5 sidecars, and a
                `once` surface has none.)
      copy      overwritten every boot; in-jail edits are discarded.  Implied
                for a directory entry.
      capture   re-rendered every boot AND in-jail edits captured into a sidecar
                that outranks the host layer — and every layer below it, but NOT
                a `computed` or `managed` key, which are re-asserted above the
                capture on every render.  [bold yellow]Never a default — always
                explicit[/bold yellow], because a captured edit wins over the host file
                FOREVER (the sidecar never ages out), so implicit capture would
                silently fork a host-mirrored file the first time a tool
                rewrote its own config (`npm config set`, any CLI's first run).
                Captured at jail TERMINATE as well as at boot, so `yolo config
                diff` describes the session that just ended, not the one before
                it.  The two folds are the same operation over the same baseline,
                so the earlier one cannot record a key the boot render would not.
    Note 0444 is DAC, not kernel enforcement: an agent running as root (Claude
    YOLO does) bypasses the mode bits.  It is a strong signal and a speed bump,
    not a sandbox — use `mounts` for a kernel-enforced read-only file.
    Inspect what any of this produced with [bold]yolo config ls[/bold]. Its first column is
    the canonical surface identity (`agent/surface`): pass that identity to
    [bold]yolo config render[/bold], [bold]diff[/bold], [bold]reset[/bold], [bold]capture[/bold], or [bold]promote[/bold] to select one
    surface; pass a bare agent to select all its surfaces. `diff` and `reset`
    apply to CAPTURE surfaces only — they are defined over the sidecars, which
    no other mode writes.

    [bold yellow]Scope: an entry that names a `source` is read from
    ~/.config/yolo-jail/config.toml ONLY[/bold yellow] (plus that file's include_if_found
    files).  In yolo-jail.toml such an entry is a `yolo check` error: a
    workspace config travels with the repo and is agent-editable, so it must
    never decide which host files cross into the jail.  A SOURCE-LESS entry
    (inline content, or only defaults/managed) copies nothing from the host, so
    it is allowed at any scope — a repo may legitimately ship one.
    Within your own user config nothing is blocked: listing ~/.ssh/… there is
    your call.  The boundary is that the REPO cannot make it for you.

    A destination may not clobber a file yolo owns (~/.claude.json, ~/.bashrc,
    ~/.gitconfig, the yolo-* single-file mounts) or any yolo-composed agent
    surface (~/.claude/settings.json, ~/.config/mise/config.toml, …).
    Runtime support: podman gets everything.  "macos-user" has no bind mounts,
    so host bytes arrive by COPY into a root-owned tree the sandbox reads
    instead (since 2026-09-13).  A `source` naming a single FILE is delivered
    there normally.  A `source` naming a DIRECTORY is copied too (since
    2026-10-05), confined to the folder (a link leading outside it is left out),
    each file keeping its permission bits, and capped at 32 MiB and 4096 files
    and folders per entry, 64 MiB and 8192 per launch.  Over the cap the launch
    stops, naming the entry: split it into the files you need, or use podman, or
    the Apple Container runtime (runtime: "container"), which binds it read-only
    from version 1.1.0 (older versions, or one yolo cannot read, skip it with a
    warning naming the reason).  Source-LESS entries are unaffected
    on every backend: they copy nothing from the host to begin with.
    Example (~/.config/yolo-jail/config.toml):
      host_files = [
        "~/.npmrc",                    # raw, readonly
        "~/.pi/agent/models.json",     # json, readonly
        "~/.pi/agent/themes/",         # directory -> recursive copy
        # path + codec both inferred:
        { source = "~/.config/starship.toml", managed = { add_newline = true } },
        { path = "~/.config/ripgrep/config", content = "--max-columns=200\n--smart-case\n" },
      ]
    Each entry is a string or a table.  A long table entry reads better as its
    own [[host_files]] table.  One file uses one form: TOML refuses an inline
    list and [[host_files]] tables for the same key.
    Example (~/.config/yolo-jail/config.toml):
      [[host_files]]
      path = "~/.config/mytool/settings.json"
      mode = "capture"
      defaults = { telemetry = false, theme = "dark" }
      managed = { telemetry = false }

  [bold]host_import_exclusions[/bold] (map of surface address to JSON Pointer array): Omit exact
    object members from imported user host config bytes for the selected surface. This is a
    user-scope-only, subtractive filter; workspace config cannot set or extend it. A target
    must name a known object-codec surface, and a non-empty policy is allowed only when
    host_management is unset or "none". Missing members do nothing. It does not filter pack,
    default, computed, managed, captured, session-home, or yolo-rendered baseline bytes, and
    it never edits the host file. It applies on the next launch that stages and renders the
    policy. Example (~/.config/yolo-jail/config.toml):
      [host_import_exclusions]
      "claude/settings" = ["/hooks", "/statusLine"]

  [bold]host_wrappers[/bold] (boolean): Generate launch wrappers for host agents.
    [bold]Default: ON when host_management is "own", otherwise off.[/bold]  You usually
    do not write this key at all — `own` means yolo composes an agent's config file
    whole, and a config file cannot carry a credential (api_key_env_name holds a
    variable's NAME), so without a wrapper on your PATH a bare `claude` would get the
    config and none of the environment it assumes.  Declaring `own` and nothing else
    used to leave exactly that half-configured host, and `yolo doctor` said nothing.
    An explicit [bold]false[/bold] still wins: if you want yolo to own your config files
    and refuse to have anything put on your PATH, say so and it is honored.
    Only a WRITTEN "own" enables them: an unset host_management ("none") never does,
    so no PATH claim lands on a machine that declared nothing.
    When on, `yolo host apply` writes one small wrapper per
    program your selected packs install into
    [bold]~/.local/share/yolo-jail/bin/wrap[/bold], each a three-line `exec` into
    `yolo host -- <program>` that names yolo by its full path.  Put that directory
    FIRST on your PATH and a bare
    `claude` (or `pi`, `codex`, …) composes its environment — Bedrock flags, the
    credentials from `env`, any unsets — the same way `yolo -- claude`
    does inside a jail.

    [bold]It must be PREPENDED[/bold], ahead of ~/.local/bin: a wrapper only works if
    it is found before the real binary, and claude's own installer writes
    ~/.local/bin/claude.  yolo PRINTS the line and never writes it: your shell rc is
    yours, so add it there yourself, below any line that puts ~/.local/bin on PATH.
      export PATH="$HOME/.local/share/yolo-jail/bin/wrap:$PATH"
    `yolo check` says whether it took effect.

    Wrappers are generated for [bold]every[/bold] program a selected pack installs, whether
    or not that program needs any environment today.  That is deliberate: the
    directory is an addressable launch surface, so `<wrap dir>/claude` is a path
    a script or an IDE's "agent binary" setting can point at and rely on
    existing — which is also the answer whenever PATH is not consulted at all.
    An IDE or desktop launcher never reads your shell rc, so give it that full
    path: the wrapper starts yolo by its full path too.  For a program outside
    yolo's floor (one whose pack [bold]host_floor[/bold] leaves out, for one), that
    launcher also needs [bold]host_path[/bold] to name the program's folder;
    `yolo check` says when.  Any other program a pack declares runs from the
    floor or the launch stops, so no folder changes it.
    A pack that installs no program (a loophole-only pack) gets no wrapper.

    Enabling this makes yolo a runtime dependency of every wrapped launch: a
    broken yolo or an unparseable config takes the wrapped program down with it.
    The real binary is still behind the wrap dir on PATH, and invoking it by
    absolute path still works.

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.toml).  The key
    puts generated executables at the FRONT of your PATH, and a workspace config
    travels with the repo and is agent-editable, so it must never make that
    claim for you.  A workspace value is a `yolo check` error, and is never read.
    `yolo check` also tells you, every run, when the wrap dir exists but is not
    actually on your PATH.
    Example (~/.config/yolo-jail/config.toml):
      host_wrappers = true

  [bold]host_apply_on_launch[/bold] (boolean): Re-check and synchronize the host render at a wrapped launch.
    Default true when [bold]host_wrappers[/bold] is true; otherwise false.  `yolo host apply`
    writes into your real home once, so without re-checking, what is in your agents'
    config files and what your packs NOW say drift apart in silence.  With this enabled,
    a launch through a generated wrapper (see [bold]host_wrappers[/bold] above) checks first:
    if a re-apply would change nothing it execs straight through; if drift is detected
    under active host management (`own`), it automatically synchronizes
    host configuration before launch (printing `yolo host: synchronized host configuration (<targets>)`
    to stderr) and execs without pausing for confirmation.

    Interactive confirmation is reserved for first-time adoption that would overwrite
    unmanaged host keys:

      nothing would change      silent; the agent starts as usual.
      a configured pack cannot  renders NOTHING, names each pack with why and the
      be resolved, or its       remedy (for a git pack, the fetch this launch already
      manifest has problems     tried; `yolo pack install` retries it; for a manifest,
                                the problems, which `yolo pack lint` re-checks), and
                                REFUSES the launch: an incomplete pack set is never
                                applied, and no launch runs on one, at any notch.
      an apply would ask        renders NOTHING, prints each question (a skills or
      something                 briefing adoption, a dropped pack's retire, a missing
                                declared dependency) and `yolo host apply --assert`
                                to answer them, and the agent launches.  The launch
                                never asks through a hidden prompt, and another
                                pack's missing tool never stops this agent.
      safe managed changes      auto-applied silently; notice printed, agent launches.
      first apply overwriting
      unmanaged keys, terminal  shows what would change and prompts for confirmation.
      first apply overwriting
      unmanaged keys, off-TTY   REFUSED, naming the commands that fix it.  No flag or
                                variable approves it (below).
      something cannot be       in the launched program's own configuration: REFUSED,
      written (a pack failed    naming it and the fix.  Anywhere else: the rest is
      to render, or a file is   applied, the failure is named with its fix, and the
      a link into a missing     program launches — pi's broken settings.json never
      directory)                stops claude.
      cannot tell               execs.  A malformed pack, an unreadable home or a
                                concurrent apply is not something a launch may
                                stop over.

    A host launch takes no approval: `yolo host` refuses --accept-config-changes,
    and no environment variable grants one.  Dropping MCP servers yolo does not
    declare, on a first apply, is a one-way door kept behind a terminal, so a
    scripted launch that meets it answers it once, where a terminal can:
      yolo host apply --assert
      claude --print ...

    What it compares is the RENDER, not your config — so a file you hand-edited is
    caught even though nothing in `packs` moved.  Concurrent launches serialize on
    a per-home lock, and one that cannot take the lock execs rather than waiting.

    [bold]Coverage:[/bold] only launches that go through a generated wrapper.  An agent
    started by its real binary, by an IDE extension or by a desktop app is not
    observed and runs against whatever the last explicit apply left.  That is the
    same boundary [bold]host_wrappers[/bold] has, and `yolo check` reports both.

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.toml).  The key lets a
    launch WRITE INTO YOUR REAL HOME, and a workspace config travels with the repo
    and is agent-editable, so it must never make that claim for you.  A workspace
    value is a `yolo check` error, and is never read.
    Example (~/.config/yolo-jail/config.toml):
      host_apply_on_launch = true

  [bold]host_management[/bold] ("none" | "own"): Who owns the config files yolo renders
    into your REAL home.  Default [bold]"none"[/bold] -- yolo writes nothing there until you
    write "own".

    Ownership is DECLARED here, never inferred from where a file happens to live.
    The value selects the surface mode the host notch renders in:

      "none"    yolo writes nothing.  `yolo host apply` REFUSES, naming this key,
                and a wrapped launch has no render to re-check, so
                [bold]host_apply_on_launch[/bold] becomes a no-op rather than a nag.
                This is also what an UNSET key means.
      "own"     yolo owns the file -- it is derived output, composed whole from
                your packs and reproducible by deleting it and applying again.
                Your edits are CAPTURED, into a store beside the provenance record
                at ~/.local/share/yolo-jail/host-capture/, and re-applied on top of
                every later render -- so the file stays yours to edit even though
                yolo composes it.  The first owned render ADOPTS what the file
                already holds, and copies the file as it found it once, into
                ~/.local/share/yolo-jail/archive/config/.  A key you keep by hand
                is captured that way, and belongs in a pack: once it is captured,
                `yolo config promote` declares it into your local pack (under
                "none" nothing is captured, so there is nothing to promote).
                `yolo config reset <agent>` is the way to discard captured edits,
                and it works host-side under this value alone.

    [bold]"assert" is RETIRED.[/bold]  It was shared ownership: yolo rewrote the keys your
    packs declare and left the rest.  A config that still says "assert" is REFUSED,
    with a message naming the two values left -- `yolo host apply`, a wrapped
    `yolo host` launch, `yolo pack update` and every jail launch stop on it, and
    `yolo check` reports it.  Write "none" (or delete the key) or "own".  A home
    yolo wrote into under "assert" is left exactly as it was: nothing rewrites it
    under "none", a jail still reads the keys yolo wrote there as yolo's rather
    than yours, and "own" takes it over with the one-time copy above.

    [bold yellow]The key enables the mechanism.  It does not grant the approval.[/bold yellow]  Same ruling
    as [bold]host_apply_on_launch[/bold] above: it selects HOW the host renders, and every
    individual write still goes through the confirmation it always did.

    Under "own" the file is derived and belongs in .gitignore -- what goes in the
    dotfiles repo is the pack.

    [bold]--revert[/bold] (`yolo host apply --revert`) takes yolo back out of your home: it
    removes the values yolo wrote, on the authority of the records it keeps beside
    them, and deletes those records and its capture store for each file -- so a
    later owned apply is a FIRST apply again.  A value you set yourself is never
    touched: not one beside yolo's inside a setting yolo also writes (your own
    variable in `env`), and not one yolo wrote that you have changed since (a
    default, a model you picked).  The dry run names each value it keeps, and why.
    It runs under "none",
    the default, which is how a home yolo wrote into under "assert" (or under
    "own", before you switched back) becomes purely yours again.  It is a dry run
    until --assert, and it REMOVES what yolo wrote rather than restoring what was
    there before.  It keeps a default that is an empty object or list, such as
    pi's empty `providers` object, since that is the shape the agent's file needs, and
    names each one.  Refused under "own" (the next apply would compose those keys
    back -- set "none" first, or delete the file).

    An UNSET key is the default, not a third value, and it bites in exactly one
    place: `yolo apply --sealed` refuses while it is unset, beside the undeclared
    inputs it already refuses for.  An environment whose host-ownership contract is
    unstated is not sealed.

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.toml).  The key decides
    whether yolo may write your real home at all, and a workspace config travels
    with the repo and is agent-editable, so it must never make that claim for you.
    A workspace value is a `yolo check` error, and is never read.  A user config
    that cannot be READ yields "none" -- a declaration nobody could read has granted
    nothing -- as does an absent key.
    Example (~/.config/yolo-jail/config.toml):
      host_management = "own"
    `yolo config set host_management own --user` writes it.

  [bold]promotion_target[/bold] ("local" | "pack:<name>"): Where `yolo config promote`
    writes when you omit `--to`.  Default [bold]"local"[/bold], the conventional personal
    pack at ~/.config/yolo-jail/local/.

    Set this when you maintain a named personal pack instead of the conventional
    local one:
      Example (~/.config/yolo-jail/config.toml):
        promotion_target = "pack:matt"

    The named pack must be configured and writable when you promote; yolo checks
    that at the promotion itself.  [bold]--to[/bold] always overrides this default for one
    command.  (`--to host` is retired with host_management "assert", and refused.)

    [bold yellow]Scope: user config only[/bold yellow] (~/.config/yolo-jail/config.toml). Captured
    settings are personal, and a workspace is writable by the agent running in its
    jail, so a workspace config cannot redirect their destination. A workspace
    value is a `yolo check` error and is never read.

  [bold]shipped_skill_prefix[/bold] (string): A word every skill yolo ships starts with.
    Default: unset, and shipped skills carry no marker.  With it set, yolo's
    built-in skills and the skills of every shipped pack are delivered as
    `<prefix>-<skill>`, in a jail and at the host alike, and the briefing names
    them that way:
      shipped_skill_prefix = "yolo"     # configuring-the-jail -> yolo-configuring-the-jail

    The value is lowercase letters, digits and single hyphens.  A skill of yours
    that overrides a built-in one still does, under either name.

    [bold yellow]Scope: user config only[/bold yellow].  A workspace value is a `yolo check` error
    and is never read.  Takes effect at the next launch or `yolo host apply`.

  [bold]agent_updates[/bold] (boolean, "launch", "next-launch", or object of pack name -> one
    of those): Keep agent CLIs current.  Default TRUE -- absent means on.
    An AGENT dependency is a program yolo installs so a coding agent can run: the
    agent CLIs themselves, and the MCP servers they drive.  Nobody's build
    reproduces against one, so a six-week-old copy is a defect rather than a
    guarantee, and yolo keeps them current.  A PROJECT dependency -- `install.mise`,
    `install.nix`, anything the work in /workspace builds against -- is the opposite
    and is never touched by this.

    WHEN AN UPDATE HAPPENS: when you type the agent's name.  The generated
    launcher checks at most once an hour per program, updates if it is due, then
    execs the real binary.  A jail that never starts an agent never touches the
    network for one, and a launch on its own updates nothing.  Failure is scoped
    to that one command: offline with the agent installed runs what is there;
    offline with it absent fails, naming the network.  No jail refuses to boot
    over this.

    TURNING IT OFF freezes the agents at whatever is installed.  `yolo pack
    update` still refreshes them on demand -- it is the only thing that ignores
    this key, because it is an act you performed.

    WHEN AN ADD-ON REFRESH RUNS: "launch" or "next-launch".  Some agents keep
    add-ons beside the program, and their pack declares a refresh for them:
    pi's runs `pi update --extensions`.  By default ("launch", the same as true)
    the refresh runs when you type the agent's name, before the agent starts,
    at most once an hour and for at most a minute.  "next-launch" runs it in the
    background instead: the agent starts at once, the refresh runs while you
    work, and the next launch runs what it installed.  The launch says so in one
    line naming the refresh's log, ~/.local/state/yolo/refresh/<agent>.log, and
    a background refresh that fails, or does not finish, is reported once, at
    a later launch.  Only that refresh moves.  The agent's own update, its MCP
    servers, and add-ons your settings name for the first time still finish
    before the agent starts.  While a background refresh runs, pi may show its
    own "updates available" notice; the next launch has them.  A jail that
    exits while the refresh runs stops it and leaves its lock behind: for ten
    minutes every jail sharing those add-ons skips its refresh, and a launch
    whose settings name a new add-on first waits up to a minute for that lock.
    A launch after that runs the refresh again.  `yolo host` runs no add-on
    refresh, so there "next-launch" means the same as true.

    EXTENSIONS YOLO BUILDS FOLLOW THE SAME VALUE.  An extension a pack declares
    with a `source` is built on the host and copied into each fresh jail.  Under
    "next-launch" a fresh launch hands it the build this machine already has and
    starts one background advance, which checks and builds it while you work; the
    launch names its log, ~/.local/share/yolo-jail/logs/background-advance.log,
    and the next launch says what it built, or that it failed and when it is
    tried again.  An extension with no build yet uses its fallback, or is built
    before the jail starts.  The owning agent's entry decides first, then the
    entry of the pack that declares the extension, then "*".  On Apple Container
    and at `yolo host`, it still updates at the launch, and the launch says so.
    macos-user builds no tree and uses the extension's fallback.

    IT GOVERNS YOLO'S UPDATER, NOT THE AGENT'S OWN.  An agent that ships a
    self-updater runs it on its own terms, and yolo does not suppress one.  Claude
    Code, Copilot and agy all do: each comes from its vendor's own installer and
    updates itself on its own schedule, so `agent_updates = false` does not freeze
    them, and yolo cannot say which version of any of them ran -- its install
    record names only what yolo itself installed.  To freeze Copilot too, set
    COPILOT_AUTO_UPDATE=false in the jail (an `env` entry).  Copilot's own
    `autoUpdate: false` setting is not enough: it stops only copilot's downloads,
    and copilot still runs the newest copy in its package caches, one of which,
    in a jail, is under the ~/.cache every jail on the machine shares.  For
    Claude Code, set DISABLE_AUTOUPDATER=1.

    The map's keys are PACK names, not binary names: one pack may install more
    than one program, and the pack is the thing you selected.  A specific key
    beats "*"; "*" beats absence.  A pack cannot opt itself out -- it declares HOW
    to update itself, never whether to.

    USER SCOPE ONLY.  /workspace is writable by whatever runs in the jail, so a
    workspace value would let an agent freeze its own updates.  A workspace value
    is a `yolo check` error, and is never read.
    Example (~/.config/yolo-jail/config.toml):
      agent_updates = false
    Example (~/.config/yolo-jail/config.toml):
      agent_updates = { "*" = true, claude = false }
    Example (~/.config/yolo-jail/config.toml):
      agent_updates = { pi = "next-launch" }

  [bold]host_floor[/bold] (boolean, or object of pack name -> boolean): Keep your agents
    installed for `yolo host`.  Default TRUE -- absent means on.
    The HOST AGENT FLOOR is yolo's own copy of every agent CLI your selected packs
    install, kept in ~/.local/share/yolo-jail/host-floor.  `yolo host -- <agent>`
    runs that copy by its full path, so the same agent starts whether you typed
    the command in a terminal or a Waybar widget, cron job or IDE started it with
    a PATH of its own.  It is on no PATH of yours: your shell, and any copy you
    installed yourself (~/.local/bin/claude, Homebrew's), are left alone, and
    `yolo check` names such a copy as not run by `yolo host`.
    WHEN IT INSTALLS: every `yolo host -- <command>` first installs every
    program your selected packs declare that is missing, as a jail does, and
    stops (exit 1) when one cannot install; YOLO_ALLOW_MISSING_PROGRAMS=1 starts
    the command anyway and lists what is missing.  Under
    `host_management = "own"` `yolo host apply --assert` installs them too,
    printing what it does (under "none" that apply writes nothing).  Selecting
    the pack is the consent; nothing asks.  An npm agent runs on the floor's own
    Node, the official release checked against its published checksum; an
    agent with its own installer comes from the
    machine's `yolo capture` of it: a jail's, on a Mac the macos-user sandbox
    account's, or on Linux with no container runtime one made on this machine
    with its installer confined by Landlock.  Where the floor cannot hold an
    agent -- an installer agent on a Mac before `yolo yolo-account create`, or on Linux
    with neither a container runtime nor Landlock, or a machine without the
    dynamic loader the agent needs (NixOS without nix-ld, a musl system) -- the
    launch stops, saying why and what changes it; it never runs a copy from your
    PATH instead.  An agent whose vendor publishes no build for this machine is
    not the floor's to hold, and `yolo host` looks for it on your PATH, saying
    so.  The floor keeps them current the way a jail does, at most once
    an hour when you start one; an agent with its own installer is captured
    again once its capture is a day old, and only a newer release is installed.
    `agent_updates` freezes both the same way.
    A pack set to false here has no floor entry: `yolo host` installs nothing for
    it and looks for its agent on your PATH, saying so -- the way to keep using
    a copy you installed yourself.  Under "own" the next
    `yolo host apply --assert` removes the floor's copy; under "none"
    `yolo check` and the launch name the command that removes it by hand.
    USER SCOPE ONLY.  It decides which programs yolo installs on your machine, so
    a workspace value is a `yolo check` error, and is never read.
    Example (~/.config/yolo-jail/config.toml):
      host_floor = false
    Example (~/.config/yolo-jail/config.toml):
      host_floor = { "*" = true, claude = false }

  [bold]host_path[/bold] (list of folders): Folders `yolo host` searches after the PATH it was
    started with.  Default: none.
    yolo looks for the programs your packs need (`rg` for the guardrails pack, a
    pack's recipe-less `program`, an agent outside the floor -- see [bold]host_floor[/bold]) and
    for the command you name with `yolo host --` on the PATH it was started
    with -- it cannot know where you keep your tools any other way.  A
    terminal's PATH usually has them; a Waybar button, a cron job or a hotkey
    launcher often hands yolo only
    /usr/bin:/bin.  Each folder listed here is added AFTER that PATH, in the order
    written, unless it is already on it, so it fills in for a launcher that lacks
    it and never changes what your own PATH finds first.  The same folders reach
    the agent's PATH, before yolo's floor, so the agent's own commands find them
    too.  With no PATH at all, yolo checks these folders alone, and the agent
    gets the usual system folders ahead of them.
    Nothing else is added: yolo guesses no folder of its own, and runs no mise
    command.  To reach mise's tools from every launcher, list its shims folder.
    It does not reach the container runtime yolo boots jails with, `yolo capture`
    included: that is still found on the PATH yolo was started with.
    WHEN SOMETHING IS MISSING, yolo prints one line naming the program, the pack
    that needs it, the whole PATH it searched with this key's part marked, and
    this key as the fix, naming a common folder such as ~/.cargo/bin when one of
    them has the program.  That folder is only a hint: yolo never runs or counts
    a program it found there.  `yolo host apply` and `yolo check-deps` print it
    for any program your packs need, and `yolo host --` for the command it
    starts.  A launch checks the programs your packs need only when
    [bold]host_apply_on_launch[/bold] is on (off unless you set it, or turn on
    [bold]host_wrappers[/bold]); with it off, a missing one prints nothing at
    launch.  `yolo check` shows the PATH it read, which is the PATH of the shell
    you ran it in, plus these folders.
    Each entry is an absolute folder or starts with ~/.  A relative folder, ~user/,
    and any entry with `$` or `:` in it are refused: yolo expands no variable.
    A refused entry is ignored, and the line above and `yolo check` name it, with
    the fix.  A folder that does not exist is kept, and `yolo check` says so.
    USER SCOPE ONLY.  A folder here decides which program `yolo host` runs, and a
    workspace config travels with the repo, so a workspace value is a `yolo check`
    error, and is never read.
    Example (~/.config/yolo-jail/config.toml):
      host_path = ["~/.cargo/bin", "~/.local/share/mise/shims", "/opt/homebrew/bin"]

  [bold]provisioners[/bold] (object): The order yolo picks a way to install a program in.
    Default: none -- each pack's own recipe first, then your package manager.
    A pack declares every way it knows to install its program: its own recipe
    (its npm package, or its vendor's installer), and the package each manager
    names it by.  When `yolo host apply` or `yolo check-deps` finds a program
    missing, yolo picks the first of these, in this order, that is on your PATH
    and has a recipe for it, and offers or prints that command.  Names: pack (the
    pack's own recipe), apt, dnf, pacman, brew, nix.
    "host" is the order at the host.  It only re-ranks: anything it leaves out
    is still tried after it, in yolo's default order, so ranking brew first
    leaves a program brew has no recipe for with its own installer.  A manager
    not on your PATH is skipped.  The report says when your order chose the
    command, and still prints the other as the alternative.  A manager keeps
    its own release cadence, which can lag the vendor's own installer.
    THE FLOOR: an agent your order gives to a manager on your PATH has no
    [bold]host_floor[/bold] entry, since the floor installs the pack's own recipe;
    `yolo host -- <agent>` runs the manager's copy on your PATH, saying why, and
    under "own" the next `yolo host apply --assert` removes the floor's copy.
    nix is the exception for now: the floor keeps an agent ranked to nix on its
    own recipe, and `yolo check` warns, so nix supplies only what the floor does
    not hold, such as a pack's recipe-less `program`.
    "per_package" gives one program its own order, replacing "host" for it;
    an order naming a provisioner no selected pack has a recipe for is a
    `yolo check` error.
    No order is read inside a jail, whose agents always come from the pack's
    own recipe.
    USER SCOPE ONLY.  It decides what yolo installs on your machine, so a
    workspace value is a `yolo check` error, and is never read.
    Example (~/.config/yolo-jail/config.toml):
      [provisioners]
      host = ["brew"]
    Example (~/.config/yolo-jail/config.toml):
      [provisioners.per_package.claude]
      host = ["brew"]

  [bold]perf_logging[/bold] (boolean): Record every launch's timings, quietly.  Default FALSE.
    The persistent, SILENT form of `--timing`: every span (probes, image load,
    the child window, the whole shutdown chain) is appended to
    <workspace>/.yolo/logs/host-perf.log as it happens (for `yolo host --` and `yolo host
    apply`, to ~/.local/share/yolo-jail/logs/host-notch-perf.log, since a host
    command has no workspace), and NO report is printed at
    exit -- one dim line names the file, and that is all.  Any span over a
    second still names itself on stderr the moment it ends, so a slow launch
    says who is holding it while you wait.

    RECORDING IS NOT REPORTING.  This key, and YOLO_TIMING=1 / YOLO_VERBOSE=1 in
    the environment, are the always-on spellings: they record in silence,
    because a ~25-line table at every jail quit scrolls away whatever was on
    screen.  To SEE a launch's table, ask for it on that launch: `yolo --timing
    -- ...` or the global `yolo --verbose -- ...`, which also turn on the
    in-container breakdown; at the host, `yolo host --timing -- ...` or `yolo
    host apply --timing`.  Read the file any time for the launches you did not
    ask about.

    WHAT IT COSTS: about 2 KB and 35 lines per launch, capped at ~110 KB per
    workspace (the file keeps the last 50 runs and trims the rest at open), and
    tens of milliseconds of wall clock.  The line count is structural -- one
    start/end pair per span -- so a 30-second shutdown writes the same 2 KB as a
    fast one.  Output costs nothing: nothing is printed unless you ask.

    USER SCOPE ONLY.  It is read at the very top of a launch, before any
    workspace config is loaded, so a workspace value is never consulted -- and
    /workspace is writable by whatever runs in the jail.  A workspace value is a
    `yolo check` error.
    Example (~/.config/yolo-jail/config.toml):
      perf_logging = true

  [bold]macos_user_mode[/bold]: [bold yellow]REMOVED[/bold yellow] — a config carrying it is REFUSED.  Which
    account a Seatbelt sandbox runs as is its setup's `run_as` now:
      yolo config set setup seatbelt-yolo-account --user   # was "account"
      yolo config set setup seatbelt-self --user           # was "self"
    then `yolo config unset macos_user_mode --user`.  seatbelt-self runs the
    agent as you, with no account, admin setup or access grants, under a
    deny-by-default Seatbelt profile that opens the workspace, the agent's own
    home in .yolo/setups/<setup>/home and the tools, and denies the rest of your files, your
    keychain and your other processes; each launch gets its own TMPDIR (see
    macos_user_shared_tmp), and every such launch says so first.

  [bold]macos_user_shared_tmp[/bold] (boolean): Open the shared /tmp to a run-as-you macos-user jail.  Default FALSE.
    Under a setup that runs as you (seatbelt-self), the agent cannot read or write the shared /tmp
    (/private/tmp): a tool that writes there fails with "Operation not permitted",
    and the agent is told to use $TMPDIR, its launch's own temporary directory.
    true opens /tmp again, read and write, for tools that need it; the agent can
    then read the files your other programs leave there.  Every such launch says
    so.  Only a Seatbelt setup that runs as you reads it.

    USER SCOPE ONLY.  It is read from your user config alone, so a workspace value is
    a `yolo check` error and is never consulted -- and /workspace is writable by
    whatever runs in the jail.
    Example (~/.config/yolo-jail/config.toml):
      macos_user_shared_tmp = true

  [bold]share_host_fonts[/bold] (boolean): Share your own font folder, read-only, with a jail that does not run as you.  Default FALSE.
    A container jail gets ~/.local/share/fonts and ~/.fonts from a Linux host, or
    ~/Library/Fonts from a Mac, mounted read-only under the jail's
    ~/.local/share/fonts, where its fontconfig finds them; a folder that resolves
    outside your home or into a credential folder is not shared.  A macos-user
    jail in the separate-account mode reads a copy yolo keeps of the readable
    files in ~/Library/Fonts, refreshed when they change and removed when you
    turn this off; the sandbox user is given no access to your home.  Every such
    launch names each folder it shares; a folder that does not exist is skipped
    with a line.  The run-as-you mode reads ~/Library/Fonts always, and
    `yolo host` is you, so neither needs it.

    USER SCOPE ONLY.  It is read from your user config alone, so a workspace value is
    a `yolo check` error and is never consulted -- and /workspace is writable by
    whatever runs in the jail.
    Example (~/.config/yolo-jail/config.toml):
      share_host_fonts = true

  [bold]local_clones[/bold] (list of paths): Clones of yours that a published patch branch URL is built from.  Default [].
    A pack names its patch branch by its published URL.  When that URL names the
    same repository as a remote of a clone yolo knows, yolo builds from that
    clone with the newest-copy rule: your local branch when it is ahead or has
    diverged, the published tip when your branch is behind, and the best copy
    when the fetch fails.  The provenance line names the clone it used.  A
    clone answers only for a branch name it has fetched from the matching
    remote (refs/remotes/<remote>/<branch>), and only when that remote
    fetches from the same repository (its first url, after insteadOf); a
    branch it has only locally or on another remote is built from the URL,
    and the line says why.  Any
    path a pack is read from that lies in a git clone registers that clone
    already, so list here only a clone that holds no pack, such as a fork of an
    upstream tool.  "~" is expanded.  When two clones match one URL, an entry
    here wins over a pack's clone, then the first in config order.  An entry
    that is not an absolute path, does not exist, is not in a git clone, or
    whose clone has no remote is a `yolo check` error, and the launch,
    `yolo host`, `yolo host apply` and `yolo pack install`, `update` and
    `status` refuse.

    USER SCOPE ONLY.  A workspace config must not point yolo at host paths, so a
    workspace value is a `yolo check` error.
    Example (~/.config/yolo-jail/config.toml):
      local_clones = ["~/src/pi"]

  [bold]update_check[/bold] (boolean): Enable update checks and notices.  Default TRUE.
    Every ordinary host command reads the cached answer.  For a release-based install,
    normally once a day it starts a detached request to GitHub's releases API;
    the first automatic request waits for a terminal so its disclosure is
    printed before the network is touched.  Source installs are checked only
    by an explicit `yolo update --check` / `yolo update`, because that operation
    runs Git against the source checkout.  It may fetch commit objects, but
    moves no ref and changes nothing `git status` shows.

    When an update exists, one line under the startup banner says so -- only on
    a terminal -- and a safe, self-contained interactive launch offers to
    update and relaunch.  Homebrew and from-source installs are self-contained.
    Development runs use a matched bundle: run `just build-dev-bundle` and invoke its
    printed launcher path, or use `just install` for the installed bundle. An exported
    YOLO_REPO_ROOT no longer selects launch sources; unset it before invoking a normal
    launcher.

    `false` turns off the background check, the notice and the offer; explicit
    `yolo update` commands still work.  YOLO_NO_UPDATE_CHECK=1 is the per-shell
    spelling.  Automatic behavior never runs in a jail or in CI.

    USER SCOPE ONLY.  It is read on every host command, before any workspace
    config is loaded, and /workspace is writable by whatever runs in the jail.
    A workspace value is a `yolo check` error.
    Example (~/.config/yolo-jail/config.toml):
      update_check = false

  [bold]workspace_readonly[/bold] (array of strings): Workspace sub-paths to overlay as read-only.
    Each entry is a relative path inside the workspace (no leading /, no ..).
    Mounted on top of the writable /workspace volume so agents cannot modify
    those paths. Use this to protect host-executed code that lives in the
    workspace repo (e.g. the yolo-jail src/ directory itself), and the git and
    agent control-plane files the host executes but `git diff` never shows you
    (.git/hooks, .git/config, .git/info, .claude, .mcp.json).
    Example (yolo-jail.toml):
      workspace_readonly = ["src", "flake.nix", "Justfile"]
    Example (yolo-jail.toml):
      workspace_readonly = [".git/hooks", ".git/info", ".claude", ".mcp.json"]
    Note: locking .git/hooks WITHOUT .git/config is defeated by core.hooksPath,
    which repoints hooks elsewhere -- lock the pair or neither.  Locking
    .git/config costs `git push -u` and branching from a remote-tracking ref
    (both write branch.*); `git push origin HEAD` and branching from a local
    ref need no config write.  If you lock .git/hooks, give hooks somewhere
    tracked to live first: `git config core.hooksPath .githooks`.
    BACKENDS: enforced on podman.  Enforced on Apple Container from version
    1.1.0 (check with `container --version`); on an older version, or when
    yolo cannot read the version, a loud warning names the paths, which stay
    writable.  So does the workspace config file, which the key also locks,
    and the warning does not mention it.  On macos-user there are no mounts
    at all, so entries are rendered as `(deny file-write* (subpath ...))` lines
    in the Seatbelt profile instead, the workspace config file among them --
    same policy, different mechanism.

  [bold]per_side_paths[/bold] (array of strings): Workspace sub-paths kept per side.
    Each entry is a relative path inside the workspace (no leading /, no ..).
    Each gets a per-workspace backing dir (under
    <workspace>/.yolo/setups/<setup>/home/venv-shadows/) shadow-mounted over it, so the
    host and the jail each see their own copy — for derived state that must
    not cross the host/jail boundary (interpreter symlinks, native builds).
    ".venv", "node_modules", and the venv path configured in the workspace's
    mise.toml are always shadowed automatically; list extra paths here (e.g. a
    workspace .cargo, or a monorepo's packages/*/node_modules -- the defaults
    are root-level only).
    Example (yolo-jail.toml):
      per_side_paths = [".cargo", "packages/web/node_modules"]
    Note: node_modules became a default on 2026-08-23.  A node_modules shared
    between a macOS host and a Linux jail is already broken for any package
    with a native build, so the two sides were never able to share it safely.
    Expect one extra install per side on the first launch after upgrading.
    BACKENDS: enforced on podman and Apple Container.  NOT enforced on
    macos-user -- per-side shadowing needs a mount namespace and that backend
    has none, so host and sandbox share these paths; a warning names your
    entries and each default the project uses.  There, uv alone is pointed at
    a venv of its own: UV_PROJECT_ENVIRONMENT=.venv-macos-user, unless you
    set it yourself.

  [bold cyan]NETWORKING: WHICH WAY IS WHICH[/bold cyan]
    Read this before writing any port key.  There are two directions, one key
    each, and [bold yellow]THE TWO KEYS PUT THE PORTS IN OPPOSITE ORDERS[/bold yellow].

      WHO CONNECTS   WHO LISTENS   Key                          Legacy entry order
      ------------   -----------   --------------------------   ------------------
      the host       the jail      machine.ports                "HOST:JAIL"
      the jail       the host      (nothing — dial by name)     n/a
      the jail       the host      machine.forward              "JAIL:HOST"
        ...same direction as the row above, but arriving on the JAIL's
           own localhost:<port> instead of on a hostname

    Read a row as "who dials whom", never as "which side owns the port".  Both
    keys are written in the jail's config and both name two ports; the only
    thing that tells them apart is the direction of the connection.

    In TOML each entry names its two ports, `host = …` and `jail = …`, so
    the order no longer matters there.  The legacy JSONC keys
    (`network.ports` and `network.forward_host_ports`) wrote them as strings in
    the opposite orders above:
    • `network.ports` was handed to podman's `-p` verbatim, and podman spells
      that flag HOST-side first.
    • `forward_host_ports` was yolo's own, and it was JAIL-side first, because
      the port you write is the one you are going to dial from in here.
    A transposed legacy entry usually does not error — it publishes or forwards
    the wrong port, and presents as a broken service.  Check the order first.

    [bold]There are TWO loopbacks, and that is the whole confusion.[/bold]  In
    bridge mode the jail has its own network namespace, so `localhost` /
    `127.0.0.1` inside the jail is the JAIL's loopback — always, no exceptions.
    The host's loopback is a different interface, reached by NAME:
    `host.containers.internal`.  `machine.forward` is the one thing that
    blurs them, and only for the ports you list: it copies a host port onto the
    jail's own loopback so `localhost:<port>` in here answers.

  [bold]network.mode[/bold] (string): Network isolation mode.
    "bridge" (default): the jail gets its OWN network namespace — its own
      loopback, per the paragraph above.  Not cut off from the host: see
      "Reaching the host with no config at all" below.  Both port keys are
      honored ONLY in this mode.
    "host": the jail shares the host's network stack.  The two loopbacks become
      one, so `localhost` works in both directions and NEITHER port key is
      needed — both are ignored, with a warning from `yolo check`.
    `yolo --network <mode>` overrides this key for one launch.

  [bold]machine.ports[/bold] (array of tables): [bold]HOST → JAIL.[/bold] Publish a
    server running INSIDE the jail so the host (and its browser) can reach it.
    The legacy JSONC key is `network.ports`.
    Each entry names `host` (the port on the host) and `jail` (the port in the
    jail).  It may also name `address`, the host interface to bind (any text
    with no ':' or '/'), and `protocol`, "tcp" or "udp".
    Example (yolo-jail.toml):
      [machine]
      ports = [
        { host = 3000, jail = 3000 },
        { host = 9000, jail = 90, address = "127.0.0.1", protocol = "udp" },
      ]
    A dev server on the jail's 0.0.0.0:3000 is then at localhost:3000 ON THE
    HOST.  The second entry is podman's -p "127.0.0.1:9000:90/udp".
    A server bound to 127.0.0.1 inside the jail is NOT publishable — bind
    0.0.0.0 in here, which is safe: the published port is the only way in.
    Bridge mode only.
    On macos-user every port the sandbox binds is already on the Mac's real
    interfaces; a REMAP is relayed by the launch (TCP only), which publishes
    whatever listens on the Mac's 127.0.0.1:JAIL, the sandbox's or yours.

  [bold]machine.forward[/bold] (array of tables): [bold]JAIL → HOST[/bold], arriving on
    the jail's own localhost.  Makes a host service answer at `localhost:<port>`
    INSIDE the jail, even one bound to the host's 127.0.0.1 (like `ssh -L`).
    The legacy JSONC key is `network.forward_host_ports`.
    Each entry names `jail` (the port you dial in the jail) and `host` (the port
    the host service listens on).  They are usually the same port.
    Example (yolo-jail.toml):
      [machine]
      forward = [
        { jail = 5432, host = 5432 },
        { jail = 8080, host = 9090 },
      ]
    The second entry makes the host's :9090 answer at localhost:8080 in the jail.
    [bold]Usually you do not need this.[/bold]  `host.containers.internal:<port>`
    already reaches the same service with no config and no socat.  Reach for
    this key only when something must literally see `localhost:<port>` — a
    hardcoded client, a tool with no host setting.
    Implemented with socat, so it needs socat on the host.  Bridge mode only;
    ignored (with a `yolo check` warning) when network.mode is "host".
    On macos-user a same-port entry needs nothing and a remap is relayed by
    the launch itself, with no socat.

  [bold cyan]Reaching the host with no config at all[/bold cyan]
    `host.containers.internal` is written into the jail's /etc/hosts by podman
    (169.254.1.2 today) and needs no key in this file.  It reaches the host
    itself AND host services bound only to the host's 127.0.0.1, because on a
    rootless podman yolo asks the network stack to forward the host's loopback
    in (--network=pasta:--map-host-loopback / slirp4netns
    allow_host_loopback).  This is how yolo's own host daemons are reached, so
    it is load-bearing, not best-effort.
    It was NOT true before 2026-08-17 — an agent "knowing" that the host's
    localhost is unreachable from a jail is remembering the old behaviour.
    What yolo decided rides into the jail as YOLO_HOST_LOOPBACK:
      requested   — the forwarding option went out; a service that does not
                    answer is a FAULT, not a limitation
      shared      — the jail shares the host's network stack, so the two
                    loopbacks are already one and `localhost` IS the host
      unsupported — yolo identified the stack and could not get it to forward
                    (a known limitation; upgrade passt)
      unknown     — no conclusion reached (rootful podman, unrecognised
                    backend, explicit network.mode, YOLO_NO_HOST_LOOPBACK)
    Only "unsupported"/"unknown" mean the forwarding may genuinely be absent.

  [bold]security.blocked_tools[/bold] (array): Tools to block inside the jail,
    and in the program `yolo host --` starts (from your user config only there).
    Each entry is a tool name, or a table that adds a message and conditions.
    Example (yolo-jail.toml):
      [security]
      blocked_tools = ["curl", { name = "grep", message = "Use rg", suggestion = "rg <pattern>" }]
    A tool name is a BARE NAME — a single PATH segment, no "/", "..",
    ":" or absolute path — because it names the FILE yolo generates in
    the block dir; a path-shaped name is refused.
    Default: EMPTY — core blocks nothing.  Until 2026-09-04 it blocked
    grep and find by default, a default that silently assumed the image
    bakes rg and fd; that is true of the container backends and false of
    macos-user, which bakes nothing, so the block removed a tool and
    pointed at a binary that did not exist.  The list now lives in the
    [bold]guardrails[/bold] pack — add "guardrails" to `packs` to get it:
      • grep conditionally blocked — only recursive invocations
        (``-r``, ``-R``, ``--recursive``, or bundles like ``-rn``).
        Pipe filters and single-file greps pass through.
      • find unconditionally blocked.
    Your own entries here are unaffected, and an entry naming the same
    tool as a pack's REPLACES it whole.
    Lists from several files merge.  An empty list (blocked_tools = []) drops
    every entry a lower file wrote.  A long table entry reads better as its own
    [[security.blocked_tools]] table, as in the flag example below.
    Conditional on the ALTERNATIVE existing: add ``replacement`` (a bare
    binary name) and the tool is blocked only when that binary is on the
    jail's PATH.  The two defaults set it (rg for grep, fd for find), so
    on a backend that bakes no image — macos-user, where tools come from
    ``install.nix`` or not at all — a jail without rg keeps working grep
    instead of losing it and being pointed at nothing.  An entry with no
    ``replacement`` always blocks, which is every custom entry.
    Exemptions: ``allow_flags`` (same pattern syntax) exempts an invocation
    even when block_flags match, or when the entry blocks unconditionally.
    It is scanned FIRST, so one allowed flag exempts the whole command.  This
    is what expresses "block unless limited" — block_flags matches on a flag
    being PRESENT and has no negated form.  Nothing yolo ships sets it.
    Conditional on FLAGS: add ``block_flags`` (array of shell case-glob patterns)
    to block only when argv contains a matching flag.  Absence means
    "always block" (find's default behavior).  Long options in
    block_flags match exactly; short patterns (starting with ``-``)
    match after any non-matching ``--*`` arg is skipped, so patterns
    like ``-*[rR]*`` catch ``-rn`` / ``-Rn`` without false-positive-ing
    ``--regex``.
    Example (yolo-jail.toml):
      [[security.blocked_tools]]
      name = "grep"
      message = "grep -r blocked; use rg"
      suggestion = "rg <pattern>"
      block_flags = ["-r", "-R", "--recursive", "-*[rR]*"]
    Bypass: Set YOLO_BYPASS_SHIMS=1 in scripts that need blocked tools.
    AT THE HOST: `yolo host -- <program>` renders the same blockers — the
    selected packs' and this list from your USER config, never a workspace's —
    into a directory yolo keeps (~/.local/share/yolo-jail/bin/block/<digest>) and
    puts it first on that program's PATH, saying so at every launch.  `replacement`
    is checked against that PATH, and YOLO_BYPASS_SHIMS=1 runs the program found
    behind each block on it (none found: the shim says so and exits 127).  Two
    things never meet a block there: a shell that resets PATH (a login shell:
    macOS's path_helper, Debian's /etc/profile) and an agent's own shell function
    of the same name (Claude Code's Bash tool defines grep and find, in a jail
    too).  `yolo host apply` starts nothing and blocks nothing.

  [bold]install.mise[/bold] (table): Extra tools installed via mise in the jail.
    Keys are mise tool names, values are version strings.  The legacy JSONC key
    is `mise_tools`.
    Default: {} — yolo ships no mise tool of its own. Every default runtime is a
    baked nix package instead (self-contained, present at boot, no first-use
    download).  (The `yolo init` template used to claim a `neovim` default here;
    there is none — see internal/config/config.go's defaultMiseToolsVals.)
    These are injected into the jail's global mise config (not workspace mise.toml).
    Deep-merged: user config adds tools, workspace config overrides versions.
    A tool written "off" (`[install.mise] <tool> = "off"`) drops the version a
    lower file pinned.

    [bold]Which of the three places does your tool belong?[/bold] They are not
    interchangeable, and picking by habit is the common mistake:
      • The PROJECT needs it to build (a language runtime, a linter CI also runs)
        -> [bold]/workspace/mise.toml[/bold]. Committed, so CI and non-jail users get it
        too, and `mise install` applies it with NO restart. Putting a project
        requirement in install.mise hides it where nobody outside a jail can see it.
      • YOU want it in every jail, but not on your host (an editor, a personal
        utility) -> [bold]install.mise in ~/.config/yolo-jail/config.toml[/bold]. This is the
        one thing no workspace file can express, and the reason this key exists.
      • It is available in nixpkgs at the version you want -> prefer [bold]install.nix[/bold].
        Costs an image rebuild, but the binary is self-contained and present at
        boot. Reach for install.mise when nix does not track what you need — a
        nightly channel, or a PyPI/npm-only tool (e.g. "pipx:some-tool").
    Once an install.mise entry stabilizes, consider promoting it to `install.nix`.
    Example (~/.config/yolo-jail/config.toml):
      [install.mise]
      neovim = "nightly"
      "pipx:some-tool" = "latest"
    `yolo config set install.mise.neovim '"nightly"' --user` writes the first entry.

  [bold]packs[/bold] (array): Everything a jail has beyond a bare shell — a coding agent
    and its config, shared skills, briefing prose.  [bold yellow]USER SCOPE ONLY[/bold yellow]: read from
    ~/.config/yolo-jail/config.toml directly, never from a workspace config.  A
    `packs` key in yolo-jail.toml is a `yolo check` error, because a workspace
    config travels with the repo and is agent-editable, so it must not decide what
    content (skills and briefing prose an agent then FOLLOWS) enters the jail.  A
    repo that wants to configure its own agents can just commit the files.
    `yolo pack add <handle>` and `yolo pack remove <handle>` edit this list.
    [bold]The packs yolo ships are selected by BARE NAME, and none is on by default:[/bold]
    Example (~/.config/yolo-jail/config.toml):
      packs = ["claude"]     # also: copilot, codex, opencode, pi, agy
    With no packs configured a jail has no coding agent, and says so at launch.  That
    is the honest default: activating agents nobody asked for would put six tools and
    their config files in every jail.
    Each entry is a HANDLE, the name config and yolo's own output use for a pack:
      claude              a shipped pack ("yolo/claude" means the same)
      local/<name>        the folder ~/.config/yolo-jail/packs/<name>
      <source>/<name>     the pack <name> inside a source that `pack_sources` names
      { git = URL }       a git repository that is one pack, whose handle is
                          <owner>/<repo>; `ref` picks a branch, tag or commit
      { pack = HANDLE }   one of the forms above, with `bare` or `namespace` set
    Only a shipped pack is named without a source.  A path is not a handle: name
    the folder that holds your packs in `pack_sources` instead.
    Example (~/.config/yolo-jail/config.toml):
      packs = [
        "claude",
        "local/house",
        "mine/review",
        { git = "https://github.com/acme/agent-pack", ref = "v2" },
      ]

      [pack_sources]
      mine = "~/dotfiles/packs"
    The "~/" is expanded against your home at load, so ONE config can name one pack
    tree on machines whose homes differ (/home/you vs /Users/you).
    [bold]Every name an agent sees for a pack starts with its NAMESPACE[/bold]: the source key
    for `<source>/<name>` (skill `review` of "mine/review" reaches agents as
    `mine-review`), the folder name for `local/<name>`, the repository's last segment
    for `{ git = URL }`.  A shipped pack has none.  `bare = true` on an entry or a
    source delivers the pack's names exactly as it wrote them; `namespace = "<word>"`
    on a `{ pack = … }` or `{ git = … }` entry picks another word.  When two entries
    would deliver one name, yolo refuses and names both; choose a namespace or set
    `bare` to fix it.  `yolo pack ls` shows each entry's handle and namespace.
    The legacy JSONC forms (a path, file://, git+ssh:// and { "source", "name" })
    are listed in LEGACY JSONC FORMAT.
    [bold]Order is precedence, in a jail and at the host alike:[/bold] where two packs set one
    key, the later wins.  Later means the order this list names them in (a shipped pack included, so list
    your own pack AFTER a shipped one it overrides), then the packs another pack pulled in
    through its `needs`, then ~/.config/yolo-jail/local, which is always last.
    A pack in a folder on this machine may be a tree of symlinks, the shape a dotfile manager (rcm,
    stow, chezmoi) deploys: its links are followed wherever they point and the targets
    delivered as files, in a jail and at the host alike.  A git pack's symlink pointing
    out of the pack is refused, because a repository you do not control must not be able
    to deliver a file from your machine.
    Host access =a reads-host file, a `mount` of a host dir, an installer program, or
    a host-prepending briefing.  EVERY pack's declared claims are honored, whatever its
    origin — shipped, local or fetched (git).  There is no approval prompt:
    selecting the pack in your config is the consent, `yolo pack footprint <ref>` is
    where to review what a pack claims before you select it, and each launch's banner
    lists what every loaded pack reads from the host.  A launch on the host fetches a
    git pack it has never fetched and re-fetches a BRANCH ref at most hourly, printing
    "Fetched pack …" / "Updated pack …" when content arrives or moves; a TAG or a full
    commit SHA is never re-fetched by a launch, so a pin is how to freeze a pack that
    carries host code (only an explicit `yolo pack install`/`update` follows a
    re-pointed tag).
    [bold]A pack written for a newer yolo:[/bold] a contribution holding a kind, a `via` or a
    field this yolo does not know is left out of every launch, which prints one line naming
    the pack, the contribution and the field; a field outside every contribution is ignored
    and named the same way.  A `blocked-tool`, `intercept` or `autonomy` contribution only
    restricts, so it is kept without the field instead.  `yolo check` warns about each one,
    `yolo host apply --assert` writes nothing while one is left out, and `yolo pack lint`
    refuses the field, so a misspelling is still caught.  `yolo features` lists what this
    yolo reads, such as patch-series, patched-extensions, kind:<kind> and via:<via>.
    A pack.json declares effects as a "contributes" list, one entry per effect with a
    "kind" from the closed set:
      program       a tool on PATH: {bin, via:"npm"|"installer"|"source"|"pack", package|url, flags}
                    — or {bin} with NO via, a NEED (see below the intercept entry).
                    yolo INSTALLS it, via a lazy launcher in ~/.yolo/bin/launch (last on
                    PATH, so it never shadows a baked binary).  Sole-owned by `bin`, so a
                    pack may declare SEVERAL programs (different bins) and each gets its
                    own launcher.
                    Also takes `protocols`: the wire protocols this program can be
                    POINTED AT, in preference order — the same names a provider files an
                    endpoint under (`["anthropic"]`, `["anthropic", "openai"]`), not the
                    `wire_api` dialect values.  It is the agent's half of the pairing a
                    provider and an adapter already declare, and it is what lets a launch
                    tell a provider this agent can use from one it cannot.  Omit it to
                    leave the agent UNCONSTRAINED: every provider then resolves directly,
                    which is what every pack did before the key existed.
                    Also takes `platform_switches`: [{platform, surface:"agent/name",
                    pointer:"/json/pointer"}] — settings in this program's OWN config
                    (a readsHost surface of this pack) that put the agent on a provider
                    platform by themselves, such as claude's
                    `/env/CLAUDE_CODE_USE_BEDROCK` in claude/settings for "aws-bedrock".
                    yolo removes one only where its own `yolo host apply` wrote it and
                    the file still holds that value; when the user's copy turns it on
                    (true, 1, yes, on) and the agent's selected provider is not of that
                    platform, the launch prints one line naming the key and both fixes,
                    and says so when the key is one `yolo host apply` wrote.
                    Also takes `platform_regions`: [{platform, region_env_name:[NAME...]}]
                    — the region variables this program reads on that platform, where it
                    reads fewer than the platform's providers list.  The region check then
                    counts only those for this agent: opencode's pack lists AWS_REGION
                    for "aws-bedrock", because opencode ignores AWS_DEFAULT_REGION, so a
                    launch delivering opencode only AWS_DEFAULT_REGION is refused.
                    via:"source" is a FORK: {bin, via:"source", fork_of:"<base pack>",
                    source:"git+https://…?ref=…", build:"<one command line>",
                    produces:[home-relative paths, one of them .local/bin/<bin>,
                    .npm-global/bin/<bin> or go/bin/<bin>]}.  The base pack keeps the
                    name, its launch flags, posture, profiles, briefing and skills; the
                    fork supplies only the bytes, and may add `platforms` and
                    `node_floor` but no other program field.  `source` is a git address
                    (file:// is refused: a directory has no revision).
                    via:"pack" is a program built from the pack's OWN tree: {bin,
                    via:"pack", from:"<pack dir>", run:"<file, relative to from>",
                    build:"<one command line>" (optional), prebuilt:{"<goos>/<goarch>":
                    {url, sha256}} (optional, used only when from is absent)}.  `from`
                    and `run` are required; `from` and `run` are refused on any other
                    program.  `yolo pack lint` warns when the source directory is empty.
                    A fresh launch builds it from that tree in a sealed build, on every
                    backend (on macos-user, for macOS), or fetches the prebuilt when from
                    is absent; `yolo pack build` runs the same build outside a launch.
                    A PATCHED fork adds `patches:"<pack dir>"`, a `git format-patch --base`
                    series yolo replays onto the UPSTREAM that `source` then names, so
                    what runs follows that upstream while the series applies and builds;
                    a newer upstream that conflicts keeps the last good build running.
                    `follow` picks a branch ref's commit: "release" (default, the newest
                    semantic-version tag), "release:<prefix>", or "head"; a tag or full
                    commit holds it.  `follow` is refused without `patches`.  `yolo pack
                    status` shows the series, the good build and what is pending; a launch
                    drops a patch upstream already holds.  `yolo pack series check [<pack
                    dir>]` says whether a local pack's series still applies, in a jail too.
                    A series that stopped fitting is rebased by hand: its error, `yolo pack
                    status` and the check print the git commands, commits filled in, for
                    you or an agent to run.  `yolo pack lint` reads the
                    series, and `--online` checks its upstream.  Needs git 2.40 on the
                    host.  Export a series from a fork:
                    git format-patch --base=$(git merge-base <upstream>/main HEAD) \
                        -o patches <upstream>/main..HEAD
      blocked-tool  {bin, message, suggestion, replacement, flags} — refuse a tool
                    inside the jail, and in the program `yolo host --` starts, and
                    print an alternative.  `flags` limits the block to matching argv
                    (absent = always); `replacement` names the binary the suggestion
                    points at, and the block is generated ONLY when that binary is on
                    the agent's PATH — so an agent without the alternative keeps the
                    original tool instead of losing both.  Core blocks nothing by
                    default; the `guardrails` pack ships grep/find.
      intercept     {bin, forward} — route a command NAME in the jail to a forwarder
                    the pack declares: ~/.yolo/bin/block/<bin> becomes
                    `exec <forward…> "$@"`, first on PATH, so a bare `<bin>` runs the
                    forwarder while the installed program stays at its own path
                    (reachable by that path, or with YOLO_BYPASS_SHIMS=1).  It layers
                    permissions over an existing CLI: the `github` pack routes `gh` to
                    a host broker.  forward[0] is a bare program name on the jail's PATH
                    and never <bin> itself.  A blocked-tool for the same name wins.
                    A program with NO via is a NEED: {bin}, optionally install_hints,
                    and nothing else.  Another SELECTED pack's program for the same bin
                    satisfies it, whatever recipe that pack carries, and the launch
                    names the provider; with no provider it must ALREADY exist —
                    asserted at boot, reported by name when absent (a warning, not a
                    boot failure), never installed.  A need owns no path, so many
                    packs may need one bin.  Two selected packs carrying a recipe for
                    one bin refuse the launch, naming both: drop one from `packs`.
                    The old kind "requires" is refused; write it as a program with no
                    via.  Every program takes optional
                      install_hints {"brew"|"brew-cask"|"apt"|"dnf"|"pacman"|"nix": pkg}
                    naming the package that provides `bin` on a host package manager,
                    which `yolo check-deps` / `yolo host apply` print as the remedy for
                    a missing binary (and write into a Brewfile and kin).  `brew-cask`
                    is a Homebrew CASK rather than a formula and wins over `brew`.  For
                    a program, the pack's OWN installer (its via/url/package) is
                    preferred over a hint — a tool shipping its own installer ships its
                    own updater, while a distro package pins whatever that repo has.
                    So hints matter most on a need, where yolo installs nothing.
      skills        {from (pack dir), into (~ dir)} — merged (built-in < pack < yours).
                    `from` IS honored, at both notches and by wrapped-plugin discovery; it
                    defaults to skills/.  A `from` naming a dir the pack lacks delivers
                    nothing and says so; an absent CONVENTIONAL skills/ is silent.
                    Takes `agent` and `agents` on the same terms as `briefing` below: the
                    owning pack declares which agent reads a destination, and a content
                    pack addresses its tree to a name instead of a path — or names
                    neither, and it reaches every skills destination.  skills/ is ONE
                    unit: it broadcasts unless a contribution names it, so adding a
                    narrower tree beside it keeps it broadcasting.  `project_dirs`, on a
                    destination, names the workspace paths its agent reads skills from
                    (".codex/skills").  A jail mirrors every such directory a repository
                    has into every destination.  `yolo host -- <agent>`, which renders
                    nothing into your home from a workspace, instead puts ONE link at
                    the agent's first path when the repository has none of them,
                    pointing at the first other agent's skills directory it does have
                    (.codex/skills -> ../.claude/skills), adds that path to the
                    workspace's .gitignore once, and says so at every launch.
      briefing      {from, into, after:"host:<path>" to prepend your own file first,
                    agent, agents, describes}.  A pack's prose is every *.md directly
                    inside its briefing/ dir (filename order), plus any file a `from`
                    names.  A root AGENTS.md, CLAUDE.md or GEMINI.md is NEVER read: it is
                    the pack repository's own instructions.  A `from` with one of those
                    basenames, or such a file inside briefing/, is refused.  `from` names
                    exactly ONE file; one that is missing or blank delivers nothing (a
                    launch warns), and no other file is read in its place.  Omitted, `from`
                    means every briefing/ file no other contribution names.
                    `agent` is the IDENTITY a destination declares for itself — the
                    launcher command whose agent reads that `into`, declared by the pack
                    that OWNS the name.  A destination SOURCES NOTHING: `from` on one is
                    refused.  `agents` is the AUDIENCE a content contribution names:
                    deliver this prose only where a matching `agent` was declared.  A
                    contribution gives `into` OR `agents`, never both — naming who it is
                    for is what makes the destination inferable, and a content pack has
                    no business naming a path it cannot keep current.  Giving NEITHER
                    means BROADCAST, with or without a manifest:
                    {"kind": "briefing"}.
                    Each file has ONE governing contribution, so declarations only add:
                    {"from": "files/pi.md", "agents": ["pi"]} beside briefing/ delivers
                    both.  Two content contributions naming one source are refused.
                    `describes` lists kinds of the pack's OWN contributions the prose is
                    about, and delivers it only where the pack's contributions of each
                    apply: {"kind": "briefing", "from": "briefing/gh.md", "describes":
                    ["intercept"]} reaches every jail and no real home, since an intercept
                    does not apply at the host.
                    One name has exactly ONE owning pack, across `program`, `launch`,
                    `briefing` and `skills`; two claimants is a launch error naming both.
                    The vocabulary is the packs you SELECTED and nothing wider: naming an
                    agent your `packs` do not provide is fatal at launch and at `yolo host
                    apply`, with one message for a typo and for a real agent you did not
                    select — they are the same mistake, with the same two remedies.  `yolo
                    pack lint` reports the targeting and refuses nothing: it reads one pack
                    root with no config, so it cannot know what you selected.
      files         {from, into} — an opaque tree the pack owns, bind-mounted :ro at
                    `into` in the jail.  Unlike skills/briefing, `from` is REQUIRED (a
                    file or a dir), and `into` or `agents` too: files never broadcasts.  Sole-owned: two packs claiming one `into` is a
                    launch error naming both.  At the HOST notch it is WRITTEN into
                    your real home rather than bound: only paths yolo's ownership
                    record claims, the previous copy archived first, and a render
                    that cannot prove ownership refuses and touches nothing.
                    A PATCHED EXTENSION replaces `from` with `source` (the upstream) and
                    `patches` (a series, as for a patched fork), with optional `follow`
                    (as for a patched fork), `build` and `produces` (paths relative to the
                    built tree): yolo builds the tree on the host and mounts a read-only
                    copy at `into` (the pi pack's extensions use it).  Put it at
                    `into: ".pi/agent/yolo-patched/<name>"`, outside ~/.pi/agent/extensions/
                    where pi would also find it by itself.  pi loads it only through a
                    `config-list` entry in `pi/settings` `/packages` that is ~/ plus `into`
                    (~/.pi/agent/yolo-patched/<name>), or a path under it, with no slash at
                    the end; without one the tree is built and mounted, pi never loads it,
                    and `yolo pack lint` and each launch say so.  Drop the extension's old
                    `git:` entry in the same edit, or pi loads it twice.  Its key in
                    `yolo pack status` and `yolo capture` is <pack>/<name>, <name> being
                    the last part of `into`.
      config        {config:[surface...]} — a composed config surface (see below)
      config-overlay {surface:"agent/name", config:{managed:{...}}, profile} — keys on a surface
                    another pack owns.  `managed` is the ONLY body field: a contributor
                    contributes keys, so path/codec/mode/defaults are refused by name.
                    Folds in BELOW the owner's managed layer, so the owner wins a
                    conflict; `yolo config diff <agent>` says which pack set which key.
                    If no selected pack owns the target the overlay has NO EFFECT and
                    is reported by name — it never creates the file.  `profile` GATES
                    the whole contribution on that profile being the one active for the
                    TARGET SURFACE's agent: inactive means a clean skip (selection is
                    the optionality), and a gated overlay naming a surface nobody owns
                    is reported only while its profile is selected.
      config-list   {surface:"agent/name", path:"/json/pointer", add:[entry...],
                    remove:[entry...], profile} — ENTRIES appended to, or deleted from,
                    one array of a surface a pack owns, without copying or replacing the
                    list (a config-overlay array REPLACES).
                    `path` is an RFC 6901 JSON Pointer ("/packages"; "~1" is a "/"
                    inside a key, "~0" a "~"), never the root and never an empty step.
                    `add`, `remove` or both are required; either may be [] (a no-op),
                    and neither may hold a null.
                    Entries fold AFTER every config-overlay, pack order then declaration
                    order, each contribution's `remove` BEFORE its `add`: `remove`
                    deletes every element equal to one of its entries from what the
                    layers below (and earlier contributions) produced — removing an
                    absent entry is a silent no-op — then existing entries keep their
                    order, then each added entry not already present, compared as
                    whole JSON values, so the same entry from two packs is written once.
                    An entry in both verbs of one contribution ends up present.  At an
                    rmw surface `remove` withdraws only entries a pack added; an entry
                    the file already held is the user's and stays.  `profile` gates the
                    whole contribution as a config-overlay's does.
                    A missing array starts empty (a `remove` alone creates nothing); a
                    non-array there, or a non-object parent, refuses that surface's
                    render.  Captured edits, computed and
                    managed values still replace the final array.  No owning pack
                    selected: no effect, reported by name.  Every object surface
                    captures a list path per entry (stateful, rmw, computed), so an
                    in-jail edit never freezes the list; a keyless (lines/raw) target
                    is REFUSED at launch, naming the surface and its mode.
      state         {at (~ dir), scope:"workspace"|"machine", because} — persists
      reads-host    {host (~-relative file), into (/ctx dest)} — one file, :ro [gated]
      mount         {host (~-relative DIR or file), into (/ctx dest)} — :ro    [gated]
      env           {vars:{KEY:"value"}, platform|profile} — STATIC strings only; no
                    interpolation, no host reads, so it is honored for any origin.
                    A GATE limits the whole contribution to the agents whose selection
                    satisfies it — the pack's own agent, or for a pack that installs no
                    CLI every agent: `platform` to those whose selected provider
                    declares that platform, whatever the profile is named (aws-auth's
                    credential pointer, for "aws-bedrock"), and `profile` to those that
                    selected that profile by name.  One gate at most.  A provider fact
                    belongs on `platform`: a second profile over the same provider gets
                    it, which a name gate misses.  `region_profile_setting` (beside
                    `served_by` and a `platform` gate) names the setting of the serving
                    loophole that holds the profile its credential is minted for
                    (aws-auth's `profile`): an agent it reaches takes its region from
                    that profile's section of the platform's `region_file`.
      hook          {hook:"shared_credentials"|"shared_directory"|"unshare_directory"|
                    "per_jail_history"|"boot_check", from (~-relative path the hook
                    acts on), flags (boot_check only), at (a
                    machine-scope state dir THIS pack declares; the two shared_* hooks
                    only)} — the shared pair replaces `from` with a symlink into `at`, a
                    FILE for shared_credentials and a whole DIRECTORY for
                    shared_directory, so one login (or one package store) serves every
                    workspace on the machine. unshare_directory undoes a
                    shared_directory the pack no longer declares: the link at `from` to
                    `at` becomes an empty directory; anything else there is left alone.
                    boot_check runs `/bin/sh ~/<from> <flags...>` once at boot in a
                    container jail (never on macos-user, whose bootstrap runs no pack
                    script, nor at the host), and prints what it says as a warning; a
                    check that is satisfied prints nothing.  It never
                    stops a launch: a failing check costs a line, and one still running
                    after 5 s is stopped.
      autonomy     {autonomous:{...}, guarded:{...}} — the agent's two permission
                    postures; the confinement notch selects one (autonomous at
                    jail/guest, guarded at host), so a jail-bypass key never reaches
                    your real home via `yolo host apply`.  Each posture takes
                    {config:[surface...]} patching the managed layer of a surface THIS
                    pack owns, plus {launch:[{bin, flags}]}.  Either posture may be
                    empty, in both directions: a permissive-by-default tool only needs
                    `guarded`, and a pack whose autonomy is a LAUNCH FLAG ALONE only
                    needs `autonomous` — a flag has no persistence, so not selecting it
                    IS the guarded posture (copilot's `--yolo` is the shipped instance).
                    A posture is the ONLY place a launch flag can be declared, so every
                    flag yolo injects is one some notch can withhold; an injection is
                    printed at the launch that makes it, with both command lines.
      profile       {name, provider} — a NAMED SELECTION OVER A PROVIDER, and that is the
                    whole body.  `name` is the selector the `profile` key or `-p <name>`
                    sets; `provider` is the `providers` entry it selects and is
                    REQUIRED — a profile without one is refused by the manifest schema.
                    Whatever ELSE a launch under that profile should deliver (env
                    vars, config keys) is declared by the gated contributions of the
                    kinds that own those channels: `env` and `config-overlay` both take
                    a `profile` field naming the profile that activates them, and `env`
                    a `platform` naming the provider service instead, which a fact of
                    the provider (not of the profile's name) should use.  A
                    profile name is sole-owned WITHIN the pack only: two packs may both
                    declare `bedrock` and stay unrelated.  A profile no launch selects
                    does nothing.
      provider      {name, platform, endpoints:{protocol:{base_url, wire_api}},
                    api_key_env_name, region, region_env_name:[NAME...],
                    region_file:{path, path_env_name, profile_env_name,
                    default_profile, profile_section, key},
                    models:{alias: id}, model_options, capabilities,
                    options:{option: default|null}, pinned_endpoint} —
                    the SERVICE facts of a named provider: what service it is
                    (`platform`, open vocabulary, "aws-bedrock" for Bedrock; an agent's
                    derive and a `platform` env gate recognize the service by it), the
                    endpoints that speak each wire protocol, the region a regional
                    provider is reached through, the model ids an alias names, and the
                    OPTION names a profile may set (`options`; see [bold]providers[/bold]
                    below).  `region_env_name` makes a region a LAUNCH REQUIREMENT for
                    every provider of this one's `platform` (which it needs beside it):
                    the variables an agent there reads its region from, so a launch
                    whose agent is on such a provider with no `region`, none of them
                    delivered to it and none in its `region_file` is refused, naming
                    every way to set one.
                    `region_file` (which needs `region_env_name` beside it) says where
                    that platform's agents keep a region the environment does not carry:
                    the `key` of one profile's section of a file under your home
                    (`path`, relocated by `path_env_name`), the profile being the one the
                    serving loophole's `region_profile_setting` names, else the one
                    `profile_env_name` delivers, else `default_profile`.  A profile's
                    section is `profile_section` with {profile} replaced; the default
                    profile's is that one when the file has it, else its bare name
                    (`profile default`, then `default`).  yolo reads it on the machine
                    it launches on and delivers the region in the first variable the
                    agent reads, at every notch, saying so; packs/bedrock declares
                    ~/.aws/config's
                    `region`, AWS_CONFIG_FILE and AWS_PROFILE.  Composed UNDER your
                    `providers` entries per field, so overriding one model alias, one
                    region or one URL keeps everything else the pack shipped, except
                    on a provider with `pinned_endpoint: true`: there a `providers`
                    entry that adds or moves any base_url is refused, because a
                    subscription's bearer token goes wherever the agent is pointed
                    (claude-auth, codex-auth and copilot-auth set it).  The
                    credential is NEVER
                    here: api_key_env_name is the NAME of a variable you hydrate
                    (env), and a base_url carrying userinfo is refused.  The
                    entry carries facts only — WHICH environment variable each fact
                    lands in is stated by the agent pack's own derive.lua (its
                    yolo.env producer), never by provider vocabulary, so a pack cannot
                    ship a credential that way either.  A
                    provider name is sole-owned — two packs shipping one is a launch
                    error.
      models        {provider, add:[{id, vendor, alias, name, description,
                    context_window, max_tokens, reasoning, input, cost}]} or
                    {provider, only:[id...]} — SHAPES the model list of the provider
                    it names, any provider's, another pack's included: `add` appends
                    entries (a duplicate id keeps the first writer's), `only` keeps the
                    ids it names and drops the rest.  One verb per contribution.
                    Every `add` applies, in pack order, before every `only`, and two
                    `only`s intersect; then your own `providers.<name>.models` composes
                    over the result, so your config has the last word.  `vendor` (the
                    model's maker) is required on each entry; `alias` makes the entry
                    reachable under a second name, such as `default`.  Under an
                    `only`, each agent's model menu for the provider is exactly the
                    list where the agent allows it, and while the profile's
                    `enforce_models` is on (the default) claude, opencode and pi also
                    refuse any other model.  `yolo check` names a duplicate, an
                    `only` id nothing added, and a provider nothing declares.
      adapter       {adapts:{from, to}, address} — a PROTOCOL CONVERSION: the wire it
                    reads, the wire it speaks, and where the converted wire is served.
                    An agent that speaks `to` can be pointed at a provider that offers
                    `from`, with no yolo-internal value in anyone's config: the address
                    composes into that provider's table entry under `to`, exactly as if
                    the provider had declared it.  IT SAYS NOTHING ABOUT WHO RUNS IT —
                    the address may be a daemon the same pack ships (a `service`
                    contribution beside this one, joined by `needs`), a remote gateway
                    you already pay for, or a proxy running on your own machine.  The
                    PAIR is sole-owned, so two selected packs converting one wire into
                    another is an error naming both; one pack may declare several pairs.
      loophole      {from} — a loophole MODULE dir the pack ships, holding a
                    loophole.toml (a legacy manifest.jsonc is still read, and
                    `yolo pack migrate` converts one), so a loophole can be developed
                    standalone and dropped into a pack.
                    `from` is REQUIRED and there is no `into`: the host half runs on the
                    host and the jail half mounts at a path core owns.  A `from` naming
                    a dir the pack lacks is refused BY NAME, not skipped.  The loophole's
                    NAME is that dir's basename and must match the manifest's own `name`;
                    it is sole-owned, so two packs shipping one name is an error.
                    THE SHARPEST KIND, and the only one whose claim is host code
                    EXECUTION rather than a host read.  Every crossing the module
                    declares is a SEPARATE claim, disclosed rather than approved (there
                    is no prompt; selecting the pack is the consent, and `yolo pack
                    footprint` lists the claims): the daemon argv + doctor_cmd (one
                    claim, raw and unelided, printed just before it runs), one per TLS
                    intercept (a CA every client
                    in the jail trusts — claimed even with no daemon), one per host bind
                    mount, one per SOCKET bind as its own read-write host-IPC class (`:ro`
                    is no boundary for an AF_UNIX socket — measured), and one per host
                    device.  `state_files` needs no claim (it stays inside yolo's own
                    state tree).  At the host notch a credential loophole's doorway
                    opens at `yolo host --` for the agent whose selection asks for it;
                    any other loophole's only client is a container, so it does not
                    apply there.
      service       {name, jail_daemon:{cmd, restart}, host_daemon:{cmd}, endpoint,
                    platforms, serves, settings} — a DAEMON the pack contributes to a
                    namespace: a yolo-jaild subcommand run in the jail (under the same
                    supervised list the loopholes use) and/or a host-side `yolo internal
                    daemon`, plus its endpoint file at /run/yolo-services/<endpoint>.
                    THE ANTI-LOOPHOLE: it holds NO grant and crosses NO boundary — it
                    binds the jail's own loopback, reads no host state, mounts nothing,
                    and so is never a claim.  The name
                    is sole-owned (the daemon log and the endpoint file are both
                    name-keyed).  The jail daemon runs under the existing supervisor.
                    The host_daemon half (argv `yolo internal daemon <name>`) runs at
                    `yolo host --` and on macos-user, as a child of the one launch whose
                    agent is paired through the service, or beside the command for a
                    service no adapter names, and stops when that command exits; it runs
                    for a pack yolo ships or a local one (a path or file:// entry in
                    `packs`, or your local pack at ~/.config/yolo-jail/local); a fetched
                    pack's, `git+file://` included, is refused by name
                    (host-notch-services.md OQ-HS4, HS-D27, HS-D29).
      mcp           {name, bin, config:{command, args, env, requires_env, provides}} —
                    ONE MCP SERVER ENTRY composed into `mcp_servers`, which every
                    selected agent's MCP file renders in its own dialect.  `config` is
                    the entry in exactly the shape you write one under mcp_servers.  A
                    `command` or `args` word starting "~/" is a path under the home of
                    the agent it renders for — /home/agent in a container jail, the
                    sandbox account's home on macos-user, yours at the host — and yolo
                    writes it absolute, since an MCP client starts servers with a
                    scrubbed environment.  `env` values are literal.  Your own
                    `mcp_servers.<name>` entry merges over the pack's per field, and
                    null removes it.  `bin` names the `program` the server runs, which
                    `yolo host -- <agent>` installs into yolo's host floor beside the
                    agent.  The name is sole-owned: two selected packs shipping one
                    refuse a jail launch and `yolo check` (at the host the later pack
                    in `packs` holds it).  At the host only a pack yolo ships or a local
                    one (a path or file:// entry in `packs`, or your local pack at
                    ~/.config/yolo-jail/local) has its entry written; a fetched pack's,
                    `git+file://` included, is left out and named.  The `chrome-devtools`
                    pack is the shipped instance.
      mcp-auth      {store, format, entries_at, companions, empty_store, lock, fields,
                    rereads_before_refresh, login_hint, unsupported_reason} — one pack-wide,
                    agent-neutral MCP sign-in store declaration.  `store` is home-relative;
                    `format` is `json`, `dir`, or `unsupported`; `empty_store` is `delete` or
                    `{}`; `lock.protocol` is `flock`, `proper-lockfile`, `mkdir-heartbeat`,
                    or `none`. `fields.expires_at.unit` is `ms` or `s`. It is schema-only:
                    no current setup reads or delivers it.
    AT LAUNCH ONLY (`yolo host -- <program>`): at the host notch the kinds below are
    delivered to the program yolo starts, for that process only, and `yolo host apply`
    writes no file for them: what each declares reaches an agent through its process
    (an environment, a PATH, the providers table, a child daemon), never through a
    config file.  The report names them in one clause; this is how each arrives.  An
    env var, an adapter, a service and a loophole also have a shape the host delivers
    nowhere, listed under the next heading, so one kind can be named in both.
      env           an env var applies to a process yolo starts: `yolo host --
                    <program>` delivers it to that process only, and `yolo host env`
                    prints it.  Setting it for your whole session would mean editing
                    your shell rc.
      blocked-tool  a blocker is a shim first on the PATH of a process yolo starts:
                    `yolo host -- <program>` puts them first on that program's PATH.
                    Putting one at the head of your whole session's PATH would mean
                    editing your shell rc.
      adapter       an adapter's address is composed into the providers table a launch
                    carries, so `yolo host -- <program>` points its agent there,
                    starting the pack service that answers it when one does.
      service       a service's host half (`host_daemon`, in a pack yolo ships or a
                    local one: a path or file:// entry in `packs`, or your local pack at
                    ~/.config/yolo-jail/local) runs at `yolo host -- <program>` beside the
                    one agent paired through it, or beside the program when no adapter
                    names the service, and stops when that program exits.  A fetched
                    pack's, `git+file://` included, is refused by name.
      loophole      a credential loophole's doorway (`jail_daemon.host_cmd`, in a pack
                    yolo ships or a local one: a path or file:// entry in `packs`, or your
                    local pack at ~/.config/yolo-jail/local) opens at `yolo host --
                    <program>` for the agent whose selection asks for it, once the
                    loophole is enabled, and closes when that agent exits.  A fetched
                    pack's, `git+file://` included, is refused by name.
    AT THE HOST NOTCH THE KINDS BELOW DO NOT APPLY: neither `yolo host apply` nor `yolo
    host --` does anything with them, and this is where the reason lives.  The report
    names them in one line and stops, because a reason is for the person changing a
    rule and not the person meeting it; what follows is that reason, per kind, once.
    "Does not apply" means the declaration has no meaning off-container — it is never
    a refusal of your apply, which stops nothing and writes your other surfaces
    normally.
      intercept     an intercept layers a permission over a CLI by putting a forwarder
                    first on a JAIL's PATH.  At the host the agent runs as you and can
                    run the real program by its path, so the layer would govern
                    nothing; `yolo host --` does not put one there either.
      state         state names a jail-writable home subtree — off-container the home
                    simply is writable, so there is nothing to declare.
      reads-host    reads-host carries a host file INTO a jail.  With no jail the file is
                    already where the reader is.
      mount         a mount grants a jail a host folder through the jail's wall.  At
                    the host there is no wall, and the folder is already where you are.
      env           an env var `served_by` a daemon the host does not serve — a bound
                    loophole's socket path, which only a jail binds (audio's), or a
                    loophole with no doorway — is withheld at `yolo host --`, which
                    names it: a client at the host reaches its own server instead.
      adapter       an adapter whose address its own pack's service answers, when that
                    service has no host half (`host_daemon`) or is in a fetched pack:
                    nothing at the host serves the address, so `yolo host --` refuses a
                    pairing through it and names the service.
      hook          the shipped hooks are jail provisioning steps — a credential or
                    package-store symlink into the machine tier, and per-jail history.
                    Off-container each is either meaningless or a mutation of real user
                    state that no pack should perform unprompted (the directory one would
                    replace a real directory in your own home with a symlink), so no
                    host verb runs any of them.
      loophole      a loophole with no doorway for a notch without a jail
                    (`jail_daemon.host_cmd`) is a host daemon whose only client is a
                    container: with no jail there is no client, no --add-host, no
                    YOLO_JAIL_DAEMONS, and nothing for its endpoint file to be mounted
                    into.  An INLINE loophole of yours (a `loopholes.<name>` entry with a
                    `command`) is one, and the report names it by entry.
      service       a service with no host half (`host_daemon`), or one in a fetched
                    pack, is a daemon pair plus an endpoint file under the jail's /run.  With
                    no jail there is nothing to supervise the jail half and nothing to read
                    the endpoint.
      mcp-auth      the grouped declaration is retained and validated, but no setup's
                    readers or renderers consume it today.  It therefore has no meaning at
                    the host (or at any other setup); this is an interim schema foundation,
                    not an implemented sign-in-sharing path.
    WHAT A HOST APPLY COMPUTES, as a jail does: `yolo host apply`, and the automatic
    apply a wrapped launch runs, run each pack's derives over inputs composed from
    your USER config alone — the providers table (your `providers` over the selected
    packs' provider facts), the MCP servers (your `mcp_servers` over the selected
    packs' `mcp` entries), your `lsp_servers`, and the selection your
    `active_provider` table names.  So the provider facts reach `pi/models`, `pi/codex-models`,
    `codex/config`, `opencode/config` and `oh-omp/models` at the host too, pi
    registers the declared openai-codex list, and every agent's MCP and LSP files
    carry those servers.  Never a fetched pack's `mcp` entry (its command would
    run unconfined as you), a workspace's config, or a value naming a path only a jail has: each is left out and named.  A table a derive declares in
    full is yolo's there, as in a jail, so an entry you added by hand to one is
    dropped — confirmed first, the first time — unless your config declares it.
    That selection is applied edge-triggered: written when the chosen profile
    changes, your own later /model pick kept, and only what yolo wrote cleared when
    you deselect.  A one-launch `-p` has no meaning here, since this command launches
    nothing.
    NOTE (shipped behavior): two packs declaring a skills `into` at the SAME path fail
    the jail at boot.  (This note also said a jail ignored `briefing.from` and read a
    root AGENTS.md regardless.  Both notches now resolve every pack through one
    predicate, and neither reads a root AGENTS.md at all.)
    A TOML entry takes the whole pack.  The legacy `only` and `exclude` filters
    have no TOML spelling; LEGACY JSONC FORMAT describes them.
    A pack SHIPS ITS TOOLS: a file carrying the exec bit stages executable, so a skill
    can ship the script it tells an agent to run.  What a pack may NOT do is land a
    destination on the jail's PATH — that is refused in the manifest, because a name on
    PATH comes from a `program` contribution, which owns it and discloses it.
    Precedence: later entries win on same-named skills.  Within one agent, the order
    is built-in skills < pack skills < your own ~/.<agent>/skills, so a pack may
    override a yolo built-in but never a skill you wrote.
    Pack prose is appended to each briefing as plain text, one blank line between
    files and between packs (`briefing_provenance = true` labels each pack's section
    once).  To EACH briefing unless the file's contribution named an audience: prose
    carrying `agents` reaches only the destinations whose owner declared a matching
    `agent`, at both notches.
    Tooling: [bold]yolo pack init|lint|ls|explain|footprint[/bold].  `lint` runs the real
    staging rules (the escaping-symlink refusal) AND validates the pack.json
    manifest (unknown kind, missing field, unknown key — every problem, not the
    first), then prints the pack's footprint.  `footprint <path>` shows what a local
    pack you are authoring claims, and any collision, before you configure it.
    `explain` lists exactly which files stage and which the filters dropped.

  [bold]pack_sources[/bold] (table, [bold]USER SCOPE ONLY[/bold]): The places a `<source>/<name>` pack handle reads.
    Each key is a source name, and `packs` names a pack inside it as
    "<source>/<name>".  The key is also the namespace of its packs' names (see
    `packs`), so it must be lowercase letters, digits and single hyphens.  "yolo"
    and "local" are yolo's own words and are refused as keys.
    A value is one of:
      "~/path" or "/abs/path"         a folder on this machine; each pack is a
                                      folder inside it
      { path = "~/path", bare = true } the same folder, its packs delivered
                                      without a namespace
      { git = URL, ref = "main" }     a git repository holding packs; `ref` is a
                                      branch, tag or commit, and a tag or commit
                                      is never re-fetched by a launch
    A source is a folder or a repository, not both, and a folder takes no ref.
    Example (~/.config/yolo-jail/config.toml):
      packs = ["mine/review", "acme/tools"]

      [pack_sources]
      mine = "~/dotfiles/packs"
      acme = { git = "https://github.com/acme/yolo-packs", ref = "v1" }
    `yolo config set pack_sources.mine '"~/dotfiles/packs"' --user` writes the
    first line.  This key has no legacy JSONC spelling: a legacy file names a
    pack by its path instead.

  [bold]providers[/bold] (table): Your own provider entries, composed OVER the ones the
    selected packs ship, per field — overriding one model alias, one region or one URL
    keeps every other field the pack shipped.  Each key is a provider NAME, and the name
    is sole-owned across packs and config together: two packs shipping one is a launch
    error.
    ⚠ WHERE A CREDENTIAL GOES IS USER-SCOPE ONLY.  `endpoints` in any form (a URL, a
    protocol, a dialect, or a removal of one), `api_key_env_name` (a value or a removal),
    `platform`, and a removed provider are REFUSED in a workspace
    `yolo-jail.toml` or `yolo-jail.local.toml`, each naming the field; write them in
    your user config instead.  The workspace file is agent-editable: an agent that can
    repoint its own model endpoint can send everything it reads to a server you did not
    choose, one that can rename the variable a provider claims can send you a different
    credential (GH_TOKEN, say) to that provider, or unclaim a key so every process
    receives it, and one that can relabel a provider's platform can hand its agents a
    credential pointer meant for another service.
    `models`, `options`, `region` and `capabilities` still merge from either scope, a
    `region` only as a region name (below).
    Per entry:
      base_url       [bold yellow]REMOVED[/bold yellow] — an entry carrying it is REFUSED, naming the
                     explicit spelling.  The bare field said WHERE without saying WHICH
                     WIRE, so the same line meant different protocols to different
                     agents (pi read it as openai, claude as anthropic) — and its
                     headline case was the trap, because llama.cpp, ollama and vLLM all
                     speak OpenAI, so `claude` plus a bare URL pointed it at a server it
                     could not talk to.  Write `endpoints.<protocol>.base_url`.
      endpoints      [providers.<name>.endpoints.<protocol>] with base_url and
                     wire_api — where each wire protocol points.
                     The KEY is the protocol an agent asks for by name, and an agent
                     that speaks none of them reaches the provider only if some selected
                     pack declares an `adapter` from one of these to one of its own —
                     otherwise the launch REFUSES, naming both protocols and the pack
                     that would bridge them.  A URL carrying userinfo is refused: a
                     base_url routes an ADDRESS, never a credential.
      wire_api       the DIALECT an endpoint speaks, when it is not the protocol key's
                     own default; declared inside an `endpoints` entry.
      api_key_env_name  the NAME of the variable you hydrate (env), or a list of
                     names for a provider with several credential routes (packs/bedrock's
                     bedrock lists six) — the credential itself is never in this
                     config.  A named variable reaches only the agents that
                     select this provider, and the launch pre-flight refuses a provider
                     some agent selected whose variable is empty.  A provider that sets
                     no api_key_env_name but a `platform` claims the names every provider
                     of that platform lists, so a Bedrock provider of your own keeps the
                     six AWS names to its agents as `bedrock` does.
      platform       what service this provider is, one token in an open vocabulary
                     ("aws-bedrock" for Amazon Bedrock).  Yours gets exactly the behavior
                     a shipped provider of the same platform gets: a Bedrock provider of
                     your own, `{ platform = "aws-bedrock", region = "eu-west-1" }`
                     selected in active_provider, switches claude to its Bedrock client, receives the
                     aws-auth credential pointer, claims the AWS credential variables
                     `bedrock` claims (unless it lists its own api_key_env_name) and is
                     required a region.  A value no pack knows changes nothing.
      region         the region a regional provider is reached through, as one DNS label
                     ("us-east-1"): the agents build their service's host name from it,
                     so a value with a dot, a slash or a "#" is refused at every scope.
                     For a provider whose platform a selected pack declares region
                     variables for (`bedrock`, and any provider of yours with
                     platform = "aws-bedrock"), an agent with no `region` here and none
                     of the region variables it reads (AWS_REGION or AWS_DEFAULT_REGION;
                     opencode reads AWS_REGION alone) delivered to it is given the
                     region its AWS profile has in ~/.aws/config on the machine yolo
                     launches on, in a jail and at `yolo host` alike, and the launch
                     says so.  When that file gives none either, the launch is REFUSED,
                     naming the three ways to set one: this key, a variable in
                     env, or the AWS profile's `region` in that file.
                     YOLO_ALLOW_MISSING_PROVIDERS=1 launches anyway.
      models         [providers.<name>.models] maps an alias to a model id — the
                     aliases a variant's `model` names.  A value may instead be a
                     table, { model, name, description, context, max_tokens,
                     reasoning, accepts, price }: the wire id plus the facts an
                     agent's menu shows (`description` is the second line claude's
                     picker gives a model).
                     The agent pack's own derive.lua decides which alias each of the
                     agent's keys reads; `default` is the alias used when a variant
                     states no model, and it is an ordinary name, not a keyword.
                     This map composes LAST, over the provider's own list and every
                     pack's `models` contribution (added entries, or an `only`), so
                     your aliases, additions and removals win.
                     Four names are CONVENTIONAL TIER ALIASES every provider is
                     expected to declare: `default`, `fast` (cheap and quick),
                     `balanced` (the middle tier) and `frontier` (the most capable).
                     A convention, not a requirement: when a pack asks for one this
                     provider does not name, the launch warns and proceeds.
                     claude pins its tiers from them: `balanced` its Sonnet tier, `fast`
                     its Haiku tier, and `frontier` its Opus tier on the ChatGPT
                     subscription's list (`openai-codex`) and on a list a pack's `only`
                     narrowed. `sonnet`, `haiku` and `opus` still work, and win when a
                     provider names both.
                     `yolo check` warns about an id no installed agent's own model
                     catalog knows, and says when it could read no catalog; it never
                     refuses one, and no launch asks.
                     A table value takes { model, name, vendor, reasoning, accepts,
                     price, context, max_tokens, extends, base, openrouter_routing,
                     wire_id }, where `model` is the wire model id and the rest are
                     facts an agent's derive reads.
                     `vendor` is the model's MAKER, one lowercase token such as
                     "anthropic" or "openai": on a provider that serves several makers'
                     models (`bedrock`), each agent is offered only the entries its own
                     client can call (claude's Bedrock client, Anthropic's alone), and an
                     entry with no vendor is offered to every agent.
                     A fact you leave out INHERITS: from the pack's facts for the alias,
                     then the shared facts `extends` names, then pi's own catalog entry
                     for the id.  A removed fact is a TOMBSTONE: the model has no such
                     fact, whatever a layer below says, pi's catalog included (THE TOML
                     FORMAT gives each removal spelling; restate the value to get the
                     catalog's back).  On pi's own Bedrock client, a row naming a
                     catalog id goes into pi's models.json as a `modelOverrides` entry,
                     which pi merges over its catalog, so its thinking levels survive in
                     any pi; a row with `base`, `wire_id` or a removed fact is written
                     whole.
                     `extends` names a top-level `model_facts` entry: the facts this
                     model's routes share, laid under this entry's own, so each route can
                     state its own price, context size or output limit.
                     Three keys are pi's alone.  `wire_id` is the id the row SENDS when
                     its `model` is a client spelling, so one provider carries one model
                     at two windows: the rows `floor = { model = "x:floor" }` and
                     `floor-200k = { model = "x:floor@200k", wire_id = "x:floor",
                     context = 204800 }` give pi two rows, each with its own facts,
                     written with `wireId` in models.json and the model-lists file.  A
                     pi that does not read `wireId` sends the row's `model`, and every
                     other agent sends `model`.
                     There is no `variants` key: declare each variant as its own alias.
                     `base` names the pi CATALOG model id this
                     row INHERITS from, so a variant id such as
                     "deepseek/deepseek-v4.1-flash:floor" keeps the catalog's thinking
                     levels (nulls included), inputs, limits and cost instead of
                     restating them.  `openrouter_routing` is an OBJECT sent verbatim as
                     OpenRouter's request `provider` field, e.g. { order = ["streamlake",
                     "morph"], allow_fallbacks = false }, so two rows for one model can
                     name different upstream orders.  A list carrying one (or, on a
                     provider pi ships, a `wire_id` or `base`) is registered
                     with pi as that provider's menu: its declared models are what pi
                     offers there, and a model outside it is refused only when an `only`
                     narrowed the list and `enforce_models` is on.  pi's models.json
                     row for a provider pi does not ship carries it too, as
                     `compat.openRouterRouting`.  `yolo check` warns about a pin no
                     request can carry: on a Bedrock provider, or one with no
                     chat-completions `endpoints.openai` that no agent runs itself.
                     A row is keyed by the model's id, or by a name you choose when it
                     says which model it is with `model` (`id` is refused).  A twin
                     that sends another row's id and takes its facts says
                     `twin_of = "<that row's key>"`.  A row over a pack's alias for
                     another id must say `model`, or it would send its key as the id.
                     A plain string, default = "glm-5.3", is the alias's wire id with
                     no facts of its own.
                     Example (~/.config/yolo-jail/config.toml):
                       [providers.bedrock.models.kimi]
                       model = "global.moonshotai.kimi-k3"
                       vendor = "moonshotai"
                     Example (~/.config/yolo-jail/config.toml):
                       [providers.openrouter.models.flash-floor]
                       model = "deepseek/deepseek-v4.1-flash:floor"
                       base = "deepseek/deepseek-v4.1-flash"
                       openrouter_routing = { order = ["streamlake", "morph"], allow_fallbacks = false }
      capabilities   the named jobs this provider performs for itself, e.g.
                     ["web_search"].  A launch that selects it OMITS every
                     `mcp_servers` entry whose "provides" names one of them — the
                     server would be a second implementation of something the
                     provider already does.  Same vocabulary `provides` and
                     `required_capabilities` are spelled in; the packs that ship a
                     provider declare it, and an entry here overrides that.
      options        [providers.<name>.options] maps an option to its default — the
                     settings this provider DECLARES, and the only schema a variant
                     answers to.  A default value is what a variant inherits when it
                     does not state the option.  A variant naming an option this
                     table does not hold is refused — but only once the provider
                     declares at least one option, since a provider with no
                     `options` imposes no schema at all.
      variants       [providers.<name>.variants.<variant>] — your own NAMED SELECTIONS
                     over this provider; see `providers.<name>.variants` below.
    Which environment variable each fact lands in is the agent pack's decision (its
    yolo.env producer) — this key carries facts, not bindings.
    Example (~/.config/yolo-jail/config.toml):
      [providers.zai]
      api_key_env_name = "ZAI_API_KEY"

      [providers.zai.endpoints.openai]
      base_url = "https://api.z.ai/api/paas/v4"
      wire_api = "openai-chat-completions"

      [providers.zai.models]
      default = "glm-5.3[1m]"
      fast = "glm-5.3-flash[1m]"

      [providers.zai.options]
      model = "default"

  [bold]model_facts[/bold] (table): Facts a model keeps on every route, written ONCE and
    named by each route's `providers.<name>.models.<alias>` table with `extends`.  Each key
    is a name you choose; each value takes a model row's facts: { name, description,
    reasoning, accepts, price, context, max_tokens, base, openrouter_routing }, a removed
    fact being a tombstone.  The order is: the route's own value, then these shared facts, then
    the agent's own catalog, so a route that serves a smaller context or charges a different
    price states just that.  A table-valued fact is ONE fact: a route's own `price` or
    `openrouter_routing` REPLACES the shared object whole, never merging key by key, so a
    1M route and its 200k twin extending one entry send the same OpenRouter `provider`
    field, and a route that removes `openrouter_routing` sends none.  An `extends` naming
    no entry here is refused.  pi gets every row in full,
    unless its pi reads the shared form: then models.json holds the facts once, as
    `sharedModels`, each row saying `extends` and stating only what differs, and the
    model-lists file carries the same `sharedModels` and `extends` beside full rows.  The
    declaration is `reads_shared_models = true` on the `program` contribution whose
    `bin` is "pi" and that supplies pi's bytes: a fork's (`fork_of`, `via: "source"`),
    which replaces the base pack's, or else the pack installing pi.
    Example (~/.config/yolo-jail/config.toml):
      [model_facts."opus-5.5"]
      reasoning = true
      accepts = ["text", "image"]
      context = 1000000
      max_tokens = 128000
      price = { input = 5, output = 25 }
    An entry refuses what only a route says: `model`, `wire_id`, `twin_of`,
    `compact_at`, `extends`.  A project config may write it too.

  [bold]adapters[/bold] (table): Where an ADAPTED provider answers — the one field of an
    adapter you may set.  [bold yellow]USER SCOPE ONLY[/bold yellow], for the same reason `providers`
    addresses are: this decides where an agent's inference goes, and a workspace config
    travels with the repo and is agent-editable.
    An adapter is a pack declaration — it says which wire it converts into which, and at
    what address — so a provider that offers only `openai` reaches an anthropic-speaking
    agent with nothing in your config naming a port.  You need this key only when that
    port collides with something: harmless inside a container, where 127.0.0.1 is the
    jail's own private loopback.  At `yolo host --` and on `macos-user` an adapter whose
    own pack's service serves it (the wire bridge's) answers on a port that one launch
    picks for the service it starts, and this override does not apply to it there; it
    still moves an adapter no pack service serves (a gateway or a proxy you run).
    Each key is the CONVERSION, spelled "<from>-><to>" — the same pair the declaring pack
    claims, which is sole-owned.  The only field is `address`, an http/https URL; a key
    naming a conversion nothing declares is inert.
    Example (~/.config/yolo-jail/config.toml):
      [adapters."openai->anthropic"]
      address = "http://127.0.0.1:9214"

  [bold]providers.<name>.variants[/bold] (table, [bold]USER SCOPE ONLY[/bold]): Your own NAMED SELECTIONS over a
    provider — a variant name and the settings it picks.  The legacy JSONC key is
    `profiles`, where each entry named its provider.  A workspace config carrying a
    variant is REFUSED, because a workspace file travels with the repo and is
    agent-editable, and a variant steers WHICH ENDPOINT and WHICH MODEL an agent
    talks to.  A variant is selected as "<provider>/<variant>".  Per variant:
      model          the provider's model alias or id this variant runs.
      enforce_models true (the default) or false.
                     Where a pack's `models` contribution narrowed the provider's list
                     with an `only`, on means every agent that can refuse a model
                     outside the list does (claude's allowlist, opencode's whitelist,
                     pi's extension), and on `openai-codex` claude and pi refuse outside
                     the subscription's list with no `only`; off means the list only
                     shapes the agents' menus.
      subagents      a table with `default` and `roles`: what this variant's child
                     agents run on.  `default` is the model a child that names none of
                     its own starts on, and omitted it is the parent's model.  `roles`
                     pins one model per subagent role, e.g. { worker = "deepseek-floor" },
                     and a role it omits keeps pi-subagents' own default.  Each value is
                     an alias or exact model id of the variant's provider, resolved the
                     way `model` is; one that does not resolve, an unknown key, or an
                     empty table is refused.  Only pi reads it: it becomes
                     pi-subagents' defaultModel and role models.
      (any other key)  an OPTION VALUE, and it must be a string.  The option name must
                     be one the provider's `options` declares; what the value MEANS is
                     the agent pack's derive.lua's business.  Omit a key to leave that
                     option at its declared default.  A provider that declares NO
                     options imposes no schema at all — an undeclared option name is
                     refused only once the provider declares at least one.
    A variant both a pack and you declare is yours to customize: your entry wins per
    option.  Declaring a variant does nothing until a launch selects it
    (`active_provider`, or `-p <provider>/<variant>` before the `--`).
    Example (~/.config/yolo-jail/config.toml):
      [providers.zai.variants.zai-fast]
      model = "fast"
      subagents = { default = "fast" }

  [bold]active_provider[/bold] (table, [bold]USER SCOPE ONLY[/bold]): The provider each agent runs on — the
    persistent spelling of `-p`/`--profile`, form for form.  The legacy JSONC key is
    `profile`.  Each value is a provider, a "<provider>/<variant>", a list of them,
    or "native" (the agent's own login, no provider):
      default = "bedrock"                every agent: -p bedrock
      pi = "codex"                       one agent: -p pi=codex
      default = "bedrock"  +  pi = "codex"
                                         every agent not named, and pi: -p bedrock -p pi=codex
      pi = ["zai", "openrouter"]         a list for one agent: -p pi=zai,openrouter
      default = ["zai", "openrouter"]    a list for every agent: -p zai,openrouter
    Example (~/.config/yolo-jail/config.toml):
      [active_provider]
      default = "bedrock"
      pi = "zai/zai-fast"
      codex = "native"
    `yolo active-provider pi zai/zai-fast` writes the `pi` line, and
    `yolo active-provider default bedrock` the `default` line.
    A key other than `default` is the BINARY a pack installs (`claude`, `pi`, `codex`)
    and NOT a pack or agent name; an unknown key is fatal, naming what is installed.
    `default` reaches every CLI the selected packs install that the table does not
    name, whether or not a command follows `--` — the command is never a provider
    target, so `yolo -- sleep 60` launches with the provider active for every CLI the
    jail installs.  A named agent keeps its own entry beside `default`, as
    `-p pi=codex` keeps pi's beside a bare `-p bedrock`.
    "native" selects NO provider for that agent, so `default` does not reach it.  An
    empty name is refused.
    PRECEDENCE: every `-p` beats this key, form for form — a bare `-p <name>` replaces
    the key's selection for every CLI it reaches, named entries included, and
    `-p <cli>=<name>` replaces that CLI's.
    A value may also be a LIST of names, the agent's ACTIVE SET: every listed provider
    is live in one session (its models in the picker, its key delivered to that agent
    alone), and the FIRST entry is where a fresh session starts.  Only an agent whose
    pack declares `provider_sets` holds one (pi, opencode and oh-omp today); a list NAMED at
    any other agent is REFUSED, naming the one-name spelling: claude, codex and copilot
    run one provider per session.  A list under `default`, or a bare
    `-p zai,openrouter`, goes whole to every agent that holds a set and its first entry
    to every other, and the launch names the agents that ignore the rest.
    A list of one is the plain name.  An empty list is refused, as is a name listed
    twice, two entries on one provider, two on one regional platform (two Bedrock
    providers share the agent's one AWS_REGION), and a variant that sets `via` anywhere but first.
    Every name must be declared, the entries a list's narrowed agents ignore included.
    On the command line a comma continues one agent's list: `-p pi=zai,openrouter` (a
    later `-p pi=…` replaces the whole list, as a `-p` pair replaces the key's).  A
    provider or variant name may not contain a comma, and in this key a list is a TOML
    array, never a comma string.
    USER-SCOPE ONLY, like variants: a workspace spelling would TAKE EFFECT rather than
    sit inert, so it is REFUSED there.
    At `yolo host` it selects for the one command composed: its own entry, else
    `default` when a selected pack installs it.  A provider reaches agent CLIs only, so
    `yolo host -p zai -- curl …` is REFUSED, naming the grant that hands an arbitrary
    command a provider's key, `yolo host --with-credentials zai -- curl …`; a key
    naming such a command cannot do it either — it is the unknown key above, refused
    at `yolo host` too — and `default` simply does not reach it.
    Selecting a name nothing declares (pack-shipped or yours) refuses the launch
    rather than selecting nothing — a silently inert selector is indistinguishable
    from a working one.  A selected provider switches ON; deactivating it does not
    write the agent's surface back — whatever a selection wrote stays, and the
    agent's own choice stands.
    AT THE HOST, `yolo host apply` (and a wrapped launch's automatic apply) writes
    this selection into the agents' real files too — pi's defaultProvider and
    defaultModel, codex's and opencode's model, claude's picker — when the chosen
    provider changes; a later /model pick of yours stands, and deselecting clears only
    what yolo wrote.  A selection the host cannot run is left out and named.  A
    selection whose pairing runs through a pack service (claude on `codex` or
    `cerebras`, through the wire bridge) writes no address anywhere: the service lives
    only for the command that starts it, so the selection takes effect through
    `yolo host -- <agent>` or the host wrappers, which start it, and `yolo host env`
    refuses it.  An agent started any other way runs without it.

  [bold]required_capabilities[/bold] (array of strings): Named capabilities this
    environment DECLARES it needs, e.g. ["web_search"].  Validated as a string list
    at pre-flight, and passed through to a nested launch (it is one of the keys an
    inner jail inherits).
    ENFORCED: a launch that declares a capability nothing satisfies is REFUSED
    (docs/reference/mcp-configuration.md, "The capability gate").  A capability is satisfied by a
    declaration — `providers.<name>.capabilities` naming it, an `mcp_servers.<name>`
    entry whose "provides" is it, or a SELECTED agent whose pack declares it for the
    source that agent runs on: its own login when no provider is active for it
    (claude and agy search the web on theirs), or the provider active_provider selects
    (a pack's provider counts only there, so `pi` on no provider gets no web search
    from the `openai-codex` provider its pack brings along; your `providers.<name>`
    entry overrides a pack's list, and removing the provider drops it) — or by the
    baseline every agent meets (code_editing, command_execution), which needs no
    declaration.  A server set to "off" satisfies nothing: the jail deletes it.  One
    agent's source is enough for the whole launch, and so is any provider of an
    agent's list.  A `providers.<name>.capabilities` YOU write counts whether or not
    active_provider selects that provider.
    The refusal runs above the backend dispatch, so it fires on every backend, and
    `yolo check` predicts it.  `yolo host -- <cmd>` asks the same gate, over your
    user config alone (a workspace config cannot refuse or satisfy a host launch),
    before it auto-applies anything, and refuses in the same words.
    YOLO_ALLOW_UNMET_CAPABILITIES=1 launches anyway, loudly.  It is there for a
    capability you really have that nothing declares — an agent whose pack does not
    state what its login does, or a tool it reaches some way yolo does not deliver.
    The key is no longer exported to the jail: nothing in a jail read
    YOLO_REQUIRED_CAPABILITIES, and the check it stood in for now happens on the host
    before the launch.
    Default: [] (declares nothing).
    Example (yolo-jail.toml):
      required_capabilities = ["web_search"]

  [bold]prune[/bold] (table): Disk-usage nudge settings for `yolo check`.  ONE key, and
    the block is host-side only — an in-jail `yolo check` skips the disk section, so a
    threshold written in a jail snapshot does nothing there.
    • [bold]warn_threshold_gb[/bold] (number, [bold]default 15[/bold]): total yolo-jail
      footprint, in GiB, above which `yolo check` warns and points at `yolo prune`.  It
      changes WHEN YOU ARE TOLD, never what `yolo prune` reclaims: every reclaim policy
      is a flag (--image-cache-keep, --cache-age, --nix-gc-max), so nothing else belongs
      under this key and any other sub-key is refused as unknown.
    ⚠ THE BLOCK HAD NO VALIDATOR AT ALL UNTIL 2026-09-16, so `prune = "hello"` and a
    misspelled sub-key were both accepted in silence — and this reference had no section
    for it, which is how it stayed that way: the coverage test that should have caught
    the omission was satisfied by the substring "prune" inside `programs.autoprune`.
    Both halves are fixed; the value is now checked and a typo names itself.
    Example (~/.config/yolo-jail/config.toml):
      [prune]
      warn_threshold_gb = 40

  [bold]lsp_servers[/bold] (table): Language servers to hand to the agents that read them.
    No defaults — declare each server you want. Its binary must be on PATH (via
    install.mise, a pack program, or an absolute path).
    Each key is a server name; its value is a table with:
      • command (string, required): Binary name (on PATH) or absolute path.
      • args (array of strings): Args passed to the LSP binary. Default: [].
      • fileExtensions (table): Extension → language ID map (required for Copilot).
    The entrypoint translates these for each agent:
      • Copilot: written to ~/.copilot/lsp-config.json as native LSP servers.
      • Claude Code: the launcher renders ONE generated plugin, yolo-lsp, from the
        whole table into the skills tree Claude loads plugins from.
    yolo installs no language server itself, on any backend.
    At the host, `yolo host apply` writes the same translation into your real
    home from your USER config, less any server naming a path only a jail has:
    Copilot's file, and the yolo-lsp plugin in the skills dir of every selected
    pack that composes one.
    Example (yolo-jail.toml):
      [lsp_servers.rust]
      command = "rust-analyzer"
      args = []
      fileExtensions = { ".rs" = "rust" }
    A server written "off" (`lsp_servers.<name> = "off"`) drops one a lower file
    declared.

  [bold]mcp_presets[/bold] (array of strings): REMOVED — a config carrying it is REFUSED,
    in either file.  yolo no longer keeps its own list of MCP servers:
      • chrome-devtools — add "chrome-devtools" to `packs` in
        ~/.config/yolo-jail/config.toml, beside your agents.  The pack gives the
        server in a jail, on macos-user and at the host.  A workspace file cannot
        select it.
      • sequential-thinking — deleted.  Write it yourself under `mcp_servers`:
        Example (yolo-jail.toml):
          [mcp_servers.sequential-thinking]
          command = "npx"
          args = ["-y", "@modelcontextprotocol/server-sequential-thinking"]
    Delete the key, then run [cyan]yolo check[/cyan].

  [bold]mcp_servers[/bold] (table): Custom local and remote MCP servers.
    Add custom servers, or set a pack's or inherited server to "off" to disable it.
    A selected pack's `mcp` entry composes under this table; your same-name entry
    merges over it per field, and a removal disables it.
    Each key is a server name; its table requires exactly one of:
      • command (string): local stdio server program, on PATH or an absolute path.
      • url (string): remote endpoint. Must be https://, except http:// for localhost or
        a loopback address. `args` and `env` apply only to `command` entries.
    Local stdio fields:
      • args (array of strings): passed to the server process; default: [].
      • env (table of string→string): Environment variables passed only to
        this MCP server's process. Use for per-server secrets and config so
        they don't leak into the jail-wide env. Default: {}.
        Values are written LITERALLY: yolo expands no [bold]${VAR}[/bold], so a
        reference reaches the agent's config as written, for the agent to resolve
        from its own environment (which [bold]env[/bold] hydrates).
    Remote fields:
      • transport (string): "http" (streamable HTTP; default) or "sse".
      • headers (table of string→string): remote request headers, written verbatim;
        [bold]${VAR}[/bold] is not interpolated.
      • oauth (table): optional static settings: `client_id` (string), `scopes` (array of
        strings), `callback_port` (integer 1–65535). A client secret is never rendered.
    Shared fields:
      • provides (string): the named JOB this server implements, e.g.
        "web_search".  Two things read it, and they are different questions.
        DELIVERY: the authentication source your launch resolves to — the
        provider active_provider selects, or the agent's own built-in login — omits
        this server when it already does that job, so a search MCP is delivered
        on a gateway that has no native search and dropped on one that does.
        REQUIREMENT: it also satisfies a `required_capabilities` entry naming
        it.  Two servers declaring one name refuse the launch: which one
        implements the job is not something to pick at random.  Optional; a
        server without it makes no claim and is always delivered.
      • requires_env (array of strings): Conditional loading gate. The
        server is only configured when every listed variable is set
        (and non-empty) in the jail's startup env. If any is missing,
        the server is skipped with a notice — not an error. Lets a
        dotfiles-shared user config declare machine-dependent servers
        that activate only where `env` provides the keys. It is
        asked per agent: a variable a provider claims (its
        api_key_env_name) reaches only the agent that selected
        that provider, so the server is configured for that agent only.
        Example (~/.config/yolo-jail/config.toml):
          [mcp_servers.tavily]
          command = "npx"
          args = ["-y", "tavily-mcp"]
          env = { TAVILY_API_KEY = "${TAVILY_API_KEY}" }
          requires_env = ["TAVILY_API_KEY"]
    Every selected agent pack renders the remote transport it declares. Codex renders
    streamable HTTP; Claude and opencode render streamable HTTP and SSE. A remote server
    whose transport is unsupported by an agent is omitted from its config and named at boot.
    Stdio servers continue through each pack's local-server form.
    AT THE HOST, the same translation is written into your real home by
    `yolo host apply` (and a wrapped launch's automatic apply), from this key in your
    USER config: every selected agent's MCP file gets these servers, as in a jail.
    A local server whose command or arguments name a path only a jail has (/workspace,
    /home/agent, /ctx, …) is left out and named, and `requires_env` is asked of the
    environment `yolo host env --agent <agent>` composes for each agent.  To give one
    host agent a server the others should not get, add a `config-overlay` for that
    agent's surface to your local pack (~/.config/yolo-jail/local/pack.json).
    Example (~/.config/yolo-jail/config.toml):
      [mcp_servers.cerebras-mcp]
      command = "npx"
      args = ["-y", "cerebras-code-mcp"]
      env = { CEREBRAS_API_KEY = "csk-...", CEREBRAS_MCP_IDE = "claude" }
    A remote server:
    Example (~/.config/yolo-jail/config.toml):
      [mcp_servers.linear]
      url = "https://mcp.linear.app/mcp"
      transport = "http"
      headers = { X-Org = "acme" }
      oauth = { client_id = "c1", scopes = ["read"], callback_port = 3118 }

  [bold]devices[/bold] (array): Host devices to pass through to the jail.
    Three formats supported:
    • USB by vendor:product ID (preferred — stable across reboots):
      { usb = "0bda:2838", description = "RTL-SDR Blog V4" }
      Resolved to /dev/bus/usb/... at startup via lsusb.
    • Raw device path (fragile — changes on replug):
      "/dev/bus/usb/001/004"
    • Cgroup rule (broad access):
      { cgroup_rule = "c 189:* rwm" }
      Grants access to all devices matching the major number.
    Example (yolo-jail.toml):
      devices = [
        { usb = "0bda:2838", description = "RTL-SDR Blog V4" },
        "/dev/bus/usb/001/004",
        { cgroup_rule = "c 189:* rwm" },
      ]
    Missing devices produce a warning, not an error — the jail still starts.
    On macos-user nothing is passed through: a raw path under /dev (a serial
    adapter's /dev/cu.* node) has its device control calls allowed by the
    sandbox, and the launch names it; raw disks stay refused, and USB and
    cgroup entries are not read.  Not yet tried on a Mac.
    Subject to config change safety (human approval required).

  [bold]machine.gpu[/bold] (table): GPU passthrough configuration (NVIDIA / AMD ROCm).
    The legacy JSONC key is `gpu`.
    NVIDIA (default) uses the NVIDIA Container Toolkit on the host (podman +
    CDI). AMD ROCm defaults to raw device-node passthrough and needs no host
    toolkit — just the amdgpu kernel driver.
    • [bold]enabled[/bold] (bool): Enable GPU passthrough. Default: false.
      If true but the host lacks drivers/CDI (e.g. laptop without a
      GPU), yolo prints a one-line warning and starts without
      GPU passthrough — so the same config can be committed and used
      on both a GPU box and a GPU-less machine.
    • [bold]vendor[/bold] (string): GPU vendor. Default: "nvidia".
      Values: "nvidia" or "amd".  Absent ⇒ "nvidia" (backward compatible).
    • [bold]devices[/bold] (string): Which GPUs to expose. Default: "all".
      Values: "all", "0", "0,1", or "GPU-<uuid>".
      NVIDIA: mapped to CDI device entries (nvidia.com/gpu=...).
      AMD: mapped to /dev/dri/renderD<N> nodes (or amd.com/gpu=... in cdi mode).
    • [bold]mode[/bold] (string): AMD only. Default: "devices".
      Values: "devices" (raw /dev/kfd + /dev/dri render nodes, no host
      toolkit) or "cdi" (amd.com/gpu=... via the AMD Container Toolkit).
      Rejected for vendor="nvidia".
    • [bold]capabilities[/bold] (string): NVIDIA only. Default: "compute,utility".
      Valid: compute, utility, graphics, video, display, compat32.
      "compute,utility" is sufficient for PyTorch/CUDA training.
      Rejected for vendor="amd" (ROCm has no driver-capabilities concept).
    • [bold]hsa_override_gfx_version[/bold] (string): AMD only, optional.
      Sets HSA_OVERRIDE_GFX_VERSION inside the jail to make ROCm treat an
      unsupported/consumer GPU as a known gfx target (e.g. "11.0.0" → gfx1100,
      "10.3.0" → gfx1030). Best-effort, same-architecture-family only.
    • [bold]seccomp_unconfined[/bold] (bool): AMD only, optional. Default: false.
      Opt-in --security-opt seccomp=unconfined (enables memory mapping for
      some HPC/numactl workloads). Removes syscall filtering — leave off
      unless a workload actually needs it.
    • [bold]vaapi[/bold] (bool): AMD only, optional. Default: false.
      VA-API video encode/decode acceleration. Bakes mesa (radeonsi VA
      driver) + libva-utils (vainfo) into the image and sets
      LIBVA_DRIVERS_PATH inside the jail. Requires enabled=true and
      vendor="amd" — device nodes and the render group come from the
      regular AMD passthrough. Adds ~1 GB to the image (mesa pulls LLVM),
      which is why it's opt-in. Verify in-jail with: vainfo

    NVIDIA host prerequisites (on the GPU machine):
      1. NVIDIA driver installed (nvidia-smi works)
      2. nvidia-container-toolkit installed
      3. sudo nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml

    AMD ROCm host prerequisites (on the GPU machine):
      1. amdgpu kernel driver installed (amdgpu-dkms) and /dev/kfd present
      2. Host user in the group owning /dev/kfd + /dev/dri/renderD*
         (usually 'render'; some distros ship them world-writable)
      3. (cdi mode only) sudo amd-ctk cdi generate --output=/etc/cdi/amd.json
      ROCm userspace (HIP, rocm-smi) lives in the image, not on the host —
      use a rocm/* base image for working compute.
    When GPU passthrough is active, yolo lifts the container's locked-memory
    soft limit to the host hard cap ([cyan]--ulimit memlock=<host-hard>[/cyan])
    so the GPU runtime can pin device queue buffers.  Current ROCm (7.2+) runs
    fine at the common 8 MB rootless cap — no host change needed.
    Run [bold]yolo check[/bold] to verify GPU readiness on a given host.
    Subject to config change safety (human approval required).
    Example (yolo-jail.toml):
      [machine.gpu]
      enabled = true
      devices = "all"
      capabilities = "compute,utility"
    Example (yolo-jail.toml):
      [machine.gpu]
      enabled = true
      vendor = "amd"
      mode = "devices"
      devices = "all"

  [bold]kvm[/bold] (boolean, default false): Expose /dev/kvm inside the jail.
    When true, yolo adds [cyan]--device /dev/kvm[/cyan] to the container run
    command plus [cyan]--group-add keep-groups[/cyan] so the in-jail user
    inherits the host's kvm-group membership (podman).
    Enables nested hardware-accelerated VMs inside the jail (QEMU,
    firecracker, Android emulator, kernel dev workflows).  Runs full-speed
    virtualization via KVM instead of falling back to software emulation.
    Host prerequisites (verified by [bold]yolo check[/bold] when enabled):
      1. CPU virtualization extensions enabled in firmware (VT-x / AMD-V)
      2. kvm kernel module loaded ([cyan]modprobe kvm_intel[/cyan] or [cyan]kvm_amd[/cyan])
      3. Your host user is a member of the kvm group
    Not supported on macOS (Apple hosts use the VZ framework) or on the
    Apple Container runtime (no device passthrough).  Skipped with a warn
    when /dev/kvm is absent on a Linux host.
    [yellow]Security note:[/yellow] /dev/kvm is a kernel hypervisor interface.
    The attack surface is narrow — historical CVEs have mostly been
    guest-to-host escape bugs requiring attacker code in a KVM guest —
    but it is strictly larger than no-kvm.  Leave this off unless you
    actually need nested virtualization.
    Example (yolo-jail.toml):
      kvm = true

  [bold]programs[/bold] (table, [bold]USER SCOPE ONLY[/bold]): What a launch does about
    programs nothing declares any more.
    • [bold]autoprune[/bold] (boolean, [bold]default false[/bold]): Remove orphans at boot.
      An ORPHAN is something installed in this jail's per-workspace home that no
      selected pack declares — what a dropped pack left behind.
      Every boot already NAMES them ("boot catalog: ..." lines, with sizes);
      nothing removes them unless you set this.
      With it on, each launch removes what it cataloged, printing every path first.
      [yellow]It is destructive and it runs with nobody present.[/yellow] ~/.local/bin
      is also where YOU may have put things, and yolo cannot tell a tool you installed
      by hand from a dropped pack's leftovers — both are "installed and undeclared".
      Look before you enable it:
        yolo programs ls              # in the jail: the orphans and their sizes
        yolo programs remove          # what removing them would unlink (a dry run)
        yolo programs remove --apply  # do it once, by hand, instead of every boot
      Workspace configs cannot set this. A repo-committed, agent-editable file must
      not be able to authorise deleting your programs; a workspace-scoped `programs`
      is a validation error, not a silent no-op.
      Every backend: on macos-user the launch hands the switch to the sandbox's
      bootstrap, which runs the same boot catalog (notch-convergence.md NC-D71).
      Not yet run on a Mac.
    • [bold]overrides[/bold] (table, keyed by program name, [bold]default none[/bold]): Build one
      program from a checkout you are developing, in place of its pack's own source. The
      name is the program's bin as its pack declares it.
      Example (~/.config/yolo-jail/config.toml):
        [programs.overrides.board]
        path = "~/code/board-cli"
      Each entry takes [bold]path[/bold] (required): the checkout, an absolute path or one
      starting with ~/. A relative path, ~user/, an empty value, or any other type is a
      validation error naming the key to fix. An unknown key inside an entry is an error, so
      a misspelling cannot pass silently; the former [bold]run[/bold] is no longer read, and
      its error says the pack's own run is used. A bad entry is ignored at launch with a
      warning naming it, and its valid siblings still apply. A malformed user config applies
      no override at all.
      USER SCOPE ONLY. A workspace value is a validation error that names this file, because
      a repo-committed, agent-editable file must not choose which bytes your programs run.
      Overrides are not inherited by a nested launch: the inner jail reads its own user
      config.
      Applies only to a program its pack builds from its own tree (via "pack"). At each
      fresh launch, `yolo host` launch and `yolo pack build`, on every backend, the program
      is built from the checkout exactly as from the pack's tree: the pack's own build and
      run, the same sealed build and store, keyed by the checkout's contents as they sit on
      disk (uncommitted edits and git-ignored files included, .git skipped). An unchanged
      checkout reuses its build; an edit is built at the next fresh launch, never in a
      running jail. Every launch prints a line naming the checkout and whether it was
      rebuilt or reused. A build that fails stops the launch as any failed build does
      (YOLO_ALLOW_MISSING_PROGRAMS=1 starts it anyway), and never falls back to the pack's
      copy. The program is refused when the path does not resolve to a directory, or is or
      contains your home, this config directory or yolo's state directory. An override of
      any other program a selected pack declares refuses the launch, naming the way to build
      it from a checkout: a fork pack (via "source", fork_of, and a git+file:// source). An
      override naming a program no selected pack declares does nothing; `yolo check` lists it.
      An entry may instead be [bold]{ prebuilt = true }[/bold]: run the pack's verified
      prebuilt artifact for a program built from its pack's tree (via "pack"), even when the
      pack ships its source. yolo never swaps a prebuilt in on its own: a source that cannot
      be built here (a Mac with no sandbox account, say) is refused, naming the setup step
      and this setting. With it set, every launch, `yolo host` and `yolo pack build` fetch
      the artifact, check its sha256 and print a line naming it. A pack with no prebuilt for
      the platform refuses the program, naming the platforms it does declare. "prebuilt"
      and "path" in one entry is a validation error naming both.
      Example (~/.config/yolo-jail/config.toml):
        [programs.overrides.board]
        prebuilt = true

  [bold]resource_groups[/bold] (table): Owner-only selection for host resource groups. No mapping is enabled by default. A selected mapping is intent only: this build cannot verify or enforce host placement, so `yolo` refuses mapped launches and `yolo check --no-build` reports placement as unsupported/unknown. No group manager, controller, device or policy probe runs when there is no matching mapping.
    • [bold]default[/bold] (string): Explicit fallback owner unit for workspaces without a more-specific mapping. Setting this opts those workspaces in.
    • [bold]maintenance[/bold] (string): Owner unit reserved for explicitly attributed machine-wide maintenance work. It is not inherited from the current directory and is not used by this build.
    • [bold]agent_percent[/bold] (integer): Planned agent share for future finite group budgets. Default: 5; valid range: 1 through 99. This value does not apply a cap in this build.
    • [bold]workspaces[/bold] (table): Exact mapping from quoted canonical absolute workspace paths to owner unit names.
    • [bold]projects[/bold] (table): Mapping from quoted canonical absolute project roots to owner unit names. The nearest component-bounded root is used after exact workspace mappings.
    Empty or unmatched mappings leave the workspace off. Project configuration cannot set or override this owner-only key. Use `yolo check --no-build` to inspect the selection.

  [bold]machine.resources[/bold] (table): Container resource limits.
    The legacy JSONC key is `resources`.
    Sets hard cgroup constraints on the jail container via podman flags.
    memory, cpus and pids_limit are enforced by the kernel — the jail cannot exceed them.
    io is not a limit, and is described on its own below.
    On macos-user, which has no cgroups: memory is checked by sampling every two
    seconds inside the sandbox, which stops the session's largest process when it is
    over (not kernel-enforced); cpus sets GOMAXPROCS, CARGO_BUILD_JOBS,
    RAYON_NUM_THREADS and OMP_NUM_THREADS, no higher than the Mac's CPU count, a
    default programs may ignore; pids_limit is read and ignored. The launch says each.
    • [bold]memory[/bold] (string): Maximum memory. Format: number + suffix (b/k/m/g).
      Examples: "8g" (8 GB), "512m" (512 MB), "2g".
      Maps to --memory flag. OOM-killed if exceeded.
    • [bold]cpus[/bold] (number|string): CPU limit as a decimal. Default: no limit.
      Examples: 4 (four cores), 2.5 (two and a half cores), "0.5" (half a core).
      Maps to --cpus flag (CFS quota).
    • [bold]pids_limit[/bold] (integer): Maximum number of processes. Default: 32768 (Podman's built-in default of 2048 is too low for agent workloads).
      Prevents fork bombs and runaway process creation.
      Maps to --pids-limit flag.
    • [bold]io[/bold] (string|object): Disk I/O priority for every process in the jail, so a
      build yields the disk to your desktop when both want it. Default: "normal".
      "low" is best effort, level 7; "idle" is the idle class; "normal" sets nothing and
      keeps the priority the launching process has. io = "low" is shorthand for
      io = { priority = "low" }, and priority is the only key the table takes.
      Examples: io = "low" (the one to start with), io = "idle" (a build can crawl
      while your desktop reads the disk).
      ADVISORY, NOT A LIMIT: any process can raise its own priority again, and the
      priority reaches reads and synchronous writes but not buffered writeback, which
      is most of a build's output. Only the bfq and mq-deadline disk schedulers honor
      it, and mq-deadline honors "idle" only; kyber and none, the usual NVMe default,
      ignore it. The launch prints one line when the disk under the workspace ignores
      the value, and `yolo check` grades that disk and names the host change.
      A `nix build` runs its builders in the host nix daemon, outside the jail, so it
      keeps that daemon's priority.
      Applied on podman on Linux, nested jails included, and on macos-user as the
      session's macOS disk I/O policy ("low" is IOPOL_UTILITY, "idle" IOPOL_THROTTLE).
      Not applied on Apple Container or podman on macOS, where the workspace reaches
      the Mac over VirtioFS, which carries no priority; the launch says so on both.
      Frozen at the fresh launch, like every resources key.
    Example (yolo-jail.toml):
      [machine.resources]
      memory = "8g"
      cpus = 4
      pids_limit = 4096
      io = "low"

    [bold]In-jail sub-process limits (cgroup v2 delegation)[/bold]:
    A host-side cgroup delegate runs alongside the container and performs all
    privileged cgroup operations on behalf of agents inside the jail.  No
    CAP_SYS_ADMIN or writable cgroup mount is needed inside the container — it
    validates every request and operates on the host cgroup filesystem via a
    Unix socket.
    [bold]OPT-IN since 2026-08-18[/bold] — select its pack, and until you do
    yolo-cglimit reports that it is not wired up:
      yolo pack add cgroup-delegate
    Then, inside the jail:
      yolo-cglimit --cpu 75 -- python train.py           # 75% of all CPUs
      yolo-cglimit --cpu 50 --memory 2g -- make -j8      # 50% CPU + 2GB RAM
      yolo-cglimit --pids 100 -- ./script.sh             # Max 100 processes
    It used to start whenever the platform allowed it, with no config key at
    all — which is the "presence activates" default the loophole rules delete.
    Podman is the primary supported runtime.
    Falls back to nice/timeout/ulimit if delegation is unavailable.
    Subject to config change safety (human approval required).

  [bold]ephemeral_storage[/bold] (string, default "volume"): Backing for /tmp,
    /var/tmp, and /var/lib/containers inside the jail.
    The container rootfs is mounted [cyan]--read-only[/cyan], so these scratch
    paths need explicit writable mounts. Two modes:
      • "volume" (default) — podman volumes, disk-backed, one set per
        launch. Deleted in the background after the jail exits, so quitting
        never waits for the delete; a set a crashed launcher left behind is
        removed by the next launch or [cyan]yolo prune --apply[/cyan], and
        [cyan]yolo stores[/cyan] lists them. Doesn't compete with the jail's
        memory budget. Recommended for workloads that touch large temp files
        (builds, model downloads).
      • "tmpfs" — RAM-backed scratch. Faster reads/writes, but counts
        against host free memory and can OOM the jail under pressure.
    /run and /dev/shm always stay on tmpfs in either mode (small + shared
    memory, respectively). Apple Container always uses tmpfs (its volume
    syntax differs and isn't a drop-in replacement). macos-user has no
    container: the sandbox writes the machine's own /tmp and /var/folders, on
    disk, and "tmpfs" is warned as not read there.
    Example (yolo-jail.toml):
      ephemeral_storage = "tmpfs"

  [bold]macos_log[/bold] (string): REMOVED — a config carrying it is REFUSED.
    It dialled a [cyan]yolo-log[/cyan] wrapper that ran [cyan]/usr/bin/log[/cyan] inside
    the macos-user sandbox, and the sandbox account cannot read the unified log,
    so the wrapper read nothing in every mode.  The log is now read on the HOST by
    the macos-log loophole, and [cyan]yolo-log[/cyan] is its client:

      yolo pack add macos-log
      yolo allow macos-log read        # what "user" was meant to give
      yolo allow macos-log read_all    # what "full" was

      • narrow ("read") — [cyan]yolo-log show[/cyan] and [cyan]yolo-log stream[/cyan]
        only, printed as ndjson, and only entries logged by processes running as
        the macos-user sandbox account
      • full ("read_all") — every argument passes to [cyan]log[/cyan] unchanged, as the host user
    "off" needs nothing: delete the key.  The Seatbelt profile denies the sandbox
    the log itself whatever is set.  macOS only (the loophole declares darwin).

[bold cyan]LEGACY JSONC FORMAT[/bold cyan]

  yolo still reads the format it used before TOML, for a few releases.  This
  section lists every spelling that format accepts, so you can read an old file
  and know what it does.  [bold]yolo config migrate[/bold] converts old files to TOML
  once, and it writes nothing unless the new file says exactly what the old one
  said.  `yolo check` and every launch say when a file is in the old format.

  Files: `yolo-jail.jsonc` (project), `yolo-jail.local.jsonc` (this machine) and
  `~/.config/yolo-jail/config.jsonc` (yours).  Each is JSON with comments.
  `yolo-jail.json` and `yolo-jail.local.json` are read in place of a missing
  .jsonc file of the same name.  Never create the .jsonc file beside one: yolo
  reads it instead, and ignores the .json file.  A legacy file and a TOML file
  of the same scope are a `yolo check` error.

  Where a legacy key went (every other key keeps its name):

    packages              -> install.nix, entry for entry
    mise_tools            -> install.mise
    gpu                   -> machine.gpu
    resources             -> machine.resources
    network.ports         -> machine.ports: "IP:HOST:JAIL/udp" becomes
                             { host = HOST, jail = JAIL, address = "IP", protocol = "udp" }
    network.forward_host_ports -> machine.forward: 5432 becomes
                             { jail = 5432, host = 5432 }, and "JAIL:HOST" names each side
    env_sources           -> env.sources, entry for entry; an inline object becomes
                             { set = {...}, unset = [...] }, a null value moving to unset
    brokered              -> allow.<source> (your user config) and requests.<source>
                             (a project's file); see "brokered" below
    profile               -> active_provider; "*" becomes `default`, and a null
                             becomes "native"
    profiles              -> providers.<provider>.variants.<name>, selected as
                             "<provider>/<name>"
    loopholes             -> allow.<pack> (the grant a switch gave, and the
                             loophole's settings); see "loopholes" below
    the inline value of a model row: `id` -> `model`, `context_window` -> `context`,
                             `input` -> `accepts`, `cost` -> `price`

  A legacy null drops what a lower file wrote.  TOML has no null, so the
  conversion writes each kind of value's own removal:
    a list (packages, security.blocked_tools, env_sources ...) -> an empty list
    one server or tool (mcp_servers.<name>, lsp_servers.<name>, mise_tools.<tool>)
                          -> "off"
    an agent under profile -> "native" under active_provider

  [bold]convert_later[/bold] — (boolean, [bold]LEGACY USER FILE ONLY[/bold]): `"convert_later": true` in
    ~/.config/yolo-jail/config.jsonc stops the launch's offer to convert old
    files to TOML, for every old file this machine reads.  A TOML file refuses
    it, because it has nothing to say there.  No command writes it.
    Legacy only (~/.config/yolo-jail/config.jsonc):
      { "convert_later": true }

  Each pair below says one thing twice: the TOML a migration writes, then the
  legacy file it came from.

  [bold]brokered[/bold] (object, [bold]repos: WORKSPACE SCOPE; sets, grant_kinds: USER SCOPE; grants: both[/bold]):
    The legacy spelling of a brokered loophole's grants and repositories (see
    BROKERED LOOPHOLES under FIELDS).  Each key is the source the loophole's
    manifest declares as `brokered.source`, such as "github" or "git".
    • [bold]grants[/bold]: in your USER config, only {"kind": "read", "repo": "*"}, read
      access for every workspace to its own approved repositories; any other grant
      there is an error.  In a WORKSPACE file, the specific grants this workspace holds,
      each naming the repository it covers, as in
      {"kind": "create-branch", "repo": "github.com/o/r"}.
      • kind: "read", which every source defines, or a kind the source's manifest
        defines.  The git pack defines "create-branch", "branch" and "tag"; the
        github pack defines "create-pr", "create-issue", "runs" and "approve-run".
        Your user config's grant_kinds must list it (or, for "read", your user config
        holds the read grant itself); anything else is a `yolo check` error naming the
        key that would allow it.
      • repo: the host and path a remote reduces to (host in lower case with a dot or
        a port, path with no scheme, user or ".git"), or "*" for every repository of
        the scope.
      • branch, for a "branch" grant only, and tag, for a "tag" grant only: the
        branch or tag it covers, as in "branch": "main" or "tag": "v*".
      • workflow, for a "runs" grant only, and actor, for an "approve-run" grant
        only: the workflow file or the login it covers.
    • [bold]grant_kinds[/bold] (USER SCOPE ONLY): the kinds of grant a workspace may hold for
      this source, as in "grant_kinds": ["create-branch"].  Listing a kind grants
      nothing by itself.  A workspace file may NOT name grant_kinds.
    • [bold]repos[/bold] (WORKSPACE SCOPE): more repositories for this workspace, as in
      "repos": ["org/lib"], with the entry rules `requests.github.repos` has.
      "repos": null in the local file clears the list.  A `repos` list in the user
      config is a `yolo check` error.  The old form, "workspaces" keyed by a
      workspace's path, is retired: move each entry into its project's
      yolo-jail.local.jsonc; host `yolo check` prints each edit.
    • [bold]sets[/bold] (USER SCOPE ONLY): the same list `allow.<source>.sets` holds, each
      entry the same fields.  A config that writes both spellings reads both lists,
      the TOML entries first; a name may appear once across the two.
    The conversion maps each grant kind to a capability: for git, "read" is `fetch`,
    "create-branch" is `new_branches`, "branch" is `push` and "tag" is `push_tags`;
    for github, "read" is `read`, "create-pr" is `create_pr`, "create-issue" is
    `create_issue`, "runs" is `runs` and "approve-run" is `approve_runs`.  A
    workspace grant naming one repository converts only when that repository is a
    remote of the workspace, and a workspace grant with "repo": "*" does not convert.
    Example (~/.config/yolo-jail/config.toml):
      packs = ["git", "github"]

      [allow.git]
      always = ["fetch"]
      on_request = ["new_branches", "push", "push_tags"]

      [allow.github]
      always = ["read"]
      on_request = ["create_pr", "runs"]

      [[allow.github.sets]]
      name = "review"
      mode = "windowed"
      window = "1h"
      admit = ["pr comment", "pr review"]
    Example (~/.config/yolo-jail/config.jsonc):
      {
        "packs": ["git", "github"],
        "brokered": {
          "git": {
            "grants": [{"kind": "read", "repo": "*"}],
            "grant_kinds": ["create-branch", "branch", "tag"]
          },
          "github": {
            "grants": [{"kind": "read", "repo": "*"}],
            "grant_kinds": ["create-pr", "runs"],
            "sets": [{"name": "review", "mode": "windowed", "window": "1h",
                      "admit": ["pr comment", "pr review"]}]
          }
        }
      }
    Example (yolo-jail.toml):
      [requests.github]
      repos = ["org/lib", "org/docs"]
    Example (yolo-jail.jsonc):
      { "brokered": { "github": { "repos": ["org/lib", "org/docs"] } } }

  [bold]loopholes[/bold] (object): The legacy spelling of loophole settings, and of host
    services declared inline.  Each key is a loophole name (it must match
    ^[a-zA-Z][a-zA-Z0-9_-]{0,63}$).  A key does one of two things.  When a selected
    pack ships a loophole of that name, the key OVERRIDES that loophole.  Any other
    name DECLARES an inline host service.
    OVERRIDING a pack's loophole takes only these keys:
      • "settings" (object): the loophole's own settings, which `allow.<pack>` holds
        in TOML, typed by its loophole.toml the same way.  Every setting is user scope.
      • "env" (object): extra environment variables for the host daemon.
      • "jail_env" (object): extra environment variables set INSIDE the jail, merged
        over the ones the manifest declares.
      • "enabled" (boolean): the switch an older yolo read.  It switches nothing now:
        a pack's loophole runs whenever its pack is selected.  The conversion writes
        the grant the switch used to give.  On a brokered loophole (github-broker,
        git-broker) it is an error naming the grant to write instead.
      "command" and "doctor_cmd" are REFUSED there by name: the loophole's manifest
      fixes them, and a config that seemed to change them would change nothing.
    Example (~/.config/yolo-jail/config.toml):
      packs = ["host-processes"]

      [allow.host-processes]
      fields = ["pid", "comm"]
      on_request = ["view"]
    Example (~/.config/yolo-jail/config.jsonc):
      {
        "packs": ["host-processes"],
        "loopholes": {"host-processes": {"enabled": true, "settings": {"fields": ["pid", "comm"]}}}
      }
    A setting under a loophole with no "enabled": true does not convert; `yolo config
    migrate` names it, and `yolo config set allow.<pack>.<key> <value> --user` writes
    it by hand.  A loophole switch in a project's legacy file does not convert either:
    `yolo request <pack> <kind>` asks for the grant in TOML.
    DECLARING an inline host service takes:
      • "command" (array of strings, required): the command to launch on the host when
        the jail starts.  "{endpoint}" in any argument becomes the host-side path the
        service should listen at; "{socket}" is accepted as an alias.
      • "env" (object): extra environment variables for the host daemon (NOT the jail).
      • "description" (string), "doctor_cmd" (array of strings).
      • "preamble" (boolean, default false): an inline daemon is a program yolo did not
        write, so it gets no framing preamble unless you ask.
      • "jail_endpoint" (string): the jail-side path, which must start with
        /run/yolo-services/.  Default: /run/yolo-services/<name>.endpoint.
        "jail_socket" is accepted as an alias.
      • "enabled" (boolean, default true): false switches the service off without
        deleting it.
    An inline service listens on a plain Unix socket, and the jail finds it through
    YOLO_SERVICE_<NAME>_SOCKET.  It runs only beside a jail: at the host no verb starts
    it, and `yolo host apply` names each one as not applying.  TOML has no spelling
    for an inline service, so `yolo config migrate` does not convert one.  Move it into
    a pack instead: `yolo pack init` starts one.
    Legacy only (~/.config/yolo-jail/config.jsonc):
      {
        "loopholes": {
          "auth-broker": {
            "command": ["~/code/auth-broker/serve.py", "--socket", "{socket}"],
            "env": {"KEYS_FILE": "~/secrets/keys.json"}
          }
        }
      }

  [bold]packs[/bold], legacy entries: a legacy file names a pack outside yolo by its path.
    • A bare name selects a shipped pack, as in TOML.
    • A PATH names a pack folder: ~/dotfiles/packs/mine or /opt/packs/mine.  The "~/"
      is expanded against your home at load.  file:///abs/path means the same thing.
      Two forms are refused, both naming the fix: file://~/… (the "~" parses as the
      URL's host; drop the scheme) and relative paths ./x and ../x.
    • A git address names a remote pack:
      git+ssh://git@host/org/repo//subdir?ref=main.
    • An object takes:
      source      required unless the entry is a bare shipped-pack name: a path, a
                  file:// URL or a git address.
      name        the name `yolo pack ls` prints and the staging folder.  It defaults
                  to the last path segment, or a git address's subpath.  Two entries
                  may not share one.
      only        globs to include; a glob matches a FOLDER prefix, so "skills/rust-*"
                  takes the whole skill folder.  Default: everything.
      exclude     globs to drop, applied after `only`.
    A path entry converts to a `<source>/<name>` handle, with a `pack_sources`
    entry for its parent folder marked `bare = true` so the pack's names do not
    change.  An object with `name`, `only` or `exclude` has no TOML
    spelling and does not convert.
    Legacy only (~/.config/yolo-jail/config.jsonc):
      { "packs": ["claude", "file:///home/me/code/acme/tools/agent-pack"] }

[bold cyan]CONFIG CHANGE SAFETY[/bold cyan]

  When yolo-jail.toml changes between jail startups, the CLI shows a
  diff of the normalized config and asks for y/N confirmation. This
  prevents agents from silently adding packages or mounts without the
  human operator noticing. Agents should still run `yolo check` after
  every config edit before asking for that restart.

  - First run: config is accepted and a snapshot saved.
  - Subsequent runs: changes require explicit y/N approval.
  - Non-interactive (piped input, CI): the launch is REFUSED. Approve
    the change for that one launch with `yolo --accept-config-changes`,
    which records it exactly as answering y would. A flag rather than an
    environment variable, so an approval is never inherited by a child
    process or left behind in a shell.

  Snapshot location: ~/.local/share/yolo-jail/approvals/<container>.json
  (HOST-side, never mounted into the jail — a record an agent could
  rewrite is not a record).

[bold cyan]AGENT PACKAGE WORKFLOW[/bold cyan]

  Agents inside the jail can request new packages:

  1. Agent adds the package to `install.nix` in /workspace/yolo-jail.toml
     (`yolo config add install.nix '"<package>"' --project` does it)
  2. Agent ALWAYS runs `yolo check` after the edit (`--no-build` is okay inside a running jail)
  3. If the check passes, agent tells the human: "Please restart the jail for new packages"
  4. On next startup, human sees the config diff and approves (y/N)
  5. Image rebuilds with the new package
  6. Agent can use the package after restart

  This keeps the human in the loop for all environment changes.
  Do NOT install packages via apt, nix-env, or other package managers.

[bold cyan]INSIDE THE JAIL[/bold cyan]

  [bold]Workspace[/bold]
    Your project is bind-mounted read-write at /workspace.
    Edits are visible on the host immediately — this is the SAME directory.
    The workspace path changes from the host path to /workspace.

  [bold]Networking[/bold]
    Full internet access, outbound and unrestricted.
    Bridge mode (default) gives the jail its own network namespace, so
    `localhost` in here is the JAIL's loopback.  The host is reached by NAME at
    `host.containers.internal` — no config needed, and it covers host services
    bound to the host's own 127.0.0.1.
    To go the other way and let the HOST reach a server running in here, publish
    it with machine.ports.  To make a host port answer at `localhost:<port>`
    in here specifically, use machine.forward (see "NETWORKING: WHICH WAY IS
    WHICH").
    Host mode shares the host's network stack: the two loopbacks become one and
    neither key is needed.

  [bold]Home Directory (/home/agent)[/bold]
    Composed at every launch, not one directory. Most of it is the
    workspace's own overlay (<workspace>/.yolo/setups/<setup>/home, one per setup): npm/go globals, shell
    and agent state, sessions. It survives restarts of that workspace's jail
    and is not seen by any other. Shared by every jail on the machine: each
    selected pack's shared dirs, the cache at ~/.cache, and, on podman, mise
    tool data at /mise (on Apple Container, /mise is a disk of the workspace's
    own). No host credential is mounted unless your config grants it.

  [bold]Per-Workspace State[/bold]
    Some state is isolated per-workspace (in <workspace>/.yolo/):
    SSH keys, bash history, copilot sessions, claude projects.
    These are NOT shared across different project jails.

  [bold]Identity & Auth[/bold]
    Git identity (name + email) is injected from the host automatically.
    GitHub CLI (gh) is not signed in: the host's gh token does not cross
    into the jail. Give gh a credential of its own if the work needs it
    (e.g. GH_TOKEN through env, or `gh auth login` in the jail).
    SSH keys are per-workspace — configure in <workspace>/.yolo/setups/<setup>/home/ssh/.

  [bold]Tools & Runtimes[/bold]
    Runtimes: Node.js 22, Python 3.13, Go (managed by mise)
    Editors:  nvim (version configurable via install.mise)
    CLI:      rg, fd, bat, jq, git, gh, curl, strace, uv, tmux
    Agents:   whichever ones your configured `packs` install — each with
              auto-approve/YOLO mode wired up.  With no packs configured a jail
              has no agent, and says so at launch.
    The 'yolo' command is available inside for nested jailing and help.

  [bold]Mise Tool Management[/bold]
    Mise manages all runtimes and supports thousands of tools from
    multiple registries:
    • aqua — pre-built binaries (kubectl, terraform, gh, etc.)
    • asdf — version-managed runtimes (python, node, ruby, etc.)
    • cargo — Rust crates (ripgrep, fd-find, bat, etc.)
    • go — Go modules (built from source)
    • npm — Node packages (installed globally)
    • pipx — Python CLI tools (isolated envs)
    • ubi — universal binary installer (GitHub releases)
    Run 'mise registry' to browse all available tools. Add tools via:
    • install.mise in yolo-jail.toml (injected into jail global config)
    • /workspace/mise.toml (workspace-specific, checked into git)
    On podman, all jails share one jail-land mise store, mounted at /mise —
    a tool installed in one jail is available in every jail. On Apple
    Container each workspace has its own tool disk at /mise, so another
    project installs its tools again. The host's own mise installation is
    fully independent; installs never cross the boundary.

  [bold]Blocked Tools[/bold]
    NOTHING is blocked by default. Blocking is opt-in, two ways:
    • the "guardrails" pack — add it to "packs" and grep -r / find are
      replaced by rg / fd (this is where the old default went, 2026-09-04)
    • security.blocked_tools in yolo-jail.toml — your own list, and an
      entry naming the same tool as a pack's REPLACES it whole
    A blocker also declares a replacement, and is generated only when that
    replacement is on the agent's PATH — so a block can never leave a jail
    with neither the tool nor its alternative. The old unconditional default
    assumed the image bakes rg and fd, which is false on the macos-user
    backend: it bakes nothing, so the block removed a tool and pointed at a
    binary that did not exist.
    Once generated, a blocker is unconditional at run time — set
    YOLO_BYPASS_SHIMS=1 for installers and scripts that need the real tool.
    `yolo host -- <program>` applies the same blockers, from your user config,
    to the program it starts (see security.blocked_tools).

  [bold]Venvs & Python[/bold]
    Venvs are per side: /workspace/.venv (plus any venv path configured in
    mise.toml and any per_side_paths entries) is shadow-mounted over a
    per-workspace backing dir, so the host and the jail each keep their own
    venv at the same idiomatic path. The jail's venv is created on first
    boot and persists across restarts; host venvs never leak in, and
    jail-built native extensions never leak out. The lockfile
    (uv.lock/requirements) in the shared workspace is the sync channel.

  [bold]Persistence Summary[/bold]
    Shared home:   /home/agent (same across all jails — auth, tools, caches)
    Workspace:     /workspace edits visible on host immediately
    Per-workspace: SSH keys, bash history, copilot sessions
    Ephemeral:     /tmp, container processes

[bold cyan]SPAWNING A NEW PROJECT[/bold cyan]

  When setting up a new project for jail use:

  1. Run 'yolo init' in the project root to create yolo-jail.toml
  2. Edit the config — add any install.nix packages or install.mise tools needed
  3. Run 'yolo check' after EVERY config edit to validate the config before restarting
  4. Run 'yolo -- bash' to enter the jail interactively
  5. Start your agent: 'yolo -- claude' (or copilot / opencode / pi / codex,
     whichever your configured `packs` install)

  [bold]For agents preparing to enter a jail:[/bold]
  Before asking the human to restart you inside the jail, ALWAYS run 'yolo check'
  and write a
  handoff document (e.g., scratch/jail-notes.md) with:
  • Current task state and what remains to be done
  • Decisions made and their rationale
  • Key files to examine first
  Your inner-jail self will be a fresh session without your context.
